# Truss v0.0.49

## Release scope

Draft release for Python embedders and operators adding explicit managed platform
grants to the [v0.0.48 runtime](v0.0.48.md). The selected tuple is Python3.11+,
PostgreSQL18.6, psycopg3.3.6, mini-racer0.14.1, UMF0.10 and Weft0.4.51 with its
exact qualified compiler cohort. Release assets and the package guide are the
delivery channels. Publication, final artifact hashes and hosted Linux
qualification remain pending under the
[managed grants plan](../managed-platform-grants-plan.md#v0049-release-execution--2026-10-22).

The native release label remains `truss-catalog-runtime/0.74-candidate`; the
selected manifest SHA-256 is
`35fd797b5cf48dd888c68e53b9e599df20cffe00f8f3d33e1563820ea808d59f`.
Exact manifest identity distinguishes this target from v0.0.48's `c4339ac7…`
target. A shared release label alone never establishes compatibility.

## Highlights and fixes

- Fresh installation accepts `tolerated_grantees`, a bounded tuple of exact
  existing platform-role names. The default empty tuple preserves strict
  installation. Selected grants and grant options remain in place; immutable
  installation metadata records their native name/OID identities and initial
  access-control-list (ACL) observations.
- Subsequent administration verifies the stored identities. Initial ACL evidence
  remains historical provenance; later grants to selected identities are allowed
  within the explicit trusted platform boundary. Ordinary privileges, private
  defaults, ownership and effective-access checks retain their exact requirements.
- A contained `InstallRefused(code="third_party_grant")` identifies the unlisted
  role and safe object-class/phase context after confirmed operation rollback.
  The local CLI prints the safe refusal as JSON and exits with status1. Prior
  caller work survives; the caller still owns outer settlement.
- Separately protected activation refuses a nonempty policy with
  `unsupported_profile` before effects. Ordinary catalog registration, module
  access, mutation, journal and feed workflows remain available within their
  selected profile.
- Strict preparation source verification accounts for ordered routine
  replacements, exact overload signatures and the finite declared ACL profile.
  It preserves declared public and registrar grants while refusing native drift.

The HF changes described in v0.0.48 remain part of the baseline; this release
adds the managed policy and its integration fixes.

## Required actions and migration

Only the latest runtime is supported. Startup never migrates an installation.
Operators must quiesce writers, back up the database and host recovery registry,
and follow the [migration guide](../../../../packages/python/README.md#runtime-migrations--v0049): inspect
status, prepare and retain the reference, apply it, reconcile uncertain
settlement, and verify before resuming application work. Install the matching
checksum-verified Weft0.4.51 compiler cohort.

The required release lineage retains v0.0.44, shared v0.0.45/46 and v0.0.47 and
adds the actual published v0.0.48 target. The v0.0.48 wheel and its public hash
must be available before that new route can be qualified. Its source profile,
original migration manifest and prior recipes/receipts must remain immutable.
All routes and recovery controls are pending final release qualification.

Forward migration installs an empty strict managed policy on existing admitted
installations. It does not opt them into platform trust. Only fresh installation
selects tolerated identities. Missing, renamed or recreated selected roles refuse;
automatic policy widening or role remapping is unavailable. Administrators must
use a separately reviewed recovery procedure for such drift.

## Hold and recovery

Hold on native drift, failed verification or uncertain settlement. Reconcile
the original attempt without resubmitting effects. Pre-commit failure rolls back;
committed changes require a forward fix or the qualified backup
restore/remigration route. Installing an old package is not database rollback.

## Qualification and known limits

The [earlier local qualification](../evidence/design-audit/managed-grants-20261022/README.md)
establishes managed behavior on its exact macOS ARM64 candidate. It includes
supported additive evolution, contained refusal for unsupported record retirement,
selected ACL variation with original evidence unchanged, and the original public
workload. Its wheel and corpus hashes identify that earlier candidate. They are
not final v0.0.49 artifacts: integration retains the newer HF62 corpus and exact
compiler cohort, and extends migration lineage through v0.0.48.

Final v0.0.49 installed-artifact, corpus, migration and hosted Linux release
receipts are pending. The mandatory finite campaign is defined in
[the Linux release workflow](../../../../.github/workflows/release.yml), including
the explicit managed-grants, migration, preparation and CLI controls. A release
pass must bind the final source, wheel, native manifest, compiler and archive.

The retained broad all-discovery diagnostic remains incomplete and unqualified.
It combines historical proof fixtures requiring removed row-home schemas and
opt-in campaigns requiring older exact compiler bundles. It is outside the
current supported release campaign; scoped passes never turn it into a complete
suite pass. Historical failures remain available in the
[original diagnostic](../evidence/design-audit/managed-grants-20261022/attempt-1/qualification.json).

Actual Lakebase service behavior, TLS/token handling and Arras adoption require
their own exact consumer receipts. The local platform stand-in does not qualify
them. Nonempty-policy protected activation, protected-profile migration,
pre-UMF0.10 migration, downgrade and other drivers remain unsupported. Successful
record/relationship retirement and broader performance targets are not added.
