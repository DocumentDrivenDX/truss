# Truss v0.0.36 — unreleased

Adds ordinary owned object graphs to the Python reference assembly. Create roots,
owned children and directed owned edges in one atomic group. Retargeting an owned
edge requires an explicit `UpdateObject.ownership_change` in the same group when
reparenting is needed. Truss updates descendant roots and versions, validates the
final forest and preserves ordered operation results. Cascades delete the owned
subtree and its owned edges; an independent incident edge must be explicitly
removed in the group.

Identity/key/page reads, relationship reads/pages, bounded traversal and retained
history preserve original root identities and their required readers. The new
`LogicalObject` carrier reports ownership; existing `ScalarObject` remains
rootless. Historical descendant versions retain their original roots after
reparenting and deletion. Dry-run remains real execution followed by caller
rollback, and original committed receipts replay after cascade deletion.

The ordinary owned query target is backend0.4.39 / binding0.5 with the explicit
`truss-postgresql-logical-query/1.0` ABI. Matching published Weft0.4.36 wheels
are pinned, including exact macOS ARM64 and Linux x64 compiler cohorts. The
unmodified Northwind Product workflow, decimal(12,2), and unnamed record/field
SQL access pass through the default public compiler. SQL uses stable UMF IDs
when authored names are absent and refuses ambiguous names. Actual
installation/runtime bytes remain bound and checked during execution.
These ordinary query checks do not qualify protected current-policy queries;
their native security gates remain open. The browser demo retains its own
frozen provider and compiler pins.

The native69 runtime adds immutable original-operation storage generated from
its UMF model. Populated native68 installations upgrade without rewriting
original keys or receipts. Basic PG18 workflows cover the owned graph, read-only
reads/traversal, history, original retry, feed delivery and ACK progress. The
public `owned_objects_workflow.py` example uses only public Python APIs and
caller-owned settlement. Release jobs run installed wheels on macOS ARM64 and
Linux x64, including a checksum-verified published SDK35 predecessor upgrade.

Owned imports, owned retained-value rebinding/key backfill, record-valued
properties, cyclic value definitions, history offload and managed-database
qualification remain unfinished. Protected current-policy queries retain their
existing rootless ABI2 scope and original UMF child; this ordinary owned graph
release does not activate protected owned facts, aggregates or UMF projection V2.

Ordinary public registration now prepares one document-validation summary rather
than per-operation inspection transcripts. Report0.5 preserves original source,
diagnostics and original-report retries; see the
[summary contract](../../02-design/contracts/catalog-registration-summary-v0.1.md).
Unnamed Fields bind to stable Field IDs, relationship extension metadata remains
in the original source, and decimal(12,2) joins the supported exact domains.
The three original consumer schemas and a500KB source pass local preparation.
The original pizza and catalog schemas also pass public registration,100 creates,
ID/key reads,200 committed updates and fresh-connection value checks. Northwind
now passes a focused Product create/update/commit/reopen/read/query workflow,
preserving decimal text `1.2300` and integer `9007199254740993`. The earlier
100-row benchmark's observation refusal at update84 remains separate unresolved
performance evidence; one successful Product workflow does not qualify all model
records or consumer actions.

Catalog support0.18 admits canonical Gregorian dates (`YYYY-MM-DD`, years0001–9999)
and exact decimal precision/scale facets, without rounding or expanding compact
large-exponent values. Create/update, import, readback and decimal key lookup
pass basic native workflows, including rejection of invalid dates and decimal
values that would require rounding. All21 original core-UMF ontology documents
in the UMF0.8 domain packs at commit `cbb6fb8718aad59fd2061b62d12976387570db2f`
register and preserve original source and reader catalog identities on PostgreSQL18.6. The256 TableSpec entries are a different
input format and are not included in that core-UMF claim. This corpus does not
prove that every valid UMF construct is supported. Date and other generic-decimal
SQL query domains remain unfinished; Weft0.4.39 adds decimal(12,2) specifically.

Practical performance still blocks release: the original100-create groups spent
46–161 seconds in COMMIT. The integrated graph change narrows repeated row-event
checks while retaining complete attempt/catalog settlement and journal checks.
Three basic native relationship/evolution workflows pass. The same catalog
workflow also passes:100-row COMMIT falls from161.269s to12.058s and create plus
commit from184.475s to40.906s. Execution remains slow (28.849s in the comparison),
so this improvement does not establish practical release performance. Native
function profiling continues. The explicit multi-group check also passes: flush
deferred constraints, retarget in a later group, flush again, refuse removal of a
required edge, commit and reopen the retargeted edge at version2. The1024-operation capacity
change, compact internal operation storage and native dispatch are separate
unreleased candidates requiring native tests and Astra review. Subsequent
single-update profiling still misses the practical performance target. Duplicate
semantic checks and duplicate module-reader checks were removed while retaining
current authorization at settlement and commit; these are reductions in repeated
work, not a claim that latency or1024-operation execution meets the target. This
candidate must not be tagged on preparation, syntax or compiler component checks
alone.
