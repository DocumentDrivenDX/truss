# Truss v0.0.50

## Release scope

The 0.0.50 candidate reduces synchronous database submissions during fresh
installation. It targets the same PostgreSQL 18.6, psycopg 3.3.6, UMF 0.10 and
Weft 0.4.51 cohort as [0.0.49](v0.0.49.md). Publication and exact installed
qualification remain release gates in the
[installer repair plan](../managed-platform-grants-plan.md#installer-round-trip-repair--2026-10-24).

## Audience and channels

Python embedders and database operators receive these notes with the immutable
GitHub release assets. Existing applications retain their public interfaces.

## Highlights and fixes

Fresh installation submits bounded batches of the original ordered SQL sources
and exact object-specific ownership and privilege commands. Catalog dependency
and effective-privilege verification use bounded set queries. Both verification
phases, exact native object identities, managed-grantee policy, private defaults,
caller-owned transaction rollback and original operation deadlines remain required.

Carrier counts measure client submissions. A captured source unit can contain
many PostgreSQL statements; fewer submissions do not mean fewer logical checks.
No VM, additional privilege or timeout increase is required by this change.

## Required actions and migration

Install the checksum-verified released wheel and matching dependency cohort.
Only the latest application runtime is supported. Every admitted UMF 0.10
database lineage retains explicit forward migration to latest without an age
cutoff; historical runtimes are migration inputs. Pre-0.10 sources remain
unsupported. Startup never migrates or resets an existing database.

The candidate leaves native installation sources and published migration recipes
unchanged. Its migration index archives the original 0.0.49 index and adds the
checksum-verified 0.0.49 wheel as an exact-current fixture. That tuple must pass
current verification without a fabricated migration edge or receipt. Older admitted native tuples use the existing explicit
offline migration tooling and preservation/recovery procedure described in the
[Python guide](../../../../packages/python/README.md).

## Rollback and support

Installation failure rolls back to the original operation savepoint and preserves
earlier caller work. A successful installation remains pending until the caller
settles the outer transaction. Do not retry uncertain settlement or downgrade an
existing database; retain the original recovery reference and reconcile it.

Actual Lakebase acceptance belongs to the separately frozen Arras campaign.
Local PostgreSQL or hosted Linux results alone do not establish that managed
service claim. The existing protected-profile and managed-grantee boundaries
remain as documented in 0.0.49.
