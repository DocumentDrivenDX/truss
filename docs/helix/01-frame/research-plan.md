# Research Plan: Storage strategy — UMF-generated per-type tables versus generic catalog storage

**Research Lead**: Project owner (DocumentDrivenDX); execution by Claude Code agents under owner review
**Time Budget**: One working day of agent execution in one sandbox session, plus owner review of the findings
**Created**: 2026-09-25
**Status**: Executed as [SPIKE-002](../02-design/spikes/SPIKE-002-storage-bake-off.md) on 2026-09-25; awaiting owner review

## Research Objectives

Every profiled system scored No fit, and [SPIKE-001](../02-design/spikes/SPIKE-001-apache-age.md)
showed that building on Apache AGE would still require most of truss. The
remaining choice is how truss stores data on PostgreSQL:

- **Option A — per-type tables generated by UMF.** UMF's DDD-to-PostgreSQL
  projection (UMF CONTRACT-043) emits one table per record type with typed
  columns. UMF performs no migrations or queries (UMF NFR-50), so a team or a
  truss runtime must write those per type.
- **Option C — generic catalog storage.** Property definitions live in a catalog;
  each object stores its values in one flat JSONB map keyed by definition id,
  with edges in their own table, per
  [discovery input](../00-discover/vision-input.md) §Draft Storage Layers.

Both options need query, migration and enforcement code. The research measures
how much of that code is per-type versus generic, and what each costs on the
outcomes the [product vision](../00-discover/product-vision.md) promises.

### Primary Research Questions

1. **Question**: What does each option cost when the schema changes?
   - **Why Important**: Schema changes without table migrations is truss's first differentiator ([competitive analysis](../00-discover/competitive-analysis.md) §Differentiation Strategy). If per-type tables absorb revisions cheaply, generic storage is not justified.
   - **Success Criteria**: For each of five scripted revisions (R1–R5 below), both options record the statements or code required, rows rewritten, the strongest lock taken and how long writers were blocked, elapsed time at the benchmark dataset size, and whether existing data that violates the new rule is detected before the revision is accepted.

2. **Question**: Which UMF assertions does each option enforce, in which layer, and can it report that?
   - **Why Important**: Runtime enforcement with a per-rule report is truss's second differentiator; the vision's primary KPI is enforcement transparency.
   - **Success Criteria**: A matrix of every assertion in the test model (nullability, length, precision/scale, integer width, primary and alternate keys, relationship endpoints and multiplicity, one record-level invariant) against both options, each cell `database`, `engine` or `none`, each backed by a rejected violating write and an accepted control write, so no cell passes vacuously. Option C tests both engine-side checks and conditional `CHECK` constraints on the shared objects table.

3. **Question**: Does any value change between write and read?
   - **Why Important**: "Nothing silently dropped" is a vision value proposition; every PostgreSQL graph layer profiled failed it.
   - **Success Criteria**: A fixed value corpus (signed 64-bit bounds, decimals at declared scale including trailing zeros, explicit null versus absent, arrays with duplicates, string-keyed maps, Unicode including combining characters and U+0000 handling, binary data, timestamps with and without offset, unknown fields) round-trips through both options using a TypeScript client on Bun, with zero silent changes, or every change listed with its cause.

4. **Question**: How much query code does each option need, and can it be generated from UMF alone?
   - **Why Important**: A runtime must generate this code; per-type code grows with the schema, generic code does not.
   - **Success Criteria**: For six query shapes (Method 5), each option's SQL is recorded with its line count, whether it is generic or per-type, and whether UMF plus a binding document supplies everything needed to generate it.

5. **Question**: Is option C fast enough?
   - **Why Important**: Generic storage is the classic performance trap (Apache Jena SDB; Bill Karwin's *SQL Antipatterns*); the vision proposes p95 within 2× of a hand-designed schema.
   - **Success Criteria**: p50 and p95 latency for each query shape and for a contended single-property update, plus on-disk size, for both options on the same dataset and machine; the C-to-A ratio reported per shape against the 2× target.

### Knowledge Gaps

| Gap | Impact | Current Confidence |
|-----|--------|--------------------|
| Revision cost of generated per-type tables versus catalog storage | High | Low |
| Whether conditional `CHECK` constraints on a shared table can enforce per-type rules at acceptable cost | High | Low |
| JSONB value fidelity through the TypeScript client path | Med | Med (hazards known from discussion, not tested) |
| Traversal latency of JSONB objects plus an edge table versus foreign-key joins | High | Low |
| How much of UMF 0.7.0 (keys, relationships) the DDL generator already emits | Med | Med (UMF CONTRACT-043 says tables stage only) |

## Scope

**In Scope**: PostgreSQL 17 (matching the PostgreSQL 17.4 subset UMF's generator is qualified for), with the fidelity and enforcement suites repeated on PostgreSQL 18.6; UMF at a pinned `master` commit; a sales model authored in UMF core 0.7.0; option A storage produced by UMF's generator where it supports the model and hand-written where it does not, each hand-written part flagged; option C storage as a minimal throwaway schema and loader; synthetic data at one scale.

**Out of Scope**: SQL Server; query language design; production code (spike code is throwaway and lives under the spike directory); UMF concepts still at proposal stage (cross-document references, schema evolution, temporal facets, constraint ideals), except where a revision needs a truss-local stand-in, which is flagged; replication, high availability, Python.

**Assumptions**: Synthetic data with realistic skew is adequate for relative comparisons; one sandbox machine gives usable ratios but not absolute figures; UMF's library is used from its repository at the pinned commit.

**Decision Enabled**: The storage strategy for truss — generic catalog storage (C), a runtime over UMF-generated per-type tables (A), or C with generated per-type tables as an optimization — recorded in an ADR, and the scope of the PRD that `frame` produces next.

## Research Methods

### Method 1: Model and data harness
- **Objective**: Shared inputs for Questions 1–5.
- **Approach**: Author a sales model in UMF core 0.7.0: Customer, Order, OrderLine and Product records; an Address value; fields with nullability, cardinality (one array and one map property), length, decimal precision/scale and integer-width facets; a primary key per record and an alternate key on Customer; relationships Order→Customer (many-to-one), OrderLine→Order (owned), OrderLine→Product, and an optional self-relationship Customer→Customer. Validate it with UMF's library. Generate a seeded synthetic dataset of about 20,000 customers, 100,000 orders, 400,000 order lines and 5,000 products, scaled down if the sandbox cannot load it.
- **Participants/Sources**: UMF `master` (CONTRACT-040 to CONTRACT-043; `fixtures/projections/ddd-postgresql-tables/`; `fixtures/relationship/core-candidate.json`; `fixtures/key/tuple-encoding-v1.json`).
- **Duration**: 1 hour
- **Deliverable**: UMF model file, data generator, load scripts
- **Decision Use**: Records which UMF 0.7.0 concepts the storage options can consume directly.

### Method 2: Build both options
- **Objective**: Questions 1–4.
- **Approach**: Option A: run UMF's DDD-to-PostgreSQL generator with a PostgreSQL binding document; add keys, foreign keys and checks by hand where the generator does not emit them. Option C: catalog tables, objects with flat JSONB maps keyed by definition id, edges, retained map and journal; a loader that turns the UMF model into catalog rows, partial expression indexes, and either engine-side validators or conditional `CHECK` constraints.
- **Participants/Sources**: PostgreSQL 17 and 18.6 built from GitHub mirror tags (the SPIKE-001 build route); Bun with `Bun.sql` or `pg`.
- **Duration**: 2 hours
- **Deliverable**: DDL for both options, loader scripts, list of hand-written parts
- **Decision Use**: Shows how much option A depends on code outside UMF today.

### Method 3: Revision script
- **Objective**: Question 1.
- **Approach**: Apply five revisions to both options on the loaded dataset while a background writer runs: R1 add an optional field; R2 tighten a length facet with existing violations; R3 add the Customer→Customer relationship; R4 change a field from one value to an array; R5 change a field from absent-allowed to required, with backfill. Record statements, rows rewritten, locks, writer blocking, elapsed time and violation detection.
- **Participants/Sources**: `pg_locks`, `pg_stat_activity`, timing from the harness.
- **Duration**: 1 hour
- **Deliverable**: Revision table with raw logs
- **Decision Use**: Tests the first differentiator directly.

### Method 4: Enforcement and fidelity suites
- **Objective**: Questions 2 and 3.
- **Approach**: For each assertion, one violating and one valid write per option, recording which layer rejected it. Round-trip the value corpus through the TypeScript client and compare byte-for-byte with the input, including reading JSONB as text and parsing it losslessly.
- **Participants/Sources**: Harness scripts; PostgreSQL 17 and 18.6.
- **Duration**: 1.5 hours
- **Deliverable**: Enforcement matrix and fidelity table with raw outputs
- **Decision Use**: Fills the vision's enforcement-transparency and no-silent-loss claims with evidence, or refutes them for one option.

### Method 5: Query code and latency
- **Objective**: Questions 4 and 5.
- **Approach**: Write SQL for six shapes in both options: fetch an object by key; one hop (order to its lines); two hops (customer to orders to lines); three hops (customer to orders to lines to products); a filtered lookup on an indexed property range; a single-property update under two concurrent writers. Record line counts and generic-versus-per-type status. Measure p50 and p95 over repeated runs after warm-up with `pgbench` or a Bun loop, plus table and index sizes.
- **Participants/Sources**: Harness; `pgbench`; `EXPLAIN (ANALYZE, BUFFERS)` for plans.
- **Duration**: 1.5 hours
- **Deliverable**: Query-code table, latency table, plans
- **Decision Use**: Checks the 2× target and whether generic queries remove per-type code.

### Method 6: Synthesis
- **Objective**: All questions.
- **Approach**: Write SPIKE-002 in `docs/helix/02-design/spikes/` with findings per question, quoted raw output, and a recommendation among A, C, or C with per-type tables as an optimization.
- **Participants/Sources**: Methods 1–5 outputs.
- **Duration**: 1 hour
- **Deliverable**: SPIKE-002 with scripts and raw outputs
- **Decision Use**: Input to the storage ADR and the PRD.
