# Truss v0.0.55 release

## Release scope

The `umf-truss==0.0.55` release adds a bounded, optional
`operation_timeout_ms` argument to `CatalogReferenceAssembly.install_in_transaction`.
It lets a caller select a longer deadline for that one fresh-install operation
when the adopted host's default is too short. The default continues to use the
host's configured operation deadline.

The override is limited to 1–180000 milliseconds. PostgreSQL's statement timeout
remains independently capped at 60000 milliseconds, and an already-active outer
host operation deadline remains the tighter bound. Later operations continue to
use the host's configured default. The override requests cancellation through
existing containment; it does not establish server termination, rollback,
transaction settlement or safe connection reuse.

The model scope is UMF model `0.10.0`. The local integration cohort is Truss
`0.0.55`, UMF SDK `0.10.2` and Core `0.10.6`, Weft `0.4.56`, and Access
`0.1.0.dev8`. The Truss package qualification target is macOS arm64 / CPython
3.12.14 with `pgserver-pg18==18.6.1` running PostgreSQL 18.6. The managed
Ashlar A1 gate passed for the selected serverless Spark 4.2.0 profile: A0 and
A1 publisher/verifier tasks succeeded, both protected ACK outcomes matched,
and post-ACK close and cleanup completed. The local Truss and R61 results are
separate evidence from that managed gate.

## Highlights

- A caller may bound one fresh catalog-install operation up to 180 seconds.
- The ordinary host deadline and later operations retain their existing
  behavior.
- Focused timeout tests and the selected fresh Truss source/ACK path passed
  locally; other hosted gates and the full suite are not claimed.

## Changes and fixes

The change affects Python hosts that install a fresh catalog using
`CatalogReferenceAssembly.install_in_transaction`. It adds no database
migration, changes no native SQL or catalog manifest, and leaves later host
operations on their existing deadline. The 0.0.53 fresh-install-only baseline
and its refusal of historical upgrades/recovery remain in force.

There are no breaking changes in the selected local scope. There is no new
operator action for existing installations. Install from the pinned GitHub
release wheel; PyPI publication is outside this release.

## Migration, hold and support

There is no new migration. Startup does not reset or upgrade an existing
database. Preserve existing environments and use only the separately qualified
fresh-install procedure; historical upgrade and receipt-recovery paths remain
unsupported under the 0.0.53 baseline.

Hold adoption if an active outer deadline is shorter than the requested
installation window, or if the host cannot contain and settle a timed-out
installation. Do not interpret cancellation request or client-side timeout as
proof that PostgreSQL stopped or rolled back. The
[install-deadline handoff](../../04-build/local-deadline-installation-handoff.md)
retains the operation and recovery boundaries.
