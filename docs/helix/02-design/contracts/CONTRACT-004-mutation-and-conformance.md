# Contract: Mutation protocol and conformance corpus

**Contract ID**: CONTRACT-004
**Type**: library
**Version**: 0.1 (draft)
**Status**: draft
**Related**: ADR-001 D5 (conformance corpus as data), ADR-002 D3, D7, D9, D10, D11, CONTRACT-001, CONTRACT-002, CONTRACT-003, SPIKE-002 (`harness/`, `loader/engine.ts`)

## Purpose

Defines, in a way that does not depend on a programming language, what each read and write operation must do against the tables of CONTRACT-001, and the language-neutral corpus that proves an implementation does it. Two implementations that pass the corpus are interchangeable over one database: either can read what the other wrote.

## Scope and Boundaries

- In scope: the operations and their effects, validation, locking, the version check, error kinds, and the conformance corpus format and pass rule.
- Out of scope: any language's method names or types (each implementation binds these operations idiomatically), the query language, the HTTP or GraphQL surface, how a host authenticates a caller.
- Owning project: truss. Implementations: truss's TypeScript engine, and any other (for example a Python implementation embedded in an application).

## Normative Surface

**Operations.** Inputs and outputs are abstract. `ref` is `(id, type)` of an object or an id of an edge.

| Operation | Effect |
|-----------|--------|
| `create_object(type, props, origin)` | Inserts an object and one `object_key` row for each key whose components are all present, returns its `ref` and `ver` 1. A key already held by another object fails as `key_conflict`; a key in `key_tombstone` fails as `key_reserved` when `setting.key_reuse` is `"forbid"`. Writes a `create` journal row. |
| `update_object(ref, set, unset, expected_ver?, origin)` | Changes the named properties, returns the new `ver`. A change to a key component also updates that key's `object_key` row, or inserts or deletes it when a component becomes present or absent; a conflict fails as `key_conflict` or `key_reserved`, and the old value is written to `key_tombstone`. A change that alters no value writes nothing and does not raise `ver`. |
| `delete_object(ref, expected_ver?, origin)` | Deletes the object and its composed children and owned objects, in one transaction; their key rows go with them by the foreign key, and each key value is written to `key_tombstone`. Refuses when any other edge refers to it. |
| `create_edge(rel_type, source, target, props, order_key?, origin)` | Inserts an edge between two existing objects of allowed types. |
| `update_edge(id, set, unset, expected_ver?, origin)` | As `update_object`, for an edge. |
| `delete_edge(id, expected_ver?, origin)` | Deletes an edge. |
| `get_object(ref)`, `get_edge(id)` | Returns the record with its `ver`, or `not_found`. Values are read as text and parsed exactly (CONTRACT-001). |
| `find_by_key(type, key_id, values)` | Returns the object holding that key value, or `not_found`: the canonical key text is built from `values` (CONTRACT-001, Key identity) and looked up in `object_key`. An incomplete key is `invalid`. |
| `list_objects(type, limit, after?)` | Keyset pages ordered by `id`, served by the `(type_id, id)` index; `limit` required. Returns the items and a marker that says whether more remain. |
| `list_edges(object, direction, rel_type?, limit, after?)` | As above, for the edges of one object, ordered by `order_key` (NULLs last) then `id`; the paging marker is the pair `(order_key, id)`. An ordered relationship's binding declares the index that serves this order. |
| `import_batch(records, load_id, origin)` | Applies imported records so that repeating the same import changes nothing. An object record is identified by its type and primary key, an edge record by its relationship and the two endpoint ids. An authorized valid identity held by a live record is skipped and reported; a tombstoned absent identity skips under `key_reuse` forbid and may be created under allow. The Import identity and skip precedence rules below govern validation order. Any other record is created as `create_object` or `create_edge` would, and a `record_source` row is written with the `load_id` and the record's `source` facts. An eligible new record that fails full validation or names a missing live endpoint is rejected and stored nowhere. Objects are applied before edges across the whole input. In an engine-owned scope, accepted records commit in bounded batches with their source and journal rows, so an interrupted import is completed by running it again. In an adopted scope, all effects remain pending and the host alone commits or rolls back (CONTRACT-007). Returns counts of created, skipped and rejected records. A type with no primary key cannot be imported idempotently; its records are rejected as `invalid` with that reason. |
| `apply_group(operations, origin, request?)` | Applies an ordered list of `create_object`, `update_object`, `delete_object`, `create_edge`, `update_edge` and `delete_edge` operations as one atomic unit. The write protocol's catalog check runs once, for the group; each operation's steps 2 to 7 run in order, and an operation may name an object an earlier one created through an alias. The whole lock set is planned and acquired before graph effects, using the shared hierarchy and revalidation of CONTRACT-009. Cross-row participation/invariants are checked on the simulated final group state. Opposed-order groups honoring that hierarchy must pass US-040-AC3; arbitrary host SQL may still cause a reported retry. Every journal row of the group has the same `origin` and the same transaction. If any operation fails, none takes effect and the error names the failing operation's index and its own kind (`group_failed`). Returns the results in order. **Idempotency.** Request-enabled execution follows CONTRACT-009's authorized scope, verified semantic-input identity, request lock and replay decision order. It must preserve every original ordered result, including mixed no-op/changed entries. The journal-only request-index spike cannot prove complete replay; ADR-005 now selects the fixed complete-result receipt home; replay readiness remains gated on its complete native installation/protocol qualification. A claimed caller hash is verified, never trusted as equality proof. Equal qualified requests replay without effects; different semantic input conflicts. At least 24-hour complete-result retention is required by US-043, independently of ordinary journal trimming. US-043 now requires complete all-no-op replay, consistent with FR-54; its persistence and longer while-journal-retained window still require governing reconciliation. Request-free groups remain independently implementable. |

### Import identity and skip precedence

Before checking live or reserved identity, validate the import envelope, selected catalog/type/relationship, required authored primary-key components or typed endpoint identifiers, and authorization to attempt that record. Unknown/keyless type, malformed identity or unauthorized input rejects; it is not a skip. Acquire shared catalog/business-identity locks and revalidate the live/reservation observation under CONTRACT-009. A hidden live identity cannot be treated as absent; the qualified host disclosure policy determines how its outcome is exposed.

If an authorized valid identity is already live, return skipped without validating or applying replacement nonidentity payload/source facts. If it is reserved, skip under key_reuse forbid; under allow, the reservation remains but does not prevent creation when no live identity exists. Skips never change payload, version, source/load id, journal or tombstones. This preserves user corrections even when an old source payload no longer satisfies the current nonidentity schema. It does not permit malformed primary-key values to identify a record.

Only an identity eligible for creation proceeds to full value/source/endpoint-existence and invariant validation, then atomic canonical/derived/source/journal insertion. Missing live endpoints for a new edge reject. Input records are processed deterministically: objects in submitted order before edges in submitted order across the whole input. Repeated equal identities in one batch therefore create at most once and later entries skip; different replacement payloads do not overwrite the first created record. The report must retain each submitted record's original index despite phase ordering. Engine-owned batch durability and caller-owned pending/savepoint semantics remain CONTRACT-007's authority. Complete public report schema, batch bounds and deleted-edge reservation encoding remain separate gates.

### Storage-key participation transitions

A key is held only when its selected binding derives a complete participating tuple. Apply CONTRACT-003's complete validation and missing/null precedence before changing membership. A transition from held to omitted frees the exact old tuple and writes its reservation in the same transaction, just as a value-changing re-key does. An omitted-to-omitted update has no key or reservation effect; graph value/version/journal effects still follow actual property changes. Omitted-to-held admission checks the full new tuple against live membership and retained reservations under the selected configuration. Held-to-equal preserves key membership and creates no new reservation even when retained lexical property spelling changes; held-to-different reserves the old tuple and admits the new one atomically. These classifications compare qualified complete tuple equality, not property text, hash equality or omission reason text. Failed validation, collision, reservation or journal production restores all old membership and record state. Catalog backfill/remapping must use its separately reviewed migration procedure rather than invent record mutations to apply these transition rules.

[Draft import-input declaration](bindings/truss-import-input-v0.1.d.ts) separates explicit complete object primary-key or typed edge identity from exact profiled nonidentity payload bytes. Admit the outer version/profile/target/load/origin/resource envelope, source byte/digest integrity and record identity before live/reserved observation. Do not decode or validate replacement values/source/ownership/order-key content for an authorized identity that skips. The payload profile is a declared trusted format, not document-supplied code; byte integrity does not imply payload validity. Only an eligible creation decodes its exact value/source/ownership/order fields under the selected profile, validates complete rules and verifies any identity-bearing payload fields agree with the admitted identity. Disagreement rejects creation, never changes identity or overwrites a skipped record. Identity alone cannot satisfy missing required creation payload. Preserve raw payload provenance and original index while processing objects before edges. Exact payload wire/decoder/resource profile remains an explicit import design output; no duplicate UMF parser/compiler is introduced by this carrier.

### Deleted-edge reservation identity

For this draft profile, an imported edge's business identity is its qualified relationship plus ordered **typed immutable storage endpoint identities**, not the endpoints' primary-key values. Source/target roles are significant. The reservation uses the same identity derivation at import and deletion, with `key_num` zero and the relationship as its type namespace (CONTRACT-001). Retain the original relationship/endpoint definition and encoding pins with the historical reservation; current definitions cannot silently reinterpret its bytes.

Under forbid, repeating the original relationship and historical endpoint tuple skips its reservation after authorized identity admission, even if those endpoints are now deleted; skip precedes live endpoint-existence validation. Without a matching reservation, an eligible new edge with missing live endpoints rejects. Under allow, a reservation alone does not suppress creation, but creation still requires both exact typed endpoints to be live and otherwise valid. Recreating an object under the same primary key allocates a new storage ID; an edge naming that new endpoint is a different identity and does not match the old reservation. No transitive reservation follows a logical business key. This preserves US-034's default-forbid repeat guarantee while keeping allow's explicit reuse semantics.

The proposed encoding is a domain-separated, version-pinned canonical tuple of source type ID, source storage ID, target type ID and target storage ID, each canonical positive decimal text. The relationship namespace, source epoch and identity/encoding profile participate in comparison/lock admission; do not compare bare tuple bytes across them. Reversing endpoints, changing a type or substituting a recreated endpoint must produce a distinct identity. Exact native tuple storage/canonical byte procedure and migration remain qualification gates; delimiter concatenation, untyped IDs and business-key substitution are invalid implementations of this identity rule. Changing this rule requires an explicit reservation migration/profile rather than a deployment setting toggle.

[Draft import facade](bindings/truss-import-capability-v0.1.d.ts) separates runBatches, which owns bounded engine transactions, from applyInTransaction, which never ends the supplied transaction. Report execution is engine_owned only for the batch-owning entry point; supplied caller handles report host_adopted and supplied outer engine handles report outer_engine_scope. Both supplied-scope modes prohibit committed batch/success counts before the surrounding transaction outcome, preserve pending progress and apply operation-local containment. An execution failure returns the exact error plus the indexed interrupted report whenever any writer submission occurred; report null requires verified no submission and cannot discard earlier committed/pending/unknown progress. Invalid envelope results occur only before writer submission. Reported/interrupted is not full-load success. Scope/disposal/authority checks apply to both entry points, and runBatches cannot silently adopt a host transaction. This extends the draft report vocabulary; exact profile/schema digests must agree, with no inferred compatibility for older readers.

An empty records array is a valid processed empty load after ordinary input/profile/target/configuration admission. Report inputCount and every count as zero, with empty outcomes/batches/unprocessedIndices, the exact verified input digest and observed execution/catalog/configuration context. It submits no record writer and creates no record/source/key/reservation/journal/feed effect. Supplied-scope methods do not end the transaction; batch-owning execution creates no artificial empty batch/commit evidence. A failure before coherent context observation remains an execution/admission failure, not a fabricated empty success. Empty success supplies no native writer qualification.

Report inputSha256 is recomputed under domain truss-import-input/0.1.0 using CONTRACT-009's selected canonical-byte profile over the complete admitted ImportInput tree, including original record order, layout/import/value/catalog pins, loadId/asserted origin, exact identity components, payload profiles and verified complete payload artifacts. Attempt ID, executor handles, current selected configuration, actual batch partition, observations and report counters are execution provenance outside submitted input. Preserve original payload bytes; absent source and explicit empty source may normalize to the same created source map under the declared default but remain distinct submitted evidence/digests. Digest equality is neither full-input equality nor record identity/replay authority: import skip still uses qualified business identity and current authorization/reservation rules. Missing/unsupported canonicalization or artifact integrity refuses admission before writers; no hash-only substitute for retained input provenance.

The [deferred payload schema](import-payload-v0.1.schema.json) reuses exact-value/map and typed-history identity definitions, excludes aliases/unknown members and permits the declared missing-source default. Eleven shape probes include duplicate-name, wrong known-source type and identity-agreement controls left to semantic admission. Invoke decoding/schema checks only for eligible creation; eager payload validation would violate identity-first skip precedence. Exact bytes/grammar/native codec support remain separately qualified.

The [import envelope schema](import-input-v0.1.schema.json) closes identity/profile/artifact structure without referencing the deferred payload schema. Eight shape probes explicitly include undecodable payload bytes that pass envelope shape; integrity/profile/identity admission remains required, and eligible creation alone invokes payload decoding. Native key-number/family/total-primary identity semantics cannot be inferred from this shape.

### Import source assertions and lookup

[Draft decoded import payload](bindings/truss-import-payload-v0.1.d.ts) reuses AuthoredValue, stored-only ownership, OrderKey and exact map source carriers. Its version/kind must agree with the record and selected payload profile. Duplicate value names/source map keys refuse creation rather than last-value-win; source author/at/system entries, when present, admit only exact string/null states under the source rules below. Empty source map explicitly means no supplied source members, not generated author/time/system. Missing source is the existing declared empty-map default for eligible creation; preserve its original absence in submitted evidence, and do not extend this default to required values/identity/ownership fields. Unknown source entries retain exact values and unsupported native representation refuses explicitly. Object payload includes all required creation values, including complete identity fields; verify resolved field ownership/order and key-profile equality against the separately admitted primary identity. Mathematical equality may permit identity 1.0 versus stored payload 1.00 while preserving both original inputs; unsupported rounding/normalization cannot manufacture agreement. Missing identity values are not filled from identity as an implicit default. Stored ownership/edge order/endpoint legality is validated only for eligible creation; aliases and executable payload content cannot enter this profile. Exact UTF-8 JSON serialization of this declared tree, lexical/token grammar and native source realization still need their selected codec/resource evidence.


An import source is a JSON object. Its optional known members author, at and system are Unicode scalar strings or explicit JSON null; missing members remain missing. at is opaque authored source text (including date-only forms), not a database timestamp: no timezone conversion, Date decoding or default current time occurs. Strings preserve spelling, including empty strings and authored offsets. Invalid known-member type rejects an eligible new record. Missing source input becomes an empty source object on the imported record; it never invents author/time/system. Unknown members are preserved under the selected exact-value profile; unsupported exact representation rejects with a loss/encoding diagnostic rather than silently rounding.

`get_record_source(entity_kind, entity_id)` accepts a typed exact storage identity in the current read context. For an authorized visible imported record it returns `{status:found, entity_kind, entity_id, load_id, source}`. For an authorized visible directly created record it returns `{status:absent}`. For an unknown or inaccessible record it returns `not_found` under the host disclosure policy, without confirming provenance existence. Native null source members remain present nulls; absent members are omitted. Storage success does not authenticate these supplied assertions.

Later edits and skipped imports cannot rewrite load_id/source. Source insertion is atomic with the created record and journal. Historical source rows survive canonical deletion, but ordinary live-record lookup cannot reveal them after deletion. A historical lookup requires a separately qualified retained-ownership authorization profile; native support remains gated until that profile is selected and qualified. A new record created with a reused business key has a new storage identity and new source facts; it cannot acquire the previous record's provenance.

The [draft historical source binding](bindings/truss-historical-source-v0.1.d.ts) is a separate opt-in retained-context lookup, not fallback behavior of live `get_record_source`. Admit exact source epoch/typed original identity/profile and the complete retained creation/definition inventory. CONTRACT-005's current-authority procedure authorizes the union of original declaring owners and, for an edge, both original endpoint owners before disclosing source existence, facts or gap diagnoses. Neither current key reuse nor a replacement live record can supply that context. Retained owner pins establish what requires authorization; they do not preserve old grants as current permission. Missing required original owner context refuses disclosure, rather than treating the orphan source row as public.

For an authorized historical identity, found returns the immutable exact original source fact with matching identity/endpoints and independently verified creation/owner/current-authority evidence. Absent requires complete qualified original creation inventory proving no source fact was produced by the direct-create path; an empty source query alone is insufficient. Unknown or hidden identity yields non-disclosing not_found with no request/evidence/fact. After authorization, missing retained source/creation evidence yields unavailable, not absent. No latest-row/source substitution or reexecution repairs a gap. Preserve missing/null source fields and opaque exact assertions as in live lookup. This defines the candidate semantic boundary; native retained-context loader, archive/resource/wire and current-authority procedure still require selection and qualification before support is advertised.

### Proposed direct lookup binding

The [fixed lookup observation draft](direct-lookup-observation-v0.1.proposal.sql) maps object-id, edge-id and baseline key selections to explicit native slots and complete baseline row projections. It is unexecuted source design. Pinned UMF source preservation/JSON reload/export now passes for this sixteenth draft; its four SELECT statements remain unhandled by the partial DDL extractor, with no complete query/parameter or native qualification. Object ID uses both native type/id; edge ID uses the global edge space and independently decodes relationship/endpoints. Baseline key lookup joins object_key to object on both object ID and type, compares admitted k under C equality and preserves native signed type/key domains. Empty/NULL/malformed slots refuse before submission. The caller cannot supply encoded k instead of typed component/key-profile admission.

Each statement observes up to two authorized rows: zero may become nondisclosing not_found only under complete qualified observation, one requires full record/owner/current-authority/decoder admission, and two is incompatible identity/observation evidence that refuses rather than choosing a winner. Native uniqueness is not a substitute for complete query/constraint inventory. Do not execute an elevated key-only probe to distinguish hidden key versus absent object. Row-byte, native work, decode and current-authority costs remain bounded by a separately admitted lookup resource profile; LIMIT 2 alone supplies no such bound.

The baseline k statement is not the proposed full-byte bucket lookup. The draft separately proposes one read-only statement over object_key_bucket, using route digests plus exact full native bytea namespace/key equality and a typed object join in one admitted snapshot. It returns complete private match/context evidence alongside the object projection to the registered internal observation path. CONTRACT-005 specifies its protected read/context privilege boundary; the template is not a direct application grant to the original-context column. This candidate does not call mutation guard_touch/guard_insert or inspect deleted reservations. Complete selected full-byte integrity/projection/policy/transport and snapshot compatibility are prerequisites; no source statement proves those invariants. Writers still use the existing full guard/generation protocol. A multi-statement discovery/chunk observer needs its separately qualified coherent guard/snapshot procedure and cannot inherit this single-statement read profile. Require returned namespace/key/context evidence to correspond independently to the original admitted components/key mapping before disclosure; unexpected duplicate full matches or stale source projection refuses. Never route unsupported large-key lookups through baseline text equality, truncate keys, search digests alone or claim not_found from an incomplete bucket scan. Plan direct lookup selection/binding in packages/postgresql/src/reads/lookup.ts with the shared category-specific decode-record.ts; no new SQL compiler or UMF key encoder is introduced.

Key lookup explicitly pins its encoding profile as well as local key number/definition. Resolve the qualified authored-key/local-number mapping and ordered component definitions within the admitted read catalog/context, then require exact encoding-profile agreement. A caller cannot reinterpret existing `k` bytes using a newer locally installed encoder. Portable core-Key lookup consumes UMF's qualified tuple encoding and the selected Truss native transport; native key text is not a mathematical order key. A held snapshot retains its own consistent catalog/key/object observation; it is not a historical business-key reconstruction API and cannot query today's rows under an arbitrary old catalog revision. An incompatible/stale mapping produces unavailable before lookup rather than false not_found or current-definition fallback.

#### Lookup resource and complete observation proposal

The [lookup resource candidate](bindings/direct-lookup-resource-v0.1.candidate.json) is separate from page limits because a bucket match carries full private namespace/key/context evidence. Its carrier allowance does not enlarge the selected 1 MiB key-codec ceiling or change native equality. Independent request, carrier/context, native encoded row/result, public record, owner, submission, peak/cumulative allocation and time dimensions all apply. Caller limits only tighten the same exact units. A two-row observation may need more private carrier budget than the one public record; unexpected duplicate observation is not free.

Before invoking a protected lookup, establish the native codec's finite framing/allocation procedure and original key/context/authority inventory. Charge input encoding, all native/coordinator submissions, both observed rows, repeated full-byte comparison, matched context/definition archives, private maps and output serialization. Public-record size cannot stand in for raw bytea/base64/hex transport size. Admit full returned original context and source correspondence privately before disclosure; a partial artifact or digest cannot satisfy the bound by replacing complete meaning.

If any complete result/evidence exceeds its selected dimension, withhold the entire found/not_found observation and use resource unavailable only after qualified containment. Do not classify oversized/unparsed matched evidence as absent, return a reduced record or retry under a different encoding/layout. An observed second row is incompatible identity evidence; failure to decode it completely is observation/resource failure, not proof of uniqueness. Original execution/recovery remains authoritative on timeout or uncertain termination. Native full-byte predicate scan/hash/comparison and backend workspace still require separately qualified work/cancellation bounds; two result rows do not bound all scanned bucket candidates.

[Direct-read binding](bindings/truss-direct-read-v0.1.d.ts) defines object-id, edge-id and object-key selections with found/not_found/invalid/unavailable outcomes. Object IDs include the qualified selected type; edge IDs retain global allocated-identifier lookup and decode returned relationship context under the read profile. Validate exact ID grammar/range and definition pins. Wrong object type cannot match by id alone or reveal another type's row.

Key requests supply a nonempty ordered exact-value list with property/definition pins matching the selected key. Verify ownership, key number/version, component count/order, no duplicates, scalar facets/null policy and canonical encoding. Unsupported comparison is explicit invalid/unsupported, never inferred not_found. Caller canonical text/hash cannot bypass component verification. Key canonicalization and key-row/object join use one qualified role/snapshot/profile; elevated key-existence probing is forbidden.

Found carries exact record and separate last-written/read catalog revisions; definition-only acceptance cannot relabel a record as newly written. Not_found covers absent/inaccessible records under disclosure policy and has no record payload. Invalid has permitted input diagnostics; unavailable names context/profile/snapshot/observation failure, never an empty found record. Diagnostics cannot expose hidden keys/owners. Lookup failures make no writes or checkpoint advances. Old retained encoding needs qualified decoding rather than today's guessed native casts.

### Proposed direct traversal profile

[Traversal binding](bindings/truss-direct-traversal-v0.1.d.ts) selects one to three ordered qualified relationship/direction hops from one typed start object. The proposed result is unique terminal objects reached after the complete hop sequence, rather than relational path multiplicities; Weft keeps its own bag semantics. Validate every hop/definition/direction and context before expansion. Broader polymorphic/association variants need declared mapping support and refuse unsupported selected meaning without redefining the full requirement.

Proposed cycle interpretation is no repeated typed object within a candidate path, including its start, and one terminal object per typed identity across all successful paths. Keep hop position and path-local visited identity in expansion state; a single global visited-node set can incorrectly discard valid paths at different hop positions or with different cycle exclusions. Final results sort by exact numeric type/id identity. This explicit interpretation requires story/profile owner review; path-valued results would be a separate requested capability with independent evidence, not a silently changed output.

The host/deployment bounds positive result limit, examined eligible edges, path states and retained UTF-8/state bytes separately. Check during expansion/allocation, not after unbounded SQL join materialization. Authorization applies at start, every relationship/edge and each target under one qualified snapshot. Hidden nodes cannot be traversed or revealed through internal count/limit reasons; expose only permitted scope-level outcomes. Work counters concern the qualified authorized expansion, not a public count of all hidden physical rows. Exact native query budget enforcement must be qualified independently.

Once complete bounded terminal membership is established, result paging uses one-row lookahead over its deterministic order and the same context. A more marker refers to a qualified staged result, not an arbitrary current query offset. Intermediate work exhaustion yields limited/not_established with no records presented as a complete page. A qualified staged-work protocol may resume, preserving hop/path state, dedup, pins and caller-held snapshot; otherwise restart is explicit. No partial expansion may claim end or use result LIMIT as proof of bounded work. A stage handle is host-managed, authenticated to context/liveness/generation and cannot reopen an expired snapshot; no implicit long-lived transaction is created.

Concrete state ownership/cleanup, deployment defaults and native resource enforcement remain design outputs. One-call live traversal may be qualified separately from held-snapshot resumability, but it cannot claim stable multi-call membership. Performance comparisons require the same terminal/cycle semantics on the independent baseline before ratios count. This direct profile is not a query parser/compiler.

The proposed staging binding now supplies a host-managed stage handle with identity/generation/query digest/context, expected work version for resume and a typed terminal boundary for result continuation. Retain and verify the complete normalized semantic query (start, ordered hops, selected profile/context), not digest equality alone, under candidate domain `truss-direct-traversal-query/0.1.0`. Page size/work-budget changes are separate admitted execution controls and cannot change membership/hops. A stage is bound to its owning host registry and live caller-held snapshot/connection; cross-host adoption requires an explicit qualified transfer protocol and cannot be inferred from handle text.

Private work state preserves the frontier's path/hop/visited data, unique terminal identities, all cumulative resource counters and exact snapshot/profile pins. Resume serializes expectedWorkVersion; conflicting workers cannot independently overwrite frontier/dedup state. Successful transition increments the version atomically; failed persistence leaves the prior stage authoritative. Qualified larger bounds may be admitted by the host, but counters never reset on resume and retained state still obeys its total resource ceiling. A hard bound with no permitted extension returns limited/restart, not indefinite hidden progress.

Complete terminal membership is sealed before ordered pages are served. Continuation is after the last returned `(typeId,id)`, with actual n+1 lookahead; duplicate requests under the same qualified snapshot/authority return the same page rather than consuming a mutable global page offset. Result pages cannot append newly discovered terminals after sealing. Changed grants affecting required stage visibility invalidate/refuse the stage before disclosure; do not drop newly hidden results and reuse the old complete-membership claim. Public diagnostics never reveal private frontier/hidden result counts.

Explicit release, snapshot end, invalid generation or administrative expiry invalidates stage handles. Cleanup deletes only that stage's private resources, does not commit/rollback the host transaction and does not mutate graph/feed state. Unknown or stale handles require restart/refusal, never live reconstruction under the same handle. The concrete stage storage/locking/resource profile is host-owned and must be selected/reviewed before qualification; an in-memory registry cannot claim cross-process persistence or crash resumability. These lifecycle rules close the proposed continuation semantics while JSON schema/native budget/owner review remain open.

#### Direct-page finite resource proposal

**Write protocol.** Every write operation and every group MUST follow these steps in one transaction. The transaction is the engine's own, or, when the caller passes one, the caller's (see Caller-controlled transactions and CONTRACT-007). Groups use CONTRACT-009 planning and final-state checks before persistence.

1. Read the catalog head as the first catalog/data lock, after operation setup/configuration (CONTRACT-007), `SELECT rev FROM schema_head WHERE id = 1 FOR SHARE`, and compare it with the revision being validated against. If they differ, fail as `catalog_changed` (MAY be retried). The share lock is held to the end of the transaction, so no revision is accepted while the write runs. Under REPEATABLE READ or SERIALIZABLE a head changed since the snapshot fails as `retry`. *(CONTRACT-001; ADR-002 D10)*
2. Lock the target row `FOR NO KEY UPDATE`; for `delete_object` and `delete_edge` lock it `FOR UPDATE`. Lock composed children after their parent, in ascending `(type_id, id)`. *(ADR-002 D9; delete lock Proposed)*
3. If `expected_ver` is given and differs from the row's `ver`, fail as `version_conflict` with no change.
4. Validate the whole proposed record against the catalog and report **every** violation, each with the UMF `rule`, a `path` and a `message`, and the `layer` that enforces it. Fail as `invalid` if there is any. *(ADR-002 D9)*
5. Apply the change. Values the catalog does not define go to `retained` and are reported, never dropped. A property set to explicit null is stored as `'null'::jsonb`; a property in `unset` is removed.
6. In `engine` journal mode, increase `ver` by 1, set `updated_at`, and set `rev` to the validated revision. In `trigger` mode, set `rev` and pass `origin` with `set_config('truss.origin', ..., true)`; the triggers maintain `ver` and `updated_at`.
7. In `engine` mode write the journal rows (CONTRACT-002) with the `origin` the caller gave and `db_role` from the database. In `trigger` mode write none: the triggers do, and writing them here would duplicate them. Read `setting.journal_mode` before step 1 and do not change behavior mid-transaction.
8. Commit, when the transaction is the engine's. If any step fails the transaction rolls back and nothing is visible. In a caller's transaction the operation returns to the caller after step 7, who commits or rolls back.

An operation SHOULD use prepared statements and MUST give the same results without them. *(ADR-002 D11)*

**Caller-controlled transactions.** CONTRACT-007 defines connection affinity, per-call savepoints, pending durability, imports and failure containment. An implementation MUST let a caller run any operation, or `apply_group`, inside a transaction the caller controls, and MUST NOT commit or end that transaction itself. The caller then sees the operation's results and effects inside the transaction, and may commit or roll back. A rolled-back operation leaves nothing: no object, edge or key row, no journal row, no tombstone, no request record, and no lock. Identifier and sequence values it consumed are not reused, so ids may have gaps. An operation inside a caller's transaction holds its row locks and the catalog head's share lock until the caller ends the transaction, so a caller keeps such a transaction short.

**Cross-row rules.** Minimum multiplicity and aggregate invariants are checked in step 4 under the parent lock (`FOR NO KEY UPDATE`) or in a SERIALIZABLE transaction. A deferred trigger under READ COMMITTED alone is never reported as database enforcement. *(ADR-002 D9)*

### Database-enforcement qualification profile

A database classification names a versioned ordinary-writer privilege profile, not only a constraint or trigger. Its inventory includes table/column DML grants, sequence privileges, function EXECUTE grants and owners, search paths, RLS/FORCE RLS flags, trigger enablement, and permissions to change guards or session replication behavior. Superuser, BYPASSRLS and administrative guard modification are outside ordinary-writer qualification and must be disclosed as exclusions. A profile permitting bypass of a claimed invariant cannot receive database classification merely because the library never exercises that permission.

For each assertion, the native corpus must attempt every materially distinct authorized write path: direct canonical-row mutation, omitted/wrong derived key or multiplicity marker, direct derived-row mutation, qualified function execution and engine mutation. Require either native refusal or preservation of the invariant, with complete state/journal observations. A unique derived table proves uniqueness of its own rows; it does not prove canonical records are represented there. Use concurrent connections for cross-row claims and inspect actual grants as the tested role, rather than running attacks solely as the layout owner.

Bind the evidence receipt to the exact installed guard and privilege inventory. Removing a trigger, broadening a grant, replacing a function or changing policy/role context invalidates current qualification until refreshed. Immutable historical acceptance reports remain historical; a current support response must verify the installed profile and cannot promote a stale receipt into a current guarantee. If inventory verification is unavailable or mismatched, report unqualified/unsupported status explicitly, without silently downgrading a required guarantee and proceeding as though full support held.

*Seed corpus.* SPIKE-002's harness inputs are the seed: the sales model and its revisions R1 to R5 (`model/`, `harness/revisions.ts`), the value corpus (`harness/fidelity.ts`), and the enforcement matrix (`harness/enforcement.ts`). Cases added later cover catalog acceptance (CONTRACT-003: ordering, unknown endpoints, rebinding) and the journal (CONTRACT-002: watermark, as-of).

*Host cases.* A host MAY add cases tagged `x-<host>` that exercise its extensions (CONTRACT-001). They are not part of the pass rule.

## Error Semantics

| Condition | Outcome |
|-----------|---------|
| A revision is accepted while a write waits for the catalog lock | `catalog_changed` after the write reads the new head |
| Two writers update one object | One waits on the row lock; the second sees the new `ver` and, if it passed `expected_ver`, gets `version_conflict` |
| A journal row cannot be written | The write rolls back; the caller sees `unavailable` |
| An unknown value in `set` | Stored in `retained` and reported; not an error |
| A key listed in `find_by_key` is incomplete | `invalid` |

## Examples

```text
update_object($a, set={coverage:"substantial"}, expected_ver=1, origin={actor:"jsmith"})
  -> ver 2; journal: op=update prop=coverage old="partial" new="substantial" ver=2
update_object($a, set={coverage:"x"}, expected_ver=1)
  -> version_conflict
create_object(Solution, {coverage: 7})
  -> invalid [ {rule:"Solution.coverage:value", path:"coverage", message:"not a string", layer:"engine"} ]
delete_object($u)   where an Order edge refers to $u
  -> has_edges
```
