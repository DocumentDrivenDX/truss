# Contract: Embedding and execution

## Owner decisions — 2026-10-07

Selected execution boundary: engine-owned callback transactions commit before returning committed results; adopted transactions remain caller-owned and return explicit pending results. Pending object/edge IDs are usable only within the same live transaction. Only confirmed outer commit authorizes durable external publication; savepoint release and successful Truss operations do not. Unknown commit requires original recovery/receipt observation. No commit-by-string-ID or live cross-network transaction protocol is selected.

A host network adapter accepts one complete bounded atomic mutation batch, invokes the embedded engine-owned transaction and acknowledges success after confirmed commit. It preserves request ID/input for receipt-based retries and does not silently split one atomic request into independent commits. Resource bounds cover work the toolkit/protected procedures control; report arbitrary native/bypass resource guarantees separately. Existing graph integrity, current authority, pooling and cleanup requirements remain.


**Contract ID:** CONTRACT-007. **Type:** library/boundary. **Version:** proposed `truss-execution/0.1.0`. **Status:** draft.

## Embedded public draft example

The [compile-only batch example](bindings/truss-embedded-group-example-v0.1.ts) consumes Executor.adoptTransaction and GroupCapability.applyInTransaction with the actual host transaction, full semantic input and explicit request selection. It preserves execution failure versus domain failure/unavailable versus semantic success. It neither commits the caller nor reruns its callback. A pending created-identity view is useful only under original live-transaction custody; TypeScript identity data alone cannot enforce that lifetime.

The host may perform its earlier work and later Truss operations in the same adopted transaction, but actual outer commit/rollback remains its responsibility. The group facade owns operation-local containment under CONTRACT-009, including rollback of failed group effects while preserving prior host work. Host commit confirmation must settle the original pending result through the selected executor/recovery boundary before durable publication. The example uses declared public draft interfaces only; no driver/package implementation or native readiness is claimed.

Compile with the selected TypeScript compiler using `--ignoreConfig --noEmit --strict --target ES2022 --moduleResolution bundler --module ESNext` and the example path. Public package export names and packed-consumer/native tests remain PD/CH-05 outputs. A future network wrapper additionally needs committed-only projection and exact original request receipt/recovery; returning this embedded pending result directly over the network is invalid.

## Network response projection and cancellation

A host network success response carries only the committed projection of the existing GroupResponse: applied/committed after original engine-owned commit, or replayed/committed after qualified original receipt observation. The [CommittedGroupResponse draft type](bindings/truss-group-result-v0.1.d.ts) excludes pending execution and same-transaction replay. Its narrowing is not commit evidence; the host must obtain the original executor/receipt proof before serialization. No new toolkit capability family or commit-by-ID protocol is introduced.

Before transaction execution, admit the complete request identity/input and selected lossless transport profile under finite body/decoded limits; preserve original semantic operation order and exact numeric tokens. A network bigint uses the selected exact text/token wire rather than an untagged JSON number. HTTP status codes and endpoint/authentication naming belong to the host's selected protocol, not a second mutation meaning.

A client disconnect or canceled response delivery does not establish native rollback. If commit already succeeded, preserve the original committed receipt and permit same-ID/input recovery; never delete the receipt to compensate for acknowledgment failure. If execution or commit remains uncertain, withhold successful semantic output and preserve original recovery custody. A retry cannot silently substitute a new request ID or changed input. Request-free uncertainty cannot be recovered through a receipt that was never requested.

Cancellation before commit follows the original executor containment protocol; client closure alone cannot prove cleanup, connection reuse or release. Response encoding/resource failure after commit reports transport failure while preserving committed effects/receipt. It cannot become group rollback or partial semantic success. Host diagnostics and recovery lookup still obey current namespace/owner authorization and cannot disclose receipt existence across forbidden scopes.

## Purpose

Specify the executor and transaction boundary used by an embedded implementation. Hosts can combine Truss changes with their own database writes and retain control of commit, rollback, role and cancellation. This is a semantic contract across language bindings; TypeScript types must express it without importing a driver into core.

## Scope and Boundaries

In scope: connection/transaction ownership, statement transport, savepoints, failure containment, exact results, context lifetime and retries. CONTRACT-004 owns operation inputs/effects and error kinds. CONTRACT-003 owns acceptance. Authentication, connection creation, credentials and pool configuration belong to the host/runtime adapter. Core validation/planning performs no input/output.

## Normative Surface

### Executor

A runtime adapter MUST provide these operations to the PostgreSQL protocol package. Identifiers below are semantic operation names; language bindings MUST publish the mapping before release.

| Operation | Inputs | Result and obligations |
| --- | --- | --- |
| `with_transaction` | Callback and isolation level `read_committed`, `repeatable_read` or `serializable` | Adapter obtains one connection, begins, supplies a transaction handle, commits only after callback success, and rolls back on failure. Returns callback value only after successful commit. |
| `adopt_transaction` | Host transaction handle already begun on one connection; isolation and cancellation context | Validates adapter/connection identity and active lifetime. Marks ownership `caller`; MUST NOT issue BEGIN, COMMIT or ROLLBACK of the whole host transaction. |
| `execute` | Parameterized SQL template, ordered parameters, transaction handle | Ordered rows of exact raw cells and statement status. Uses the handle's connection exclusively for the call. |
| `savepoint` | Active transaction handle and an implementation-generated identifier | Creates an operation-local boundary; identifier cannot originate in user data. |
| `rollback_to_savepoint` | Same handle/boundary | Undoes the operation/group and its transaction-local state; returns only after rollback is confirmed. |
| `release_savepoint` | Same handle/boundary | Ends the operation-local boundary without committing the transaction. |

The SQL template is trusted Truss/backend code. Parameter values MUST NOT enter SQL text. A parameter is `{position, carrier, text}` where position is a positive contiguous integer, carrier is `text`, `integer`, `decimal`, `boolean`, `json` or `null`, and text is an exact string except for null, whose text is absent. SQL types/casts belong to the trusted template. A JSON parameter MUST be exact validated JSON text; no host float may rewrite a number token.

A raw cell is `{state:"null"}` for SQL NULL or `{state:"text",text:<exact driver text>}`. Numeric, JSONB and temporal columns MUST have an explicit text read path. Driver default JSON/number/Date decoding is forbidden. SQL NULL is a transport observation; the record decoder MUST separately distinguish absent property, stored JSON null and a present value under CONTRACT-001 and the selected native profile.

A transaction handle is opaque and connection-scoped. It records ownership, isolation, liveness and cancellation; no credentials belong in diagnostics. It MUST reject reuse after completion, cross-adapter use and concurrent calls whose statement ordering would be ambiguous. Hosts needing parallel calls use separate transactions. The adapter MUST NOT silently substitute another pooled connection or change the transaction's isolation level.

### Embedded operation scope

Adoption verification is a native observation boundary. It cannot silently recover an aborted host transaction or change ownership to engine. Native observation failure preserves the unusable/unknown state and reports it under the executor failure protocol; no automatic whole-host rollback. Recheck active lifetime/connection identity after asynchronous observation before issuing a handle. A host's established snapshot is preserved; when none exists, ordinary reads may establish the first snapshot naturally, without claiming continuity with an invented earlier cut.

The candidate execution binding carries verified read_only/read_write accessMode alongside ownership/isolation. Engine-owned creation explicitly selects mode; adoption supplies expected mode and asynchronously verifies actual host transaction state through the qualified connection-affine procedure. A mismatch refuses without changing access mode, isolation, snapshot or transaction lifetime. Synchronous caller metadata alone is insufficient when native observation is required. Core mutation/import/acceptance admission rejects read_only before write planning effects; qualified direct/compiled reads retain read-only support and use CONTRACT-005's authority procedure. Transport execute remains a trusted-template boundary, not permission to infer writability from a live handle. Final adapter capability/profile review must qualify observation across poolers and ended/failed transactions.

#### Original transaction custody and adoption arbitration

E01's native adapter profile must recognize the original host transaction identity and generation independently of caller wrapper equality. Keep one adapter-owned custody entry for that original active transaction; multiple compatible wrappers cannot issue independently usable handles that evade statement serialization. Admission reserves the entry before asynchronous native observation, rechecks its original generation/liveness/connection after observation, and publishes a handle only while the reservation still owns that entry. Concurrent adoption of the same original transaction refuses as invalid_transaction; it cannot observe on a second connection or silently share a different issuer. Unknown identity refuses rather than falling back to connection name, backend PID or caller metadata. Exact host-object recognition is adapter-owned; Truss does not define another driver wrapper.

The entry tracks idle, observing, executing, containing, unresolved and ended phases, with at most one native call or containment procedure admitted at a time. Savepoints belong to the same original entry/generation and record their confirmed creation/release lifetime. Ending or invalidating the original host transaction closes future calls through every retained handle and savepoint. A later transaction using the same connection has a new generation; it never inherits old handles, origin or recovery evidence. Duplicate adoption refusal does not invalidate the first valid handle or roll back earlier host work.

The host must exclude its own concurrent connection statements/commit/rollback while an adopted call is active, using the selected original driver/host coordination mechanism. An adapter mutex that covers only Truss calls cannot prove this exclusion. If the adapter cannot recognize original lifetime or establish the required host coordination, caller adoption is unsupported for that profile; engine-owned support cannot substitute for required embedded support. A host end observed during asynchronous admission/execution invalidates the entry and preserves actual original outcome/recovery, without guessing rollback from handle disappearance. Truss invalidation is a local admission action, not native transaction termination.

Retain unresolved entry/attempt custody until the qualified native procedure establishes containment or outcome. Disposal closes new calls but cannot erase the entry, release a caller's connection, end its transaction or free quarantined recovery resources. Resolved ended entries may drop reusable payload/handles under the selected retention profile; required original recovery evidence remains exact in protected custody. Re-adoption after a local handle is invalidated requires actual profile-qualified original transaction state and explicit host coordination, never a new wrapper around an unresolved entry.

#### Operation admission versus native call serialization

Original transaction custody lasts through the original transaction; exclusive Truss operation admission lasts only through an active call and its required containment. Successful savepoint release returns the entry to idle without ending the host transaction or invalidating its original handle. The host may execute sequential host statements between completed Truss calls, then use the same original handle again; recheck actual generation, connection, isolation/access mode and liveness at the next admission. No new detach/re-adopt API is required for this normal composition. Duplicate adoption cannot become a second independently scheduled handle during that lifetime.

Hold one private operation admission token across all native statements, savepoints, authority coordination, result admission and containment for that public operation/group. Internal executor calls under that original token serialize on the original entry; they do not recursively acquire a new public operation lease and deadlock themselves. The token is adapter-issued private custody, not caller-supplied metadata or a public TransactionHandle substitute. A public concurrent call, including through another capability sharing the transaction, refuses rather than interleaving. A group uses one admission token for the whole group; engine import uses its declared batch boundaries, while caller import retains original host ownership throughout its selected operation scope. Native worker/job calls on separately owned resources use their own declared scope and cannot borrow this token.

| Current phase and observation | Next phase / permitted action |
| --- | --- |
| No original entry; recognized active host transaction | Reserve observing entry, verify actual state, then publish idle handle; failed observation closes admission and preserves unresolved original custody when required |
| Idle; next public call passes original state and host exclusion checks | Executing under one private operation token; only its serialized internal native calls may proceed |
| Executing; operation succeeds and all required boundary restoration/release is confirmed | Idle; return pending caller result or wait for engine COMMIT under the original engine procedure |
| Executing; operation requires cleanup | Containing under the same original token; no second public call or host connection reuse until qualified completion |
| Containing; operation-local rollback/release and restored state are confirmed, host transaction remains usable | Idle; return the qualified failure without ending earlier host work |
| Executing/containing; native outcome or cleanup cannot be established | Unresolved; retain token/attempt custody and quarantine, with no later operation admission |
| Any phase; original native transaction end is actually observed | Ended for that generation; preserve in-flight actual outcome/required recovery, reject every retained handle/savepoint |

The proposed Executor<HostTransaction> signatures remain unchanged: there is no public operation-token argument. Distinguish the public operation guard from the short native-call guard. The admitted assembly operation closes over its private guard/ownership state and invokes ordinary executor methods sequentially; each executor method obtains only the native-call guard for its duration. Internal group/mutation helpers consume the private admitted context directly rather than calling public capability admission again. Never infer reentrancy from a TransactionHandle, async-local runtime state, thread identity or a caller boolean. Browser-compatible core must not require Node AsyncLocalStorage to establish ownership.

The selected composition must provide one original public-operation arbitration registry shared by all assemblies/capabilities that can use the same executor-issued transaction. Per-assembly WeakMaps alone cannot establish this property across two assemblies. The original executor/host composition owns the registry and must expose its qualified private integration to the assembled protocol implementation; construction verifies exact original registry/function custody inertly. No registry name or metadata declaration creates the integration. E06 must publish this actual integration contract before adapter implementation; the existing generic Executor interface by itself does not prove it. Until that integration is selected, concurrent multi-assembly adoption/execution support is unqualified rather than silently assumed. Required embedding still includes coherent sequential host/Truss composition.

Cancellation signal delivery alone changes neither native phase nor transaction outcome. A pre-admission cancelled call performs no statement; active cancellation stays under the original token until its containment/outcome is established. Unexpected host statements during an admitted call are a host-coordination contract violation: retain original evidence and refuse further admission until qualified native observation restores a known state. Do not guess that either operation was rolled back or replay the call. The selected adapter profile must define observable host coordination and these exact transitions, including asynchronous completion after disposal; this table does not claim driver support.

Every public operation or group accepts either an adopted caller transaction or an engine-owned execution scope. Reads, catalog acceptance and imports obey the same ownership distinction. Truss MUST NOT commit any adopted scope.

For a caller scope, Truss creates a savepoint before operation-local statements. On success it releases that savepoint and returns a result with durability `pending`; locks remain until the caller ends the transaction. On failure it rolls back to and releases the savepoint before returning an error. Earlier host work is preserved. On engine-owned success, results have durability `committed` only after commit succeeds. A caller may combine several successful Truss calls and host statements; a later caller rollback removes all their transactional effects.

`durability` is result-envelope metadata, not record state. Reading pending effects on another connection is not promised. Sequence values consumed during failed/rolled-back attempts are not reused. A failed COMMIT MUST NOT be presented as a successful operation; a lost connection during COMMIT yields `commit_unknown` and MUST NOT cause an automatic retry.

Each operation reads journal mode consistently within its scope. The catalog-head lock is the first **catalog/data lock**, after connection setup, savepoint and configuration reads. This clarifies CONTRACT-004's “first statement” wording without permitting a write before the catalog check. Journaling context is transaction-local and restored at the call boundary; it MUST NOT leak to later host writes or the next pool borrower. A group shares its origin internally. Settings changes require the administrative exclusion procedure in the layout profile; an implementation MUST NOT switch journaling ownership mid-transaction.

### Imports

An engine-owned `import_batch` may commit bounded batches as CONTRACT-004 describes. Within a caller transaction, it MUST NOT commit batches: accepted records are pending in that transaction, rejected records are reported under per-record savepoints, and the caller may roll the entire import back. A transaction-fatal error stops the import and is not counted as a rejected record. This ownership distinction is returned in the result envelope. Partial engine-owned progress includes a resumable report; it cannot claim all-or-nothing batch import.

### Retry and cancellation

Truss reports CONTRACT-004 retry kinds. In caller transactions it MUST NOT replay the caller callback or silently retry Truss operations. For serialization/deadlock errors, the host restarts the entire transaction because its snapshot and earlier host work may matter. For an engine-owned operation, retries are explicit host policy and restart the whole operation against a fresh catalog context; no uncertain commit is retried without its qualified idempotency protocol.

Cancellation propagates to the active statement. Return only after operation rollback is confirmed or the context is marked unusable. If savepoint rollback/release fails or the connection is lost, report `transaction_unusable`; caller recovery is a whole-transaction rollback/discard, not another operation. Cancellation does not imply that a successfully committed earlier import batch was undone.

Cancellation and timeout are observations, not proof of rollback. Before COMMIT begins, an engine-owned attempt can report cancelled/no effects only after whole-transaction rollback is confirmed. Once COMMIT has been sent, cancellation or connection loss that prevents learning its outcome is `commit_unknown`, even if the deadline expired first at the host. If commit is confirmed, report committed rather than claim cancellation undid it. For adopted transactions Truss never sends COMMIT; a cancellation after successful savepoint release cannot revoke earlier pending host work, and host transaction completion remains the host's responsibility.

Every adapter profile must define how it drains the in-flight statement, establishes rollback/commit outcome and quarantines an unresolved connection before pool reuse. A server cancel acknowledgment alone is not a rollback receipt. Do not start outcome lookup while an original transaction can still commit and interpret temporary absence as definitive nonapplication. Request-receipt lookup and bootstrap marker inspection require qualified fresh observation plus termination of the original attempt when absence is used to authorize reapplication. Without a qualified identity protocol, uncertain mutation outcome remains unresolved for host recovery; reading current values is insufficient to prove whether this attempt committed.
