# Contract: Journal

## Owner decisions — 2026-10-07

Accepted by the owner: history supports reconstruction without current rows. Creates retain complete new records; deletes retain complete prior records; updates retain ordered property deltas plus the selected complete metadata boundary witness. The selected two-property mutation emits two property deltas and one witness. Local retention is deployment-configurable, including very short or zero retention. Continued reconstruction after local deletion requires a qualified durable archive handoff; otherwise return explicit unavailable history. Required consumer/receipt protections and atomic history production are not bypassed by a zero-retention setting. Native producers, archive continuity and selected encoding/profile qualification remain build gates.


**Contract ID**: CONTRACT-002
**Type**: schema
**Version**: layout 0.2 (draft)
**Status**: draft
**Related**: ADR-002 D7, CONTRACT-001 (storage layout), CONTRACT-004 (mutation)

## Purpose

Defines the journal: the append-only record of every change to an object or an edge, written in the same transaction as the change. It is the audit trail, the source of as-of reads, and the feed that carries changes to a warehouse. Every implementation writes it the same way so any reader can use it.

## Scope and Boundaries

- In scope: the row shape per operation, the `origin` object, ordering, the consumer watermark, as-of reads, append-only rules, retention.
- Out of scope: the table's DDL (CONTRACT-001), who is allowed to write (a host), the Delta publication job.
- Owning project: truss. Source tags as in CONTRACT-001: ADR-002 (accepted), SPIKE-002, or Proposed.

## Normative Surface

**Row shape.** One row records one property change, or one whole-record create or delete. Columns are in `storage-layout.sql`.

| Column | Rules | Source |
|--------|-------|--------|
| `seq` | From `journal_seq`; unique with `at`. Assigned at insert. Not commit order. | SPIKE-002; Proposed |
| `at` | The database clock when the statement ran (`clock_timestamp()`). Not a commit time. The partition key. | SPIKE-002 |
| `xid` | The writing transaction (`pg_current_xact_id()`). | SPIKE-002 |
| `entity_kind` | `o` for an object, `e` for an edge. | Proposed |
| `entity_id`, `entity_type` | The record's id, and its `type_id` (object) or `rel_type_id` (edge). | Proposed |
| `ver` | The record's `ver` after the change. | Proposed |
| `op` | `create`, `update`, `delete`, `retain`, `rebind` or `transform`. | ADR-002 D7; Proposed (values) |
| `prop_id` | The property changed, or NULL for a whole-record row. | SPIKE-002 |
| `old_value`, `new_value` | The property's old and new value as JSONB, in the encodings of CONTRACT-001. | SPIKE-002 |
| `rev` | The catalog revision in force. | SPIKE-002 |
| `origin` | A JSON object; see below. | SPIKE-002 (text); Proposed (object) |

**Rows per operation**

| Operation | Rows written |
|-----------|--------------|
| `create` | One row with `prop_id` NULL and `new_value` the object `{"props": <the props map>, "retained": <the retained map or null>}`. `ver` is 1. |
| `update` | One row per property whose value changed, with `old_value` and `new_value`. All rows of one change share `entity_*`, `ver` and `xid`. A write that changes nothing writes no row and does not raise `ver`. |
| `delete` | One row with `prop_id` NULL and `old_value` the object `{"props": ..., "retained": ...}` as it was. `ver` is the version it had plus 1. |
| `retain` | One row when a later change stores data that matched no definition in `retained`: `prop_id` NULL, `old_value` NULL, `new_value` an object of the retained entries added, keyed by the author's field name. A `create` row carries `retained` in its envelope and writes no `retain` row. |
| `rebind` | One row per property when retained data is bound to a newly defined property at catalog acceptance (CONTRACT-003): `prop_id` the new property, `old_value` the retained value, `new_value` the bound value. The retained entry is removed in the same change. |
| `transform` | One row per property whose stored value a catalog revision's declared total transform changed (CONTRACT-003): `prop_id`, `old_value`, `new_value`, and `rev` the new revision. |

A `rebind` or `transform` is a change: it raises `ver` and sets `updated_at`.

A record's history is ordered by `ver`, then `seq`. All rows of one change share `entity_*`, `ver` and `xid`.

**`origin`.** A JSON object that records who or what caused the change. Defined keys:

| Key | Meaning |
|-----|---------|
| `actor` | The person or service the caller asserts. Not authenticated by truss. |
| `db_role` | The database role the change ran as, taken from the database, never from the caller. |
| `load` | For a bulk load, `{id, initiated_by}`. When present, `actor` SHOULD be absent. |
| `reason` | Free text. |
| `request` | `{id, hash}` of an idempotent group (CONTRACT-004, `apply_group`): the caller's request identifier and a hash of the group's inputs. Written on every journal row of the group. |
| `x-*` | Reserved for hosts. truss preserves and ignores them. |

An implementation MUST NOT set `db_role` from a value the caller supplied.

**Who writes what.** `setting.journal_mode` says, and every implementation MUST read it before it writes.

| Mode | Journal rows, `ver`, `updated_at` | `origin` |
|------|-----------------------------------|----------|
| `engine` | The engine writes the journal rows and maintains `ver` and `updated_at`, in the write protocol (CONTRACT-004). | The engine builds it. |
| `trigger` | Triggers on `object` and `edge` write the journal rows and maintain `ver` and `updated_at`. The engine MUST NOT write journal rows or set `ver` or `updated_at`; doing so would duplicate rows and raise `ver` twice. It passes `origin` with `SELECT set_config('truss.origin', '<json>', true)` in the same transaction. | The trigger reads `current_setting('truss.origin', true)`, adds `db_role`, and ignores any `db_role` in it. |

A change in `engine` mode made by plain SQL is not journaled; in `trigger` mode it is. A host that must journal every change, including plain SQL, uses `trigger` mode.

**`db_role`.** The role the operation ran as, determined by the database and never taken from the caller: `current_setting('role')` when it is not `none`, otherwise `session_user`. Inside a `SECURITY DEFINER` function `current_user` is the function's owner, so it MUST NOT be used. Verified on PostgreSQL 16.2 and 17.9 (4 Oct 2026): after `SET LOCAL ROLE app_w`, a definer function saw `current_user` as the owner, `current_setting('role')` as `app_w`, and a transaction-local `truss.origin`.

**Atomicity.** A change and its journal rows MUST commit in one transaction. If a journal row cannot be written the change MUST NOT commit. *(ADR-002 D7)*

**Append-only.** The journal MUST NOT be updated or deleted by a role truss or a host recognizes. A trigger that refuses UPDATE, DELETE and TRUNCATE is RECOMMENDED; a host MAY require it. Retention removes whole partitions, never rows. *(Proposed)*

**Bypass.** A change made by plain SQL that does not go through an implementation, or a host's trigger, is not journaled, and the enforcement report says so. A host that must journal every change MUST add triggers or write functions (CONTRACT-001, extension rules). *(ADR-002 D7)*

**Ordering and the consumer watermark.** `seq` and `at` are assigned when a row is inserted, not when its transaction commits, so a row with a higher `seq` can become visible before a row with a lower one. A consumer that reads the journal incrementally MUST NOT use `seq` or `at` as a watermark. It MUST read only rows whose `xid` is below the snapshot's minimum, in `(xid, seq)` order:

```sql
SELECT * FROM truss.journal
WHERE xid < pg_snapshot_xmin(pg_current_snapshot())
  AND (xid, seq) > ($last_xid, $last_seq)
ORDER BY xid, seq;      -- served by the journal_feed index
```

Every transaction with a lower `xid` has then finished, so no row below the watermark can appear later. The order is stable and complete, and it is the order in which transactions were given an `xid` (at their first write), not the order they committed. *(Proposed; verified on PostgreSQL 16.2 and 17.9 on 4 Oct 2026: a committed row is withheld while an older transaction is still open, and both appear in order once it commits.)*

**As-of reads.** The state of a record at version `v` is its `create` row's `new_value.props` with every `update`, `rebind` and `transform` row of versions up to `v` applied in order. A value is interpreted with the definition in force at the row's `rev`, taken from `schema_change` when a revision changed it. As-of reads are by version; a read by time is not defined in layout 0.1, because `at` is not a commit time. The object row stays canonical. *(ADR-002 D7)*

**Partitions and retention.** `journal` is RANGE-partitioned by `at` and has **no default partition**: once rows sit in a default partition, a range partition covering them cannot be created (verified), and a retention job could never remove them. A deployment MUST create partitions ahead of time, and a write at a time no partition covers fails with `check_violation` and rolls the change back, which is the intended failure for an audit trail. The deployment chooses the interval, the horizon and the retention period; truss defines none. Retention drops whole partitions, never rows.

## Precedence and Compatibility

### Reconstruction completeness outcomes

**Definition-only revisions and unchanged record versions.** Version reconstruction uses the interpretation pins recorded by the complete baseline and applicable record events. A later catalog acceptance whose transform returns identical presence-qualified stored values creates no record mutation/version merely to attach the new definition (CONTRACT-003). Its `schema_change` still records the definition change. Reconstructing the unchanged record version continues to return its recorded historical interpretation; it cannot silently substitute the latest catalog or report that the record was transformed. A current read separately identifies its current read catalog revision. Reinterpreting historical values against a selected later catalog requires an explicitly designed and qualified profile; this version-only request does not provide that operation. Missing original interpretation pins yields history-unavailable even if the latest definition exists.

[Draft reconstruction result binding](bindings/truss-history-reconstruction-v0.1.d.ts) separates reconstructed, deleted, proved-unwritten, hidden/not-found, unavailable and unsupported outcomes. Successful reconstruction must match the requested typed identity and version and carry independently verified baseline, event and definition inventories. Digest-shaped strings are evidence references, not proof of completeness. Authorize disclosure before returning gap reasons or unsupported meaning; the hidden/not-found result carries neither request context nor record payload. Deletion and unwritten outcomes cannot carry a fabricated empty record.

[Draft event schema](history-event-v0.1.schema.json) now defines closed create/delete/property/transform/rebind/metadata envelopes, referring to the exact-value and complete-record schemas. [Twelve shape cases](../../04-build/evidence/design-audit/check-history-event.ts) distinguish required payloads and presence homes; [receipt](../../04-build/evidence/design-audit/history-event.json). Positive event count and digest syntax cannot prove group completeness. Verify same typed entity/source epoch/producing xid/event version, complete ordered sibling inventory and the independently recomputed group digest under ADR-007 before exposing a completed mutation/version.

Semantic admission also checks event/record identity correspondence, old/new definition/context validity, exact scalar/time domains, legal presence transitions, mutation version continuity and operation-specific invariants. Rebind requires the declared retained-to-property move with all four homes consistent; arbitrary schema-valid states cannot authorize overwrite/discard. Metadata before/after must describe an authorized supported change, not a general record-type mutation. Whole-transaction side facts and current historical owner union remain CONTRACT-005/006 obligations; the event schema does not establish them or qualify old partial rows.

[Draft complete record schema](history-record-v0.1.schema.json) implements ADR-007's proposed carrier inventory only. It does not reinterpret the old props/retained-only create/delete profile as complete. Validate all historical definition/ownership pins, positive native identity/version ranges, timestamp semantics, property/retained uniqueness and aggregate resource bounds before reconstruction. Unknown required carrier fields refuse this wire version; preserve unknown authored value content through its qualified exact/opaque homes rather than discarding it. Schema success alone cannot prove a retained baseline or event continuity.

Version reconstruction requires a complete retained baseline and every required subsequent event through the requested version, plus the exact historical definitions needed to interpret them. A complete create envelope or separately qualified checkpoint can supply a baseline; current canonical state cannot fill an unknown gap. Verify event ordering/version continuity under the selected event profile, including multi-row versions, metadata changes and deletion. An empty journal query alone does not prove the requested version was never written.

Return reconstructed state only when that completeness is established. A qualified delete boundary yields an explicit deleted outcome with its version/context, not an invented live empty record. A genuinely unwritten version may return the story's unwritten/not-found outcome only when retained identity/history evidence proves it was not written. Missing partitions/events/baselines/definitions produce history-unavailable with the permitted horizon/profile reason. Unsupported required event meaning produces unsupported rather than partial reconstruction. Authorization is checked first under CONTRACT-005's retained-context rules; ordinary callers cannot use outcome distinctions to probe hidden existence.

Retention must publish what reconstruction evidence remains, independently of consumer feed protection. Dropping a partition may make an old version unavailable even when all registered consumers have advanced. Do not advertise unlimited version reconstruction from append-only storage when retention removes required inputs. A qualified checkpoint may restore support only for its declared version/horizon and complete state/definition context; it cannot recreate earlier discarded versions. Horizon/checkpoint metadata and exact result schema remain D-07 design deliverables. Successful reconstruction of one record does not prove a graph-wide consistent historical snapshot.

- Versioning: with the layout version (CONTRACT-001).
- Precedence: a row's columns govern; `origin` keys not listed here are preserved untouched.
- Backward compatibility: preserve unknown origin content; optional nonsemantic display omission requires the pinned profile's permission and cannot erase archived assertions. Unknown required operation/event meaning blocks reconstruction/complete consumption with unsupported before application or acknowledgment. It cannot be ignored as if no change occurred. A new required operation needs explicit compatible profile/version and refreshed evidence.

## Error Semantics

| Condition | Outcome | Retry | Recovery |
|-----------|---------|-------|----------|
| A journal row cannot be written | The whole change rolls back; the caller is told it failed | After the database recovers | None; no partial change exists |
| A reader asks for a version that was never written | No rows; the reader reports an empty history, not an error | no | |
| A consumer's saved watermark is ahead of the snapshot minimum | The consumer reads nothing until the minimum passes it | wait | |
| No partition covers `at` | The write fails with `check_violation` and rolls back | after a partition is created | Create partitions ahead of time |

## Non-Normative Notes

The bake-off's journal had no entity kind, no version and a text `origin`; it wrote one whole-record `create` row and a `migrate` operation for revisions. This contract adds the entity kind, the version, whole-record `delete` rows, a JSON `origin`, and names the revision operation `transform`. Whether the journal or the object row is canonical was left open by the layout review; ADR-002 chose the object row, and a journal-canonical design can be adopted later without changing the table set.

### Conditional lexical numeric journal correspondence

When ADR-006's exact lexical value profile is adopted, CONTRACT-004's stored-value equality governs event selection. A token change such as 1.0→1.00 is a real property change even when CONTRACT-010 NX mathematical witnesses are equal. The selected engine or trigger journal writer must retain both exact old/new values under their original type/home/codec definition and the complete selected event envelope; it cannot diff only native numeric_value or suppress the event because a business key remains mathematically equal. Engine/trigger ownership stays exclusive, with no duplicated property event.

For row-home values, reconstruct the complete admitted typed old/new state through the original payload/source/definition correspondence; raw normalized numeric output is insufficient to reproduce original tokens. For adopted typed JSONB token storage, preserve the original catalog-directed token encoding without confusing literal strings with numeric leaves. Legacy JSONB number rendering does not recover lost source spelling and cannot supply an invented old token. Any required carrier/envelope migration remains explicit under ADR-006/007 and CONTRACT-001.

One actual lexical property change follows existing shared entity/version/transaction/origin rules; an otherwise identical selected stored-value update follows the existing no-op rule. Journal failure must roll back canonical token/value/source, derived key effects and owner version together under original containment. The governing modes remain engine and trigger; journal mode selects the exclusive writer and does not change numeric stored-value equality. No third mode is introduced by this conditional handoff. No new event kind, source key encoding or compiler ABI is introduced.

### Proposed mutation-group metadata snapshot correspondence

For the unadopted complete historical profile, a non-create/delete record mutation group uses one complete metadata before/after snapshot pair to close all record-version/timestamp/context/owner/endpoint/order facts. Its before record is the original complete state at the start of that typed entity/eventVersion mutation; after is the complete final record. They are group-boundary witnesses, not instruction to overwrite staged properties or a claim that every metadata row's before equals the state after the preceding property event. Original source sequence still orders every sibling and remains in the digest. Exact producer adoption must emit this interpretation; old partial or differently interpreted metadata rows cannot inherit it.

Admit the complete original baseline, typed identity/source epoch, all historical definitions and complete sibling group before staging any result. Require one unambiguous group metadata witness for this non-create/delete procedure. Its full before image must match the independently reconstructed group-start record, including original value/source/presence and metadata meaning. Capture that start immutably, then apply every admitted property/transform/rebind delta, plus retained additions only under their separately selected new event profile, in original source order to a separate bounded staged value inventory. Every delta's before state must match the corresponding current staged home; duplicate/conflicting unaccounted transitions, wrong owner/definition or an illegal retained-to-property move refuses. No event is ignored because a later full snapshot agrees with another event.

After all deltas, compare complete staged property/retained membership and original exact values to metadata.after. Missing deltas, extra after members, silently dropped retained content or source-token substitution refuses even if event counts/digests are valid. Apply only independently admitted metadata differences: immutable typed identity/kind/creation meaning must remain valid; version/catalog/updated timestamp and selected ownership/edge endpoints/order follow their exact original mutation and definition rules. The metadata snapshot cannot authorize a field-value transform by itself, or convert an edge into an object. Validate the full after record's original context and compare its record version to the requested mutation version before admitting it as the next complete baseline.

Create/delete groups use their separately complete envelopes and original operation invariants. This non-create/delete snapshot procedure neither synthesizes their before/after states nor determines unwritten/deleted horizon semantics. Later definition-only revisions do not replace recorded interpretation. A gap or unavailable snapshot/definition remains history-unavailable; unknown required event meaning remains unsupported. Full snapshot equality is supplementary correspondence, never original sibling completeness, native commit truth or current disclosure authority.

Reserve immutable group-start, staged deltas, complete before/after snapshots, definitions, sibling inventory and comparison/encoding work under one cumulative account. Releasing an actual buffer does not refund spent work; comparing shared snapshot views still charges each required traversal. Stage every required mutation version through the request and publish only after complete original continuity/current-authority admission. Interruption cannot publish the last valid prefix as the requested version or use current canonical data to fill a missing group. ADR-007 reconstruction is already owner-selected. Exact original native snapshot producer/order/resource profile composition and qualification remain required; no further reconstruction decision is needed.

### Conditional snapshot capture and finalization procedure

The proposed complete profile binds snapshot capture to an original entity/version mutation, not the enclosing transaction or public group as a whole. Two successful changes to one entity in one host transaction retain two distinct mutation versions and boundary pairs. The second starts from the first's pending complete result under the original transaction; neither may reuse the transaction-start record. A request-free group uses the same history procedure without introducing request receipts.

1. Under the admitted entity/definition/operation guards, reserve the complete snapshot, delta, sibling and encoding account before the first canonical effect. Capture and validate the full original start record, including exact values/source, retained inventory and exposed object/edge metadata. Capture failure refuses before effects. This capture belongs to the same rollback containment as the mutation.
2. Preserve the start immutably while recording all original ordered admitted transitions, including retained additions only under their separately selected new event profile. Multiple transitions to one home retain their intermediate before/after correspondence when the selected mutation procedure permits them; do not collapse them merely because final bytes match. A truly no-op admitted operation follows its separately selected no-op rules and produces no fabricated version/group.
3. After canonical and derived effects satisfy their required finalization, collect the complete final record under the same guards and original definitions. Independently reduce the staged deltas from the preserved start and compare complete values/retained membership with that final record. Admit metadata differences and version progression separately. Intermediate capture, partial collector output or a later unrelated operation's record cannot supply the final witness.
4. Build exactly one metadata pair for this non-create/delete group. Account all original siblings, actual sequence positions and envelope bytes before final count/digest publication. Both engine and trigger modes use this semantic boundary; their exclusive producer ownership remains unchanged. Ordinary row triggers alone do not prove operation-end completeness.
5. Seal only after complete correspondence and group-manifest admission. Any snapshot, encoding, allocation, journal or manifest failure rolls back canonical/derived/version and staged history effects together under the original containment. Savepoint rollback discards captured boundaries and pending siblings of the rolled-back operation; a later retry captures its actual start anew and cannot reuse those artifacts.
6. A sealed group is transaction-local evidence until original commit is confirmed. Outer rollback removes it; lost commit acknowledgment retains the original recovery custody and does not authorize producing the same mutation again. Reconstruction consumes only independently admitted committed/historical evidence under its separate read and current-authority procedure.

The native implementation must explicitly select transactional snapshot/staging storage, operation-end scheduling and original sequence/digest realization. Insertion-assigned baseline seq and append-only journal semantics prohibit silently rewriting visible committed events to repair manifests. This procedure does not choose a sequence-reservation mechanism or approve a new physical store; those exact source/dependency/privilege/resource selections remain mandatory before producer adoption. A caller's full-record JSON cannot replace protected native capture.

### Selected reference complete-group sequence reservation

Select protected prepublication sequence reservation for the reference implementation of ADR-007's complete profile. This is an implementation design selection under the accepted reconstruction direction; exact source/profile realization still requires review and qualification before activation. This preserves the proposed identical manifest on every event and digest coverage of actual source positions without a committed-row repair pass. It explicitly changes baseline insertion-assigned seq timing; legacy layout 0.2 does not acquire this allocation rule implicitly. A source profile must identify the actual allocator, domain, privileges, native call bounds and insert behavior.

After final snapshot/delta correspondence, freeze the complete ordered sibling inventory. Reserve exactly one original native position per sibling in that order, retaining the returned position alongside its immutable payload. Require valid native domains, no repeated position and strictly increasing positions within this group. Do not require consecutive numbers: another transaction's allocation or a prior refused attempt may leave gaps. A failed/uncertain allocation cannot be replaced by a guessed value, recycled gap or timestamp-derived position; refuse the mutation under its original containment and preserve the allocator's separately qualified recovery meaning.

Construct all exact event payloads with those actual positions, original producing xid/epoch/entity/version/origin and selected historical context. Exclude mutationGroup from the canonical digest input, then compute the ordered digest and attach the same final count/digest to every sibling. Reserve all payload copies/digest work and publication capacity before submitting any journal append. Append only complete envelopes using their reserved positions; independently compare actual returned journal identity and admitted payload correspondence to the prepared inventory. A default or trigger assigning another seq invalidates the candidate, even if rows are otherwise well shaped.
