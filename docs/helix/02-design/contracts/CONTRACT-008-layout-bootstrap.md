# Contract: Layout bootstrap from UMF

**Contract ID:** CONTRACT-008. **Type:** generation/deployment boundary. **Version:** proposed `truss-bootstrap/0.1.0`. **Status:** draft.

## Purpose

Generate Truss's fixed PostgreSQL layout from a versioned UMF physical model and verify it against the storage contract. Fresh installation is a host/tooling operation; application catalog acceptance never generates tables per type.

## Scope and Boundaries

UMF owns representation, parser fidelity and generation APIs. Truss owns the physical model, required-object inventory and installation obligations. Truss MUST NOT implement a competing UMF SQL parser/deparser or reinterpret DDD as a required ontology for its system tables. This contract specifies fresh bootstrap, not automatic database migration.

## Normative Surface

### Selected installation metadata and publication order

The [metadata SQL](installation-metadata-v0.1.proposal.sql) and [UMF capture](installation-metadata-v0.1.proposal.umf.json) now author fixed `installation_marker` and `installation_archive` homes with a separate archive allocator and nonunique identity route. They are integrated in [CONTRACT-012's 0.5 review profile](CONTRACT-012-weft-storage-handoff.md). These are fresh declarations, not an adopted installer or an implicit baseline migration.

The marker singleton maps every marker-wire field explicitly: interface version, opaque installation/layout/database/schema identities, exact 32-byte bundle/inventory digests, inventory profile and original database-observed installed time. Its native `installed_at` and retained `installed_at_text` must independently match under the admitted clock/output profile; neither a host Date nor an arbitrary timestamp cast supplies original clock custody. The marker's installation identity is unique and remains within the existing wire character bound.

Archive rows retain exact role/identity/bytes, generated content digest, native-derived checked UTF-8 identity digest and original installation membership. The original generated identity expression in metadata candidate0.1 is noninstallable on PostgreSQL17.9 because convert_to is STABLE. The [UMF-authored 0.13 repair](../models/truss-layout-weft-integration-0.13.proposal.umf.json) uses an ordinary NOT NULL identity digest with an exact native CHECK; the installer/archive producer computes it from the same original identity input during insertion. This preserves exact derivation without falsely declaring a conversion function IMMUTABLE. The older source remains historical evidence and cannot be installed unchanged. Routing hashes are nonunique; the installer compares full installation/role/artifact identity and complete bytes, preserving collisions and distinct identities. Exactly one artifact exists per admitted full role/identity; PK/FK/digest checks alone cannot establish that or complete required archive roles. The deferred marker FK permits archive writes before marker insertion in the same transaction. Ordinary writers receive no direct metadata mutation or archive-allocator authority. Actual native owner/grant/body/dependency/index-size/encoding evidence remains required.

### Authoritative inputs

A bootstrap bundle contains `interfaceVersion`, `layoutVersion`, `model`, `generator`, `target`, `names`, `initialization` and `expectedCatalog`. Versions are exact strings. `model` contains UMF document bytes, identity, core/vocabulary versions and SHA-256 of those exact bytes. `generator` identifies the pinned UMF operation/backend versions and content hashes. `target` identifies PostgreSQL major/minor, database encoding and relevant locale/collation settings. `names` supplies the deployment schema and a collision-checked identifier map. Model content MUST NOT load code or acquire connections.

`initialization` is ordered, versioned Truss-owned data/policy: revision zero/head, deployment settings, administrative roles and journal-partition interval/horizon supplied by the deployment. No default journal partition is created. Partition intervals and role names are explicit inputs, not inferred from an application schema. Initialization statements, policies/functions and generated DDL each have source-qualified inventory entries; no unreported SQL patch is permitted.

For the proposed protected row-home layout, [fresh capacity initialization](row-home-capacity-initialization-v0.1.proposal.sql) is a separately inventoried initialization effect after the fixed capacity/touch homes exist and before installation marker publication. Parameter 1 is the complete original admitted layout-definition carrier, excluding future installed observations/marker/commit receipts; parameter 2 is the complete original admitted touch-retention resource profile carrier. Preserve exact bytes, original encoding/profile/hash correspondence and selected target bytea binding; no JSON normalization or caller profile substitution. The layout definition can reference the original source/model/inventory artifacts but cannot incorporate a digest of the initialized row that contains that definition. Initialization policy/statement/parameter meaning enters the bootstrap immutable basis separately; actual inserted row/commit evidence does not feed its own preimage.

The installer must prove complete fresh empty touch/capacity data scope under original namespace/head/capacity exclusion and administrative authority before submitting the fixed INSERT. The initialized singleton has all four counters zero and exactly the two admitted original carriers. Validate the one returned row, then independently recollect complete singleton/touch membership and full source/native/profile parity before provisional marker creation. Missing/duplicate rows, nonempty original touch scope, a mismatched carrier or unknown native termination prevents success; returned row count alone is insufficient. No ON CONFLICT/reset/upsert is allowed. A populated conversion requires its own complete original retained/reservation inventory and cannot reuse these zero values. Failure/commit-unknown follows the original bootstrap outcome and reconciliation protocol, never an implicit second INSERT.

The [initialization UMF capture](row-home-capacity-initialization-v0.1.proposal.umf.json) and [source receipt](../../04-build/evidence/design-audit/row-home-capacity-initialization-source.json) retain exact source/archive/reload/export through existing owner APIs. The initial physical-model profile uses UMF's `umf.postgresql` native representation from UMF CONTRACT-015. ### Coverage report

Generation returns either a blocked report or a candidate `{sql, coverage, obligations, qualification, sourcePins}`. Blocked output contains no installable SQL. SQL is complete ordered text; sourcePins include every generation input. Coverage entries contain exact physical identity, object kind, owning input path, generated statement ordinal and disposition `generated`, `initialization` or `blocked`. An inventory object without a statement/initialization entry blocks installation readiness. Unknown unused annotations may remain retained; unknown selected layout semantics block.

Required inventory includes all CONTRACT-001 tables, columns/types/defaults, constraints/actions, sequences/default ownership, indexes/collations/includes/predicates, schema comment/version, initial rows and the selected journal/role/policy functions. Optional module isolation is an explicit separate component with its own inventory. Catalog comparisons include owner/grants, row-level-security flags/policies, function bodies and partition definitions when the selected profile installs them. Environment-generated OIDs are normalized; logical/physical identities and exact values are not.

TD-045's physical reconciliation table tracks contract additions absent or unqualified in the captured 0.2 baseline: configuration archive/exclusion, selected relationship retained-content home, complete receipt/history context, four complete-feed stores/producer guards, authority and protected installation evidence. A selected profile's inventory must close every applicable row with exact model/statement/native correspondence. Baseline generation receipts cannot qualify later additions merely because the old SQL still exports deterministically. New selected layout artifacts receive a new explicit version and independent parity evidence; preserve the baseline unchanged.

Native syntax/AST fidelity does not qualify database validity. A candidate is installation-ready only with independent baseline/generated catalog comparison and behavior probes on the declared target versions. Evidence records parser version separately from server version. The currently inspected UMF parser/export profile is PostgreSQL 17.4-derived; successful 16/17 installation requires separate server evidence and never follows merely from parsing.

### Installation and versioning

Tooling MUST inspect the target schema before executing fresh bootstrap. An empty intended deployment namespace may be installed; an existing Truss layout or unknown objects in that namespace cause refusal without mutation. Roles/shared objects outside that namespace require an explicit host-owned administrative plan; no existing role is silently altered. The installer MUST not drop/recreate an existing database or silently migrate it.

Transactional DDL and initial rows install atomically. Steps that cannot run transactionally are explicit ordered obligations with cleanup evidence; the default fresh bootstrap has no concurrent-index build. All statements use safely quoted identifiers; schema substitution MUST operate on typed model/policy identifiers, not textual replacement across SQL/function bodies. A success marker is written only after the installed inventory/check passes. Failed installation returns its stage and rollback outcome; it never claims the layout is ready.

### Shipped layout migration system and consumer deployment

The owner requires Truss to ship migrations, with infrequent use expected. Physical layout/runtime upgrades belong to Truss administrative tooling; normal UMF catalog revisions remain DDL-free under ADR-002. The tooling exposes version/status inspection, an inert explicit upgrade plan, invoked application, original-attempt reconciliation and independent verification. Exact published command/package names follow B-014; the system itself is required rather than a deferred consumer responsibility.

A consumer's migration runner may invoke the shipped tooling as a deployment step and record its confirmed result. Fresh installation keeps the existing dedicated installer-owned administrative transaction; it does not adopt the consumer's already-open transaction. Transactional upgrade steps likewise declare ownership, exclusion and termination in their selected procedure. A framework that wraps every migration in one outer transaction must run this deployment step outside that wrapper. A successful framework history entry cannot replace Truss's committed marker/archive/parity evidence. A later consumer deployment failure does not imply rollback of a Truss upgrade that already committed.

Ship one exact UMF-generated fresh-layout DDL artifact with digest and a versioned ordered upgrade manifest. Each supported upgrade edge identifies its original source layout/bundle/inventory/profile, target equivalents, immutable step identity and bytes/digests, preconditions, data/codec/history treatment, administrative authority, transactional boundaries, writer-fencing/downtime requirements, validation and recovery procedure. Never derive a step by comparing version numbers alone. Unknown source, changed step bytes, incomplete native state or unsupported path refuses before upgrade effects. A caller cannot insert arbitrary SQL into a registered migration plan.

Current marker/archive and original bootstrap/administrative attempt recovery supply installation provenance. Retain ordered immutable migration input/result evidence under an explicit layout-migration domain and qualify its exact storage/initializer in the UMF model before installation. Existing key-profile migration receipts keep their distinct domain; matching migration labels do not make them layout-upgrade evidence. An exact already-applied step is a no-op only after committed original-attempt/target correspondence and current native parity. A ledger row or marker version alone cannot hide missing routines, grants or data conversion.

The default upgrade profile uses transactional DDL/data changes and holds the selected installation/catalog/security/configuration exclusions against old writers through publication. Preserve original retained IDs, history/report/configuration bytes, epoch identity unless an explicit lifecycle transition is required, and all outstanding receipt/feed/recovery protections. Recollect complete target objects, transitive callable/privilege dependencies and data-conversion invariants before target marker publication. Publish runtime readiness only after original confirmed commit and committed target admission. Unknown commit keeps admission closed until reconciliation; retry retains the same attempt and never blindly repeats DDL or issues another epoch.

Nontransactional/online/multiphase steps require a separately selected durable progress/cleanup/recovery profile; the default system refuses them. Downgrade has no implicit inverse or generic down script: only an explicitly qualified reverse edge can be applied, otherwise refuse and leave the original installed state. Recovery from a failed transactional step is observed rollback; restore is a deployment action with its own epoch/incarnation admission, not a claimed migration rollback.

Version compatibility remains CONTRACT-001's declared layout-major rule: an implementation refuses a different major. Within a major, the release still declares exact supported layout/runtime/corpus/profile ranges and upgrade edges; same major is not permission to execute against unknown routines/codecs. The post-install/post-upgrade verifier runs without modifying state and reports actual current correspondence or explicit unavailable/drift. Native PostgreSQL and Lakebase deployment qualification remain separate; current native 0.16/core 0.6 candidates are not a stable published layout.

### LM-01 candidate manifest and planner wire

The internal pure planner implements proposed `truss-layout-migrations/0.1.0` metadata. The closed manifest has interfaceVersion, family, layouts, steps and routes. Each layout has version, bundleSha256 and inventorySha256; versions are three canonical decimal components (each at most 20 digits) and hashes are exact lowercase 64-digit SHA-256 text. This is a new candidate release-version wire, not a reinterpretation of historical 0.15/0.16 review labels. Layout versions are unique in a manifest family.

Each step has id, from, to, recipe (identity/sha256), procedure (identity/version/sha256) and transactional boolean. Each route has id, from, to, direction (upgrade/downgrade) and a nonempty ordered list of step IDs. Route IDs and source/target pairs are unique. Every complete route must chain declared layouts in its stated direction with no repeated step. Only the explicitly requested source/target route can be selected; available intermediate steps do not imply a supported path. A selected nontransactional route is unavailable in this default planner profile.

The supplied observation has interfaceVersion `truss-layout-observation/0.1.0`, family and layout pin. Exact source bundle/inventory fingerprints must match the manifest. This is caller-supplied metadata at this stage, not native observation authority. The planner returns plan, no_steps or refused under scope declared_metadata_only. Frozen output retains exact source/target and ordered recipe/procedure pins; it contains no executable SQL or callback. no_steps cannot qualify already-applied migration or current installation readiness.

Reuse the existing closed numeric-free decoder's one-MiB UTF-8, duplicate-member, Unicode, depth/node/work limits. Each metadata collection is limited to 1,024 entries and each nonempty identifier/profile text to 256 UTF-8 bytes; routes/steps/layouts validate as a complete manifest before selection. Version comparison uses exact integers, never JavaScript numbers. These limits bound this controlled component's metadata work; they do not establish native migration budgets or a universal heap guarantee.

LM-02–05 must bind the selected metadata to registered original artifacts/procedures and actual installation/attempt/native observations before application. Manifest fingerprints are locators/byte-correspondence inputs, not executable registration or grants. The planner neither verifies recipe bytes nor classifies current database state. Nine unit scenarios establish exact route/order/refusal semantics; full LM-T01–08 schedules and release publication remain required.

### LM-02–05 original route application and recovery handoff

The [draft administrative carrier](bindings/truss-layout-migration-v0.1.proposal.d.ts) binds the registered manifest and route to exact source/target pins, original source observation, procedure/resource profiles and lifecycle transition profile. Its method names are internal proposals; B-014 still owns published command/package names. `apply` owns a dedicated administrative transaction for the **entire declared transactional route**. All intermediate step effects remain pending in that transaction; only the final target is eligible for publication. A route requiring independently committed intermediate states needs the separately selected multiphase profile and refuses in this default profile.

The request is evidence data, never an activation permit. Before any new upgrade effects, runtime admission MUST resolve original manifest/recipe/procedure bytes through the selected registration and verify their full correspondence. The transition profile explicitly selects unchanged epoch or a qualified lifecycle transition; a layout version change alone cannot mint an epoch. Resource admission covers the entire route, original recovery custody, retained data/history and target verification; per-step output limits cannot bound their cumulative retained allocations. Actual finite native/transport budgets and registered procedure bodies remain selected-profile outputs.

| --- | --- | --- |
| Admission | Resolve exact route, all ordered artifacts/profiles, administrative authority, dedicated transaction ownership and retained recovery capacity | Unknown route/profile, caller transaction, changed bytes or unavailable registry refuses before effects |
| Original registration | Register one immutable layout-migration attempt before native submission, using the existing installed recovery target and original request/evidence | Registry failure prevents submission; registration does not prove execution or settlement |
| Exclusion and source verification | Acquire the selected installation/catalog/configuration/security exclusions in their admitted common order; recheck current authority and complete source marker/archive/native/data basis under those exclusions | A stale plan, changed configuration generation, incompatible held context or unavailable source prevents steps; release only after confirmed termination |
| Ordered steps | Execute exact registered recipes in declared order in the same transaction; compare actual data/effects and prerequisites before advancing | Failure rolls back the entire route, including earlier successful steps; no intermediate ready marker or independently committed step receipt |
| Target verification and publication | Independently admit complete target native/callable/privilege/data/preservation basis; retain immutable route receipt and target archive/marker together under the selected finalizer | Missing sibling effects, protections or evidence prevents COMMIT; deferred guards remain active |
| Settlement | Observe original COMMIT, rollback or unresolved end using the qualified driver/outcome producer | Unknown end keeps original custody and readiness closed; no replacement attempt or automatic step retry |
| Committed verification | Fresh authorized observation proves original committed target/receipt/archive and current complete parity | Only complete correspondence returns migrated; confirmed commit with unavailable/drifted current observation returns committed_unverified |

Reuse `HostRecoveryRegistry` and its `installed` target kind. `LayoutMigrationAttempt` retains the original source installation/epoch/database/schema plus a distinct layoutMigrationAttemptId, originalRequest and procedure. The registry's immutable originalEvidence MUST retain that complete layout-migration-domain attempt/request/profile and source/target correspondence; structural extension fields alone do not register meaning. No new registry target kind, second identity authority, key-profile receipt interpretation or security resolver is introduced. A qualified transition records the target epoch in committed installation evidence while original recovery still addresses the original source attempt. Disposal, restart and restore retain the same original custody obligations.

The result carrier separates migrated/already_applied, refused with confirmed containment, rolled_back with original termination evidence, commit_unknown, recovery_required, and committed_unverified. Pending/unknown results carry no complete commit/readiness artifact. `committed_unverified` retains confirmed commit evidence and a recovery reference; a failed fresh observation cannot relabel committed work as rollback or authorize applying the route again. Read-only reconciliation follows the earlier original installation recovery classification, preserving confirmed outcomes even when inquiry is unavailable.

For an exact repeat, resolve the original complete request/route receipt and commit evidence under current authority/exclusion, then verify complete current target correspondence. Only this produces already_applied with the original commit and fresh verification. An unrelated matching target layout, a target marker without the original route receipt, a changed request or a later incompatible migration cannot be substituted for that repeat. The pure planner's no_steps is a separate metadata result and supplies none of this authority.

Example: a declared route has steps A (1.0.0→1.1.0) and B (1.1.0→1.2.0). If B fails after A writes, independent observation must show the original 1.0.0 state and preserved data after confirmed rollback. If COMMIT succeeds but its reply is lost, reconciliation queries the original attempt and may establish the complete committed 1.2.0 result; it never reruns A. If COMMIT is confirmed but current verification cannot inspect a required grant, the result is committed_unverified with the same commit evidence and runtime readiness stays closed.

This handoff selects route atomicity and outcome meaning for implementation. Exact migration-domain UMF storage/initializer, archive/marker/receipt bodies, finite resource realization, native source/target parity, driver outcome correlation and the security owner's exclusion/authorization composition remain LM-02–05 prerequisites. It does not adopt a stable release layout or qualify migration execution.

### Layout migration receipt body and settlement evidence

LM-02–05 use `LayoutMigrationReceiptBody` in the [administrative binding](bindings/truss-layout-migration-v0.1.proposal.d.ts).
The native retained body identifies the original installed attempt/request,
complete manifest and route, exact source/target, procedure/resource/transition
profiles and original source observation. Its nonempty ordered step evidence
retains each registered recipe/procedure, preconditions, actual effects,
validation and preservation. Final target observation, preservation and proposed
target installation/inventory belong to the same body. A same-version planner
`no_steps` result does not create an empty upgrade receipt.

The protected producer compares this body with the complete originally admitted
request and declared route: exact step count/order/identity, contiguous source
and target pins, complete recipe bytes/digests, profile correspondence and final
target all must agree. Step evidence cannot substitute a generic success flag
for the registered procedure's data/history/codec assertions. Duplicate,
missing, reordered or unrelated artifacts refuse publication. ExactArtifact
hashes are verified against retained bytes and original registered interpretation;
a caller-shaped body supplies neither authority nor successful effects.

The body is prepared **before COMMIT** and retained atomically with final target
archive/marker publication. It therefore contains no observed-commit claim.
The original driver's settlement observation and a fresh independent native
committed receipt/target observation are separate evidence. Only their qualified
correspondence constructs `LayoutMigrationCommit`. A visible row from the
writing transaction, a serialized committed label or the framework's migration
history is insufficient. Confirmed COMMIT followed by unavailable verification
still produces committed_unverified; the body never justifies resubmission.

Use a distinct layout-migration storage domain. The existing bootstrap archive
role enumeration has no layout-migration receipt role: do not smuggle these
bytes into its input/marker roles or change a deployed enumeration implicitly.
LM-02 must author the selected receipt/artifact home, exact uniqueness route,
parent/installation/attempt correspondence, immutable guards and initializer in
UMF, including any explicit archive extension/upgrade. Preserve complete original
artifact bytes under finite whole-route limits; any shared artifact deduplication
must retain full identity/byte equality and all protection dependencies. No
cleanup follows merely from a later installed version. Original recovery,
retained interpretation/history and supported repeat promises must release their
protections first under an admitted lifecycle procedure.

LM-T04/05 additionally require refusal for omitted/reordered/duplicate step
bodies, mismatched original request or recipe, and self-asserted COMMIT evidence.
Independent rollback observation must find no receipt or target publication from
the failed route. Lost acknowledgment must recover the same immutable body and
original commit without appending another migration. These are native schedule
obligations; declaration checks cannot qualify settlement or persistence.

It validates with zero errors and incomplete native interpretation; no portable key profile or installed mapping is inferred. The owner schema browser displays the receipt and downloads its original model byte-exactly. DELETE remains unconditionally unavailable; no caller cleanup flag,

### Publication drain within migration exclusion

When a selected upgrade/authority transition requires retiring old read contexts
or acknowledging revocation, LM-03 must consume the security-owned publication
lease/drain protocol as well as native writer exclusion. The security
[counterexample review](../../04-build/evidence/design-audit/security-publication-lease-loss-review.json)
shows that reader backend loss may release native locks while a live publisher
retains an old result. Do not equate terminated sessions, completed SQL or lock
availability with application final release. Unknown required publisher drain
prevents transition acknowledgment/readiness; exact fencing and unresolved
outcomes follow the shared security profile. This does not impose a new lease
implementation or imply that every compatible layout upgrade revokes all reads.

### Migration storage initialization and self-upgrade

The ledger initializer is part of the exact declared installation/upgrade
recipe, not an independent preparatory migration. Fresh installation composes
the selected receipt home, allocator, guards and privilege inventory into its
original dedicated bootstrap transaction, with no invented upgrade receipt for
an empty database. Initial absence of upgrade receipts is declared bootstrap
state; it does not prove that arbitrary future routes were applied.

For a first upgrade whose qualified source layout has no migration-receipt
home, register the original attempt in the host recovery registry before native
submission, verify that source under the common exclusions, and create the
selected target receipt storage/guards in the same transaction as the entire
route. Missing storage is legitimate only when the exact registered source
inventory declares it absent. The target finalizer inserts the complete original
receipt after all steps and target/preservation checks, then publishes the
corresponding target archive/marker atomically. A failed route rolls back the
new home and receipt with every other route effect. A lost COMMIT response
queries the original attempt and committed target; it does not initialize the
ledger again to discover whether the upgrade succeeded.

No `IF NOT EXISTS` or version-only repair adopts a preexisting unrecognized
home, allocator or trigger. Source and target inventories must account for
exact definitions, ownership/privileges, sequence settings and initializer
state. A source without admitted installation/epoch/attempt custody requires
its own explicitly registered source-transition protocol; this adjunct cannot
mint a trusted source identity retroactively. Receipt source-epoch FK insertion
requires the original retained registry correspondence, including its
incarnation, not today's epoch pointer.

| Initialization state | Permitted outcome |
| --- | --- |
| Fresh empty namespace | Original bootstrap recipe creates the declared empty migration subsystem; no applied-route result |
| Qualified old layout declaring no receipt subsystem | Registered first-upgrade recipe creates it inside the route transaction; readiness remains closed until full commit/target admission |
| Qualified layout with exact existing subsystem | Verify original definitions and retained complete receipts; ordinary upgrade appends one original route receipt |
| Missing/drifted subsystem where the source declares it present | Refuse before steps; do not silently recreate or erase original evidence |
| Unrecognized existing subsystem or source epoch | Refuse unsupported/integrity admission; caller cannot select a repair flag |

A later migration of the receipt subsystem must preserve every original
request/receipt/profile/identity byte and source correspondence needed by
recovery, repeats and retained history. Its registered conversion explicitly
accounts for old and new homes, full-byte correspondence, pending protections,
whole-route peak capacity and the resulting read/reconciliation profile. A
new storage encoding is not permission to rewrite an old receipt's original
meaning, mark unresolved attempts committed, reset its allocator or replace
original recovery custody. Keep the old evidence protected until the conversion
and lifecycle release are fully admitted. Current immutable DELETE/TRUNCATE
refusal supplies no cleanup path; a self-upgrade requiring one needs a separately
reviewed qualified procedure rather than disabling the guards during normal
application.

LM-02 now has an authored initializer placement/order. Exact registered native
producer/security/privilege/resource composition and generated whole-bundle
installation remain implementation outputs. The current adjunct is not a
stable published upgrade edge and neither bootstrap nor migration execution is
qualified by its rollback-only probe.

## Proposed namespace exclusion profile 0.1.0

`truss-bootstrap-namespace-lock/0.1.0` proposes one transaction-scoped PostgreSQL bigint advisory lock for fresh namespace installation. The installer owns an explicit READ COMMITTED administrative transaction. Admit trusted exact database/schema identity and register original attempt before acquiring the lock; acquire it before any installation savepoint or emptiness observation, retain it through commit/rollback, and never release it via a session-unlock call. Execute a separate fresh native namespace inventory statement after acquisition, then recheck immediately before DDL under the same lock. Do not combine lock wait and namespace observation in one statement whose snapshot may predate the winner’s commit. Held REPEATABLE READ/SERIALIZABLE snapshots are not silently substituted for this fresh-install profile.

Key bytes are ASCII `truss-bootstrap-namespace-lock/0.1.0` followed by one zero byte, then database identity UTF-8 byte length as unsigned 32-bit big-endian, those exact bytes, schema identity UTF-8 byte length in the same format, and those exact bytes. Identity admission rejects NUL, unpaired surrogates and out-of-profile byte bounds before encoding. Schema identity is the exact resolved quoted native name; no case folding, Unicode normalization, display-name substitution or textual connection identity. SHA-256 the complete preimage, take the first eight bytes in big-endian order, interpret as signed two’s-complement 64-bit integer, and bind its canonical decimal string as `$1::bigint` in `SELECT pg_catalog.pg_advisory_xact_lock($1::bigint)`. No host-number conversion or native hashtext shortcut is compatible. Hashing can occur in the browser-compatible host cryptographic implementation; no pgcrypto extension is required by this profile.

The digest is a serialization route, never identity or authorization. A collision only serializes unrelated namespaces; exact actual database/schema/marker/inventory checks still decide ownership and eligibility. All conforming installers for the same trusted target use this profile; mixed lock profiles cannot claim mutual exclusion without an explicit transition protocol. Nonparticipating host DDL remains outside this advisory exclusion and must fail/rollback honestly on native conflict. Native lock privilege, adapter connection affinity, timeout/cancellation/termination and fresh catalog visibility need independent evidence per selected target. These are proposed procedure rules, not current support or a layout release decision.

[Four byte vectors](bindings/truss-bootstrap-namespace-lock-v0.1.vectors.json) distinguish case and Unicode normalization forms. Python-published expected SHA-256/signed keys and an independent WebCrypto/BigInt probe establish byte mapping only. PostgreSQL documents transaction-level advisory locking and READ COMMITTED per-command snapshots in its [advisory lock functions](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS) and [transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html) references; actual Truss native tests remain separate.
