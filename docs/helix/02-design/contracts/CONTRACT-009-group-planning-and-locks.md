# Contract: Group planning and locks

## Owner decisions — 2026-10-07

ADR-005 is owner-selected: request-enabled groups require a complete immutable request receipt persisted atomically with effects, including all-no-op results. Exact equal identity/input replays; unequal full input conflicts; unknown commit uses original lookup/retry custody. Retired/expired request identity cannot silently reapply. Receipt storage and its native protocol must join the selected installer before replay readiness; request-free groups remain independent.

Precommit allocation uses the original graph transaction/sequence and returns only transaction-scoped pending identities. Committed identities are never reused; pending IDs are not durably published before confirmed outer commit. The independently committed allocation service is an optional stronger proposal, not a default dependency. Network hosts submit complete atomic batches and acknowledge only confirmed commit.


**Contract ID:** CONTRACT-009. **Type:** mutation protocol. **Version:** proposed `truss-group/0.1.0`. **Status:** draft; request-receipt persistence remains a decision gate.

## Purpose

Make ordered groups with aliases, key changes and owned deletion implementable without acquiring row locks in arbitrary operation order. Preserve atomicity, original operation ordering and the whole-group outcome of FR-51/54/55.

## Scope and Boundaries

CONTRACT-004 owns operation meanings and error kinds. CONTRACT-007 owns execution scope/savepoints. This contract governs planning, final-state validation and lock acquisition. It does not promise that arbitrary host SQL, third-party triggers or a caller's earlier lock acquisitions can never deadlock.

## Normative Surface

[Draft group facade](bindings/truss-group-capability-v0.1.d.ts) exposes inert exact-profile selection and applyInTransaction with explicit request none/present. Newly applied effects report pending even inside an outer engine transaction; only the outer executor's confirmed commit can produce an engine committed response. An admitted committed replay may report its original committed durability, while same-transaction replay stays pending. Native/transaction failures wrap the application result in CONTRACT-007 Outcome. group_failed carries canonical zero-based index plus exact profiled inner error; malformed envelopes/empty groups have invalid diagnostics without a fabricated operation index. Every application failure requires confirmed operation-local rollback and no surviving effects. Unknown cleanup remains an execution failure. Unavailable receipt/profile/observation cannot authorize reapplication or overwrite retained evidence. Request-none uses no receipt storage/namespace and does not depend on request replay readiness; ordinary group planning/invariants still apply. Existing handles recheck assembly admission, transaction identity/mode, current authority and complete pins on every call.

### Planning

The executor locks the catalog head once for the group and establishes the journal mode before writing graph data. An empty group and a forward/duplicate alias are invalid. Allocate identities for planned creates from `id_seq`; allocations may leave gaps after rollback. An alias refers to exactly one earlier planned create, with its declared type. It never becomes a caller-selected persistent id.

Build a complete plan against the selected catalog and a database observation of every existing object/edge affected. Include transitive owned-deletion descendants, all incident edges that must be removed/checked, composition roots and old/new business-key identities. Discovery performs no graph change. Plan input references, ownership structure and key observations MUST be revalidated after locks are acquired; stale observations yield `retry` before persisting any operation. Under a fixed snapshot a retry requires a new transaction.

Simulate operations in input order over the locked starting state, retaining an ordered result for every operation, including no-ops. Field/type/key/endpoint validation applies to each intermediate operation as required by its meaning. Cross-row minimum participation and aggregate checks apply to the group's **final simulated state**, so creating a parent, child and their relationship in one atomic group is possible. Their database checks must be transaction-deferred or the executor must order its physical persistence so that the valid final state is installed atomically. No intermediate simulated state is published as a committed graph.

An invalid group returns `group_failed` with its zero-based operation index and inner CONTRACT-004 error. An immediate failure names its own operation; a final invariant violation names the last operation affecting that invariant, with every violation path retained. No application-visible graph, key, marker, journal or receipt effect survives that failure. Foreign-key visibility and role checks are evaluated under the actual caller context, not an elevated simulated authority.

### Request-free dispatch and outcome procedure

Select the request branch from the immutable admitted original envelope before namespace/receipt discovery. For state none, resolve the qualified ordinary group profile and current graph/catalog/acting-role/executor obligations, then enter the existing complete discovery, ordered simulation, lock revalidation, persistence and finalization procedure. Do not synthesize a request identity from operation bytes, origin, transaction ID or operation ordinal. No request namespace guard, receipt lookup, receipt capacity reservation, replay digest or retention clock is admitted solely for this branch. Original operation/touch custody, ordinary policy guards, group result capacity and journal/history obligations remain required. An installed unknown or incompatible object still follows bootstrap/policy admission; branch independence does not authorize ignoring it.

Keep the complete ordered result in the original operation's bounded pending result custody. Return applied/pending only after confirmed operation-local success and containment of all required work. Actual outer commit or rollback settles that original result through CONTRACT-007; no receipt insertion is needed to establish an ordinary confirmed transaction outcome. Allocation durability and unresolved native completion follow their selected existing procedures. A request-free group cannot return replayed, request_conflict or receipt_expired merely because another call has equal input; receipt-specific unavailable reasons require an actual selected receipt dependency and therefore do not describe this branch.

The proposed facade now has a request-none overload returning RequestFreeGroupApplicationResult; a caller whose request branch remains a union retains the full result union. Four negative consumer cases reject replayed success, receipt-expired/receipt unavailable and request-conflict failure for the none branch. [Strict declaration receipt](../../04-build/evidence/design-audit/request-free-group-typecheck.json) records only this static check; actual native dispatch and recovery remain required.

Every later invocation with request none is a new mutation evaluated against then-current admitted state. Equal input is not an idempotency promise: it may create another admissible record, fail an existing-key/expected-version rule, or produce an actual no-op according to operation meaning. Following lost execution/commit acknowledgment, preserve original recovery custody and report the unresolved outcome; automatically invoking the same request-free input again could duplicate committed effects. Do not convert native uncertainty into a replay result or prove absence from a missing receipt that was never required. The request-present branch retains the independent replay decision order below.

### Protected creation-alias allocation

The proposed row-home profile realizes planning aliases through AP01–AP06 below. It consumes the existing group command meanings and CONTRACT-001 shared `id_seq`; it does not add an alternative identifier service or change the Weft binding. Every create, including an unnamed create, has its original zero-based command ordinal. An alias is an additional invocation-local reference to that create; it is not the allocator key. An edge alias retains its independent declared relationship identity, not a property-owner type substituted for that identity.

| Phase | Original inputs and protected action | Required invariant / failure boundary |
| --- | --- | --- |
| AP01 admit original commands | Under the admitted catalog/head and applicable capacity admission, retain the complete original input, command order and family/context. Enumerate creates and every alias reference without allocating or mutating graph rows. | Validate alias uniqueness, earlier-create references, kind and declared catalog identity. An unreferenced named create remains an allocation obligation; a create without an alias still appears by command ordinal. Invalid input refuses without canonical effects. |
| AP02 reserve accounting | Compute the complete create count and original correspondence-carrier byte/work requirements with checked arithmetic. Reserve the selected operation/transaction custody capacity before creating its records. | Charge create slots, alias bytes, original command/definition occurrences and eventual native correspondence copies to existing whole-group and custody budgets. No extra unbounded alias map or independent allowance; declared ceilings are aggregate and simultaneous memory limits still apply. |
| AP03 allocate native identities | A protected canonical-writer path calls the admitted installation's actual shared sequence once per original create, in command order. Preserve each exact returned bigint without host-number conversion. | Actual sequence identity/ownership/noncycling configuration and positive native range are installer prerequisites. A returned invalid or already occupied identity refuses the attempt; never reset, decrement, recycle, skip until success or adopt an existing owner. Allocations can leave gaps on failure. |
| AP04 bind correspondence | Retain immutable original installation, native transaction/operation address, create command ordinal, original create/alias definition, owner kind, declared type/relationship discriminator and exact allocated owner ID. | Exactly one allocation per create and one create per allocated identity within the invocation, including unnamed creates. Resolve each later alias to its exact earlier create. Preserve original submitted locators unchanged; this correspondence is separate protected effect evidence. |
| AP05 revalidate locked plan | Use the allocated identities in the complete simulated plan and acquire/recheck the full CONTRACT-009 hierarchy. Recheck original catalog, existing owner versions, owner union, roots, old/new keys and planned scope before canonical insertion. | Discovery remains graph-read-only. New IDs do not authorize hidden reads or reduce endpoint/key checks. Earlier-guard discovery or stale state returns the established retry/rollback outcome; no automatic callback or group replay. |
| AP06 apply and finalize | Insert validated objects/edges and complete effects through the admitted producers; compare original planned scopes and allocation correspondence against actual effects in both directions before readiness/sealing/application completion. | Creation followed by deletion retains both ordered outcomes and complete removed scopes; empty final graph is not an empty effect inventory. Missing, duplicated, substituted or unplanned correspondence refuses atomically. Never overwrite a finalized earlier operation to fit later alias use. |

Allocation custody is pending native transaction evidence, independently of optional request replay. Request-none needs no replay store or namespace. A request-present committed replay returns admitted original outcomes without allocating again; unresolved original execution reconciles through CONTRACT-007 rather than starting AP03 again. A genuine new invocation may reuse alias text, but has its own native address and allocation obligations. Operation-local savepoint rollback removes that attempt's pending correspondence and canonical effects while sequence consumption remains nontransactional; whole-transaction rollback and uncertain acknowledgment preserve their existing distinct recovery outcomes.

PostgreSQL 17 documents atomic concurrent `nextval`, bigint results, privilege requirements and non-reclamation after transaction abort in [Sequence Manipulation Functions](https://www.postgresql.org/docs/17/functions-sequence.html). It also qualifies sequence-state persistence after a crash before commit. Therefore AP03 supplies no restart/failover nonreuse proof for externally observed pending allocations: US-007-AC4’s broader durability requirement still needs its selected durable allocator/recovery profile and independent crash corpus. Do not promote live-process rollback observations into that claim, or discard the broader requirement to make the sequence candidate pass.

#### Pending-allocation crash durability decision

The [conditional service design](durable-allocation-service.proposal.md) now specifies reserve/observe custody, commit-before-disclosure, graph/service ownership, continuity and DA-01–07 schedules for the stronger alternative. Its existence does not select that alternative; owner interpretation remains pending.

The upstream requirement is PRD FR-15: every object/edge identifier comes from one sequence and is never reused. US-007-AC4 explicitly tests concurrent creates and nonreuse after deletion; it does not independently define whether an uncommitted number disclosed before a crash is a permanent identity. PostgreSQL 17’s documented precommit sequence-state uncertainty makes that distinction a real requirement decision, not a codec limitation. Preserve the unconditional FR-15 text until the owner resolves this interpretation; do not silently narrow it to committed graph rows. AP03’s ordinary connection-affine sequence path alone cannot claim the stronger interpretation.

If pending disclosed IDs must survive crashes, propose an explicitly registered host allocation service using the same installation sequence. Before IDs enter a public pending result or native graph producer, the service commits their allocation on its own admitted connection and records the complete original allocation-attempt identity, create ordinals and exact returned IDs in protected durable custody. This service never commits or rolls back the caller’s graph transaction. Its connection must not wait for catalog/head/capacity/policy/owner guards held by that graph transaction; all required authorization/installation admission must be available without reacquiring those guards. An implementation needing that inversion refuses the composition. The service is a separately declared host capability, never an implicit pooled connection opened by core.

The durable path needs an exact synchronous durability/failover/restoration profile and acknowledgment/reconciliation procedure. Lost allocation commit acknowledgment must recover the original allocation attempt before use, not request another block and infer that the first failed. Durable reservation can remain consumed after caller rollback; cleanup may delete original custody only after its recovery obligations are settled, and must never recycle its numbers. Resource admission must bound create count, original custody and retained abandoned reservations before service work. A qualified sequence commit is necessary but does not alone establish arbitrary backup restoration or asynchronous failover nonreuse. Admission also requires deployment continuity; restoring an earlier allocator state cannot silently resume the same installation identity.

If the owner selects committed-ID plus live-process pending-ID scope instead, reconcile that meaning explicitly into FR-15, CONTRACT-001/007/009 and STP-007 before adopting the ordinary sequence profile. Keep committed deletion nonreuse, shared object/edge allocation, protected sequence configuration and restart/failover checks. These are two explicit design alternatives awaiting requirement interpretation; neither is currently accepted. No UMF or Weft interface change is needed.

The exact native allocator/registry routines, original sequence observation, privileges and guarded correspondence encoding remain installer outputs. AP01–AP06 specify their required ordering and complete contents, not native qualification. STP-007 A01–A08 supplies independent schedules; tests must additionally observe competing allocators, original create ordinals without aliases and invalid/occupied sequence output without granting public sequence control.

### Lock hierarchy

All Truss write implementations MUST use the same hierarchy. Ordered sets are locked completely at a level before moving to the next; a discovered earlier-level lock not already held causes rollback of the attempt and `retry`, never acquisition out of order.

The table incorporates current-authority and namespace lifecycle refinements below. Levels describe the selected complete native profile, not readiness from declarations alone. A profile requiring an unavailable guard cannot silently omit it; request-free groups omit namespace/request levels only. Exact native identity/mode/procedure and unavoidable writer coverage remain qualification prerequisites.

| Level | Lock set/order | Rule |
| --- | --- | --- |
| 1 | Original catalog/configuration head | Shared for participating writes; exclusive for catalog/configuration/key-profile transitions; retain through native transaction termination |
| 2 | Complete current-authority policy guard set | Selected current-authority protocol; stable complete owner order, fresh actual-caller checks after guard acquisition; no hidden substitute for explicit read-only adoption |
| 3 | Trusted namespace lifecycle guards, when request-bearing | Shared for request admission/replay; exclusive for namespace administration; complete native namespace identity and fresh generation/state admission |
| 4 | Request identity, when present | Selected full trusted namespace/request serialization; digest routing alone cannot establish identity or authority |
| 5 | Business-key identities and qualified bucket guards | Complete old/new key sets in selected unambiguous byte order before roots; selected advisory or protected native bucket protocol, never assumed interchangeable |
| 6 | Composition roots | Root object rows ascending `(type_id,id)`; strongest needed mode acquired first |
| 7 | Other object rows | Ascending `(type_id,id)`, excluding already locked roots |
| 8 | Existing edge rows | Ascending edge id |
| 9 | Derived key/limit/tombstone/receipt effects | Stable typed identity order in the planned writes; cannot discover/acquire a missing earlier guard during persistence |

For the proposed row-home reference capacity profile, a protected installation-scoped touch-capacity ledger is a subordinate head-level guard: acquire the original head first, then the complete touch-capacity guard before level 2 policy guards and every lower key/owner/effect lock. This applies to request-free row-home writes and cleanup as well; it is not the optional request namespace level. Retain its native transaction exclusion through actual termination. The reference candidate serializes capacity-consuming transactions at this ledger and must measure that cost; it makes no independent-writer throughput claim. A supplied transaction already holding an incompatible lower guard cannot acquire the ledger late; refuse the combination under the selected adoption protocol. Native touch observers must verify an existing original capacity reservation, never discover/acquire this earlier guard from child DML. Cleanup and administration use the same head-then-capacity order and cannot hold a lower policy/owner guard while waiting for capacity. Exact ledger row identity/mode/routine/grant/wait/timeout realization and cross-connection qualification remain required.

Typed lock-identity encoding MUST be unambiguous and independent of presentation names. Under an explicitly selected advisory profile, hash collisions may serialize unrelated work but must not allow omitted locking; exact PostgreSQL advisory conversion is versioned and checked by its native corpus. It does not implement namespace custody, complete-key comparison or bucket snapshot coherence. External host writes that bypass Truss must honor the entire selected hierarchy to participate in this guarantee.

For CONTRACT-001's large-key bucket candidate, the business-key level includes the complete qualified digest-bucket guard set and its native generation admission, before object/root locks. Locking a digest is not current snapshot evidence. Full-key uniqueness/reservation observations require that profile's fresh-observation/write-conflict rule; a stale fixed snapshot retries its entire transaction without effects. Plan old and new key buckets together for re-key/delete/group operations. Same digest collisions serialize but differing complete key bytes remain separate identities. A native trigger that cannot preplan this lock set is not qualified by the engine hierarchy alone.

CONTRACT-005 owns the selected current-authority procedure at the policy level. Guarded writes, catalog/policy administration and replay adopt the same reviewed ordering. Complete private owner discovery and fresh admission obey that contract; earlier owner discovery after a lower lock requires containment/restart. Explicit read-only snapshots need the separately qualified authority-adoption protocol rather than a forbidden row guard or hidden host commit. Policy-only administration may omit the head only when it never later acquires one; namespace-only administration may omit earlier guards only when it never later acquires them. Omission does not authorize inversion. Cross-connection authority services must not reacquire a head blocked by their own data caller.

Composition roots are locked before discovering a stable subtree for a destructive operation. Every conforming edge/ownership change locks its affected endpoint roots, so it cannot expand a locked subtree unnoticed. Discovery may find roots before acquisition; after acquisition the executor re-enumerates the closure and verifies ownership/cycles. Changes of ownership/root lock both prior and new roots and obey the same hierarchy. Root cycles or unestablished ownership are invalid; they never lead to unbounded recursion.

Rows to be deleted use FOR UPDATE; other rows use FOR NO KEY UPDATE unless a stronger lock is necessary. A root later deleted is locked in the stronger mode initially. Identities of planned new rows are reserved before planning but their rows are inserted only after validation. Update/delete guards include the observed version, preventing plan application against a changed state.

All ordinary single-operation writes use this hierarchy as one-operation plans. Catalog acceptance already excludes concurrent writes through its head lock. This avoids a second ordering regime in which groups and single writes acquire the same rows differently.

### Mutation configuration admission

Configuration generation is execution evidence scoped to its source epoch/installation, not a rewritten caller semantic input or authority token. It cannot reset or wrap within that scope. The administrative profile must specify native range/exhaustion refusal and preserve prior generations; restore/replacement uses an explicit new epoch rather than recycling an old generation. Administrative transitions acquire the strongest required head mode before lower-level locks; an operation that already acquired ordinary mutation/business locks cannot upgrade itself into a configuration transition.

The draft configuration profile serializes `key_reuse` changes through the existing catalog-head exclusion: participating mutation transactions acquire the required share head lock before admitting the exact configuration generation and value; administrative changes acquire exclusive head ownership, validate authority, and atomically update the value and monotonic generation. No business/record lock may precede this admission. A locked observation that differs from the operation's selected generation refuses/retries before effects; a fixed old snapshot cannot substitute its old setting for the current admitted generation. Exact native lock/observation and generation storage procedures remain qualification deliverables.

Once admitted, a mutation transaction uses that configuration unchanged through all operations, reservations and journal production. An adopted transaction can delay configuration changes until its host ends the transaction; Truss cannot secretly release its exclusion by committing. An engine-owned multi-batch import releases transaction exclusion at each commit but retains its selected configuration generation across the attempt. Before the next batch it readmits that generation under the head lock; a change stops the attempt before submitting that batch, preserves earlier confirmed commits and reports remaining indices unprocessed. Restart under a new policy is a new explicitly admitted attempt, not continuation of the old attempt with mixed reuse rules. Retain exact admitted configuration/generation in attempt evidence and its report profile provenance.

`journal_mode` changes additionally change the qualified writer/trigger installation. Updating the setting alone cannot enable another mode: require an exclusive administrative transition that reconciles the installed producer/guard inventory, preserves exactly one journal writer, and refreshes qualification before graph writes resume. Failed or unknown transition cannot expose a partially installed mode as available. CONTRACT-011 owns the installation evidence; choosing native transition DDL is a build-design gate. Uncoordinated direct setting edits invalidate the claimed configuration profile.

Deadlocks caused by unconstrained host SQL or hidden database locks return `retry`; no deadlock is swallowed or partially committed. US-040-AC3's opposed-order two-group case MUST show both groups complete without a PostgreSQL deadlock when they start in otherwise empty caller transactions and all code honors this hierarchy. Broader freedom from every database deadlock is not claimed.

### Persistence and journal

The executor persists the ordered simulated effects within one operation/group savepoint and one transaction. Each actual change retains its operation's version progression; unrelated updates are not merged into one undocumented version. No-op operations preserve their versions and write no property-change rows. Whole-group final invariant checks run before releasing the savepoint. Journal ownership remains exactly one of engine or trigger, with no duplicate writer.

Request replay MUST preserve every ordered original result, including mixed no-op/changed operations. The existing journal-only design cannot infer no-op results solely from property-change rows. ADR-005 selects durable complete receipt storage; until its complete native storage/protocol is incorporated and qualified in the installed layout, idempotent replay is gated; a request-enabled profile MUST NOT claim full FR-54 conformance from the request-index spike alone. Request hash derivation, scope, authorization and retention are part of that gate. Atomic groups without request IDs remain independent of it.

### Required replay decision order

Current mutation configuration admission governs new effects, not reinterpretation of a retained committed result. After current authorization and compatible receipt admission, changing `key_reuse` cannot turn an identical request into a new create, replace its canonical input, or invalidate its original outcome merely because the old policy differs. Retain original execution configuration separately as receipt provenance; verify the historical profile needed to interpret it. Missing provenance needed for interpretation yields unavailable, never reapplication. For an absent receipt, admit the current selected configuration before planning new effects. Pure replay still requires current disclosure/compatibility/liveness checks but does not run new-writer installation merely to reconstruct the saved result.

The [draft group-result binding](bindings/truss-group-result-v0.1.d.ts) proposes one ordered semantic result per input operation, exact generated identities/versions, resolved aliases, complete deletion-effect inventory and event references. An unchanged update retains its original observed version and has no emitted events. A replay returns those immutable entries even after later writes/deletion; it never rebuilds them from current records. Count/kind/order correspondence, alias uniqueness and complete affected-event inventories require runtime validation and independent expected vectors.

GroupResponse places durability/disposition outside the stored semantic result. First adopted execution is pending, confirmed engine execution is committed, and replay of a committed receipt reports committed. Uncertain commit is an execution failure under CONTRACT-007 rather than a fabricated successful GroupResponse. The draft now carries exact profile identity/version/digest pins. Changed results require nonempty event references; unchanged results require an empty event list. This is a proposed complete-result surface, not receipt persistence approval or a claim that current journal rows contain it.

An exact request repeated inside its original still-open native transaction returns the original semantic result with replayed/pending and same_transaction observation evidence. It performs no second graph/key/journal/source effect. Verify original receipt/input equality, current authorization and the executor's exact native transaction identity through the selected observation profile; connection identity or a caller transaction label alone cannot prove this basis. Both responses/effects remain pending and vanish together on host rollback. Another transaction must not read this uncommitted result through an assembly cache; ordinary request exclusion waits/reconciles under the native profile. Only an independently admitted committed-receipt observation may produce replayed/committed. Missing/ambiguous basis is unavailable/unknown under the execution protocol, never a fresh application. Replay observation evidence is fresh response context and is not written into the immutable semantic result or canonical input. This rule also applies to a group invoked inside a surrounding engine scope before its outer commit.

This order applies to ADR-005's selected durable receipt home. Its physical/native candidate still requires installed profile admission; the old journal-only persistence alternative is superseded. Authenticate the host context, establish the authorized request namespace, validate the request envelope and compute its canonical semantic identity before consulting retained results. Take the catalog and request locks in the hierarchy above. Authorize lookup and replay under the current caller policy before disclosing whether a receipt exists or its result. Receipt existence never grants access.

| Retained identity state | Required outcome before business planning |
| --- | --- |
| Retained, compatible, same canonical input, replay authorized | Return the complete immutable original semantic result; do not revalidate original expected versions, current endpoint existence or current property constraints as if this were a new mutation |
| Retained, different canonical input, lookup authorized | `request_conflict`; no graph effects or replacement of the original receipt |
| Retained, incompatible receipt/result profile | Explicit unsupported/profile failure; never treat incompatibility as absence and apply again |
| Lookup or replay unauthorized | Refuse without receipt contents or cross-scope existence disclosure; do not apply a replacement mutation |
| Absent in a qualified observable snapshot | Plan and validate a new group against the current locked catalog; persist its complete result atomically with effects |
| Winner potentially committed but invisible to this fixed snapshot | Require a new host transaction or report retry; invisibility is not proof of absence |
| Expired or administratively removed | Follow the published replay-window/epoch policy; neither original-result recovery nor safe reapplication is inferred from missing evidence |

The canonical request includes the caller's explicitly selected catalog/layout/profile pins. A dynamically observed head revision is execution context, not a new caller input on each retry. Record the actual execution pins in the receipt. A retry of the same caller input after catalog advancement can replay its retained result when receipt compatibility and current authorization permit; rewriting its digest using today's head would incorrectly turn it into a conflicting new request. An explicit caller change to an effect-relevant pin remains a conflict. A new request must satisfy current compatibility and stale-catalog checks before effects.

Origin treatment must be selected in the digest profile: any excluded retry metadata cannot rewrite the original audited origin, and an asserted actor cannot supply authenticated scope. Until that profile is published, no request hash or scope format is advertised as interoperable. A replay result is the original operation result, not a fresh read of records that may have changed or been deleted; its durability context follows CONTRACT-007.

## Precedence and Compatibility

### Proposed canonical-byte profile

The [draft group-input binding](bindings/truss-group-input-v0.1.d.ts) enumerates six operation families, stored versus alias references, exact authored values, expected versions, caller profile pins and current versus explicit catalog selection. Request identity is separate from semantic input; its authorized namespace must be resolved by trusted host policy. Origin follows ADR-005's inclusion proposal. These are review shapes, not complete JSON/runtime semantics or activation of the receipt proposal.

Runtime validation rejects empty groups, duplicate/forward/wrong-kind aliases, duplicate value names, set/unset overlap, malformed exact identities and mismatched model/definition pins. Property names resolve only through the qualified owning definition/mapping profile; unknown values follow retention rules. Options for composition lifecycle, metadata updates and any additional effect-relevant form must be represented in a reviewed profile before support, not silently defaulted outside the digest. This draft cannot exclude required owned-deletion/group behavior or replace the full result schema. No compiler/parser is introduced by these input shapes.

The candidate binding now includes explicit rootless/owned selection, root changes, edge endpoint changes and order-key changes. These are proposed extensions of the abstract operation inputs and require CONTRACT-004/profile reconciliation before publication. Root selection is not permission to bypass composition semantics: validate the final ownership graph, root identity/cycles and declared lifecycle under the catalog, lock old/new roots and affected endpoints, and journal complete metadata changes under ADR-007. Absent metadata-change members mean unchanged; explicit rootless/null order states mean an actual selected change, not omission. Retargeting rechecks relationship endpoint constraints, authorization and multiplicity/key/ownership consequences. Any unsupported selected form refuses before effects; the full design scope remains required.

Candidate `truss-canonical/0.1.0` encodes validated semantic-input trees containing null, booleans, Unicode scalar strings, arrays and string-keyed objects. Host JSON numbers are forbidden; exact integer/decimal values and version/id metadata use their declared text carriers. This does not equate numeric text with a string-valued property: tagged value family remains part of the semantic input. Parse duplicate object members before tree construction and refuse them. Reject unpaired surrogates and selected PostgreSQL-bound NUL content under CONTRACT-010; no normalization is implicit.

Encode null/boolean as their lowercase JSON tokens. Encode strings with double quotes, escaping quote and backslash as backslash-quote/backslash-backslash; encode every U+0000–U+001F control as lowercase six-character `\u00hh`, without alternate short escapes. Other scalar characters are direct UTF-8; slash is unescaped. Arrays retain order. Object members sort by exact UTF-8 key bytes, then encode key, colon and value with comma separators and no whitespace. Empty arrays/objects remain distinct; omitted members differ from explicit null. Authored string content is never trimmed or case-folded.

The digest preimage is the ASCII profile version plus LF, the exact semantic domain version plus LF, then canonical tree bytes. Request and catalog-acceptance domains differ, so equal tree bytes cannot substitute across protocols. Hash SHA-256 and render lowercase hexadecimal. Verify from trusted validated input, never accept caller hash as proof. Resource limits apply before and during encoding; no partially encoded digest is returned on failure.

This proposal resolves deterministic byte spelling only. Closed request/acceptance input schema proposals and explicit compared-origin handling are now authored in CONTRACT-003/004; exact profile adoption, complete effect-relevant option/default correspondence, original persisted-input producers and owner review remain gates. Do not hash arbitrary host objects, prototype/accessor behavior or fields unknown to the semantic input profile and call that interoperability. A profile update changes digest identity explicitly; stored old fingerprints are not reinterpreted.

[Independent byte/hash vectors](bindings/canonical-byte-v0.1.vectors.json) enumerate manually specified canonical tokens, UTF-8 bytes and SHA-256 preimages for null, empty containers, sorted members, controls and direct Unicode. They now use the proposed binding's `truss-group-input/0.1.0` domain, replacing superseded `truss-request-input/0.1.0`; no persisted deployed fingerprint is migrated by this draft correction. [Complete wire-shape vectors](bindings/canonical-input-v0.1.vectors.json) add native-ingress acceptance and rootless group trees, changed asserted origin and an intentionally wrong-domain comparison with identical bytes. Fixture profiles/documents do not establish semantic validity. Digests were computed with Python hashlib from independently authored exact tokens; no production canonicalizer was used. Reproducible byte/digest checks are in `04-build/evidence/design-audit/check-canonical-vectors.py`. Cross-language encoders, duplicate-member/refusal cases, complete operation/options coverage and owner review remain qualification outputs; these fixtures cannot close FR-54 or catalog replay.

ADR-002 locking and storage invariants govern. This contract refines CONTRACT-004's group-wide lock order and final-state validation; it preserves the accepted whole-group requirements. New lock profiles require refreshed multi-client evidence and compatible participants; a writer cannot join a deployment using a different hierarchy silently. Planned unsupported dynamic forms refuse with a named diagnostic, while the full required alias/owned-deletion forms remain implementation/test deliverables.

## Error Semantics

Invalid group shape/ownership is `group_failed` with inner `invalid`; stale discovery or deadlock is `retry`; property/endpoint/key/version errors remain CONTRACT-004 errors. A failed savepoint cleanup is `transaction_unusable` under CONTRACT-007. Only the host may restart an adopted transaction. A mismatched lock/profile version refuses before graph mutation.

## Examples

Group A updates objects 20 then 10, while group B updates 10 then 20. Both lock the relevant roots and object set in canonical order before applying either input sequence; their returned results still follow their own input order. A group creates Order alias `o`, creates Line alias `l`, then connects `o` to `l`; final participation validation sees the edge.
