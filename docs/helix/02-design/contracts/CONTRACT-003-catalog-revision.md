# Contract: Catalog revision

**Contract ID**: CONTRACT-003
**Type**: library
**Version**: 0.1 (draft)
**Status**: draft
**Related**: ADR-002 D1, D8, D9, D10, D12, CONTRACT-001, CONTRACT-002, SPIKE-002 (`loader/catalog.ts`, `loader/revise.ts`)

## Purpose

Defines how a set of UMF documents becomes an accepted catalog revision: the order documents are imported in, how catalog rows are derived, how ids stay stable, what happens to an entity type that a relationship names but no document defines, and the report every acceptance produces. Any implementation that accepts a revision does so the same way, so the resulting tables are the same.

## Profile selection and baseline interpretation

This draft contains the legacy module/element layout behavior and proposed document-qualified replacement profiles. The selected, version-pinned layout/identity/lifecycle binding determines which identity rule is admissible; do not combine a candidate's matching rule with legacy constraints or advertise candidate capability from source capture. ADR-004 and the allocation/finalization candidates remain unaccepted. Legacy module/element duplicate handling and provisional lookup below describe the baseline only. Under a future admitted document-qualified profile, resolve exact owner/category identities through its complete source correspondence, then apply the matching/allocation/finalization sections; retired reintroduction remains decision-gated.

Two definitions under different document owners are distinct lineages in the proposed profile, even if their names or payload bytes match. Exact-repeat acceptance of the same full input is the separate retained-report rule; it does not authorize duplicate claims inside a new candidate set. Baseline identical-definition coalescing cannot be used to merge distinct document-qualified owners. Unknown endpoint resolution must use the selected upstream and layout identity rules, never silently fall back to legacy module/name matching when document-qualified resolution is unavailable.

CONTRACT-007 governs transaction adoption, timeout restoration, original containment and durability throughout the steps below. A lock timeout does not by itself authorize rolling back a supplied host transaction or immediately retrying an unresolved attempt. Original transaction/candidate recovery precedes any new attempt under the selected executor profile.

## Scope and Boundaries

- In scope: the import set, validation, ordering, derivation phases, unknown entity types, identity stability, tightened-rule checks, atomic acceptance, the acceptance and enforcement report.
- Out of scope: UMF's own semantics (truss consumes UMF and never defines it; ADR-002 D12), conversion of other UMF dialects into core documents, the tables themselves (CONTRACT-001), the mutation operations (CONTRACT-004).
- Owning project: truss.
- UMF assumption: documents are UMF core 0.7.0 (records, fields, named keys, and `module.relationships` per UMF's draft CONTRACT-041), the version SPIKE-002 exercised. Each document's exact UMF version is recorded; the supported subset is declared in the report.

**Input: an import set**

| Element | Rules |
|---------|-------|
| `documents` | One or more UMF documents as received bytes. Each has an identity `doc_id` and an owner-issued `doc_revision`. |
| `binding` | Optional truss binding vocabulary (storage home, indexes, statistics). |
| `origin` | The caller's `actor` and `reason`, and any `x-*` keys, as for a journal row (CONTRACT-002). The implementation adds `db_role` from the database and ignores any `db_role` the caller sends. |
| `policy.unknown_endpoint` | What to do with a relationship endpoint that no document in the set and no earlier revision defines: `reject` (default), `provisional` or `skip`. |

**Acceptance steps.** An implementation MUST perform these in order. Acceptance is all-or-nothing: if any step rejects, nothing is written and the report says why.

0. **Lock.** Begin a transaction and take the catalog lock: `SELECT rev FROM schema_head WHERE id = 1 FOR UPDATE` (CONTRACT-001). This waits for the writers holding the share lock and blocks new ones while it is held, so no write runs between the checks below and the revision's insert. Set a `lock_timeout` first; on timeout the acceptance rolls back and MAY be retried later. The row read is the head; the new revision is head + 1. Steps 1 and 2 MAY run before the lock; everything from step 3 runs under it.
1. **Verify.** Compute `content_sha256` of each document's bytes, parse it exactly, and validate it with the pinned UMF validator. A document that fails validation rejects the set. An implementation that is not UMF's reference MUST accept and reject the same documents as the validator, with the same diagnostics (severity, code and path), which the corpus's `umf` cases test (CONTRACT-004); a document using a feature the implementation does not support is rejected and reported, never accepted silently.
2. **Order.** Sort the documents so that a document comes after every document it declares as a dependency or references by element. Collapse dependency cycles into strongly connected components, then topologically order the component graph dependency-first. Among ready components, compare their member `doc_id` vectors (each sorted by exact UTF-8 byte order) lexicographically. Members of each component take consecutive positions in that same byte order. This ordering rule does not authorize references or cycles that the pinned upstream validity profile rejects. External dependency syntax, valid cycle policy and revision pins remain upstream-gated; a local reference never searches another document. The resulting `ord` of each document is recorded in `schema_doc` and is deterministic for a given set.
3. **Derive in phases.** Over the whole sorted set, derive in this fixed order: all types, then all properties, then all keys, then all relationships and their endpoints. Because every type exists before any relationship is derived, an endpoint defined in a later document of the set is not unknown. Derivation follows SPIKE-002 and ADR-002 D5: a UMF record becomes a type; a field becomes a property; a record-valued field whose record has identity becomes a composition relationship to a child object with owned lifecycle, carrying `root_id` and `root_type`; a record-valued field whose record has no identity is stored as a structured value inside the owner's `props`, typed through the catalog (ADR-002 D5, provisional on V3); a named key becomes a `key_def`; an authored relationship becomes a `rel_def` with one endpoint triple per source and target pair.
4. **Resolve unknown endpoints** by `policy.unknown_endpoint` (below).
5. **Keep identity** under the selected layout/profile (below). In the legacy baseline, two documents in one set that define the same `(module, element)` reject the set as `duplicate_definition`, unless their bytes are identical; each catalog row records its defining document (`doc_ord`). Proposed document-qualified acceptance instead requires ADR-004 source ownership and the complete matching/allocation/finalization profiles below. A profile must preserve original IDs and retained high-water evidence; current visible rows alone cannot establish safe allocation (CONTRACT-001).
6. **Plan transforms and check candidate state.** A property type/cardinality change requires a declared qualified total transform; absence rejects before persistence. Evaluate each required transform over every affected stored value under the head lock, retaining the exact candidate result or its failure. Validate all tightened/added rules against the candidate state: transformed values where declared, unchanged values elsewhere, and final derived keys/relationship invariants. Report every available violation and transform failure, not only the first. A failed or incomplete scan rejects. Evaluation MUST NOT publish graph or catalog changes. Trusted transform registration, exact carriers and resource/report bounds require a versioned profile; input document content cannot load executable code.
7. **Persist** in the same transaction, still under the lock, unless the verified exact-repeat rule below applies. The following lists required effects, not permission to construct an incomplete parent report or expose separate persistence phases: insert `schema_rev` at head + 1 with its `origin` and the `schema_doc` rows; insert catalog rows, with new catalog ids and key numbers allocated as the current maximum plus 1 (CONTRACT-001); update in place only the rows this contract permits, recording the before and after in `schema_change`; persist the exact transformed candidate values already checked at step 6 and write `transform` journal rows for each actual changed value; write `rebind` journal rows (CONTRACT-002); store the complete acceptance report in `schema_rev.report`, including declared pending index work, using the selected immutable-report ordering below; and update `schema_head` to the new revision. A failure while constructing or storing the report rejects and rolls back the entire acceptance. Accepting a type adds catalog rows only: no table, partition, column or index is created. Because the acceptance holds the lock, the revision number it inserts cannot conflict with another acceptance.
8. **Return acceptance** only according to CONTRACT-007 durability: engine-owned results follow successful commit; caller-owned results remain pending until the host commits. The report stored at step 7 is an immutable statement of acceptance, not a mutable index-job status row.
9. **Build declared indexes separately** after confirmed commit. Index work does not run inside acceptance and cannot change its accepted result. The acceptance report lists the declared jobs as pending at acceptance time; separate versioned readiness receipts record completion or failure. For an adopted transaction, the host must explicitly confirm commit before dispatching jobs; savepoint release is insufficient. The job/receipt schema and administrative execution API remain design gates.

### Proposed immutable report persistence order

#### Genesis is installation evidence

Baseline storage-layout.sql seeds schema_rev revision 0 with report `{}`. This is the empty installed catalog, not acceptance of an empty UMF input set. acceptance-report-v0.1 requires a positive revision and complete acceptance/source/authority inventories; `{}` cannot qualify that wire. #### Protected native persistence boundary

The reference candidate encapsulates parent insertion, dependent persistence, complete actual parity and head publication within one qualified native function invocation, submitted as one statement on the original admitted transaction. Core/UMF validation and trusted transform evaluation occur beforehand and produce retained bounded candidates; the function cannot invoke document-selected code, replay host callbacks or become a second UMF compiler. Its registered native plan/parameter grammar must admit exact original candidates, complete source/report/profile context and finite generated-metadata reservations before effects. The exact grammar/body remains a separate required output; an opaque caller blob or function name is not admission.

The selected function is VOLATILE, SECURITY DEFINER, PARALLEL UNSAFE, has an exact trusted search path and owner/dependency inventory, revokes PUBLIC execution and grants only the qualified acceptance path. Native acting-role/admin/disclosure admission remains independent of the function owner's effective privileges. Ordinary grantees have no direct catalog/report/head/source mutation or independently callable partial persistence/finalization helpers. Participating maintenance and host extension paths are included in the same closure; unsupported bypass paths invalidate the profile. A function-owner/superuser escape remains outside the ordinary-role guarantee.

The function and its admitted dependency/trigger chain cannot commit/rollback the caller transaction or expose a resumable phase handle. PostgreSQL 17's [transaction-management rules](https://www.postgresql.org/docs/17/plpgsql-transactions.html) distinguish transaction-ending CALL/DO paths from intervening SELECT function execution; use that boundary as a design prerequisite, not native qualification. Host/executor arbitration prevents another invocation/COMMIT from racing on the same original connection. Native exceptions propagate through the qualified statement/savepoint/whole-owned-transaction containment protocol; a caught error cannot return accepted while retaining only a subset of effects. The function returns complete pending semantic/report evidence only after parity and head publication. Outer confirmed commit remains the executor's responsibility, and cancelled/lost transport retains original execution custody.

Candidate `truss-acceptance-persistence/0.1.0` preserves immediate revision/document FKs and immutable schema_rev rows. Under the original exclusive head and complete admitted candidate/resource/profile closure, construct the complete expected acceptance report before inserting the parent revision row. Every reported effect identity/value/version/source and required generated metadata must already have an exact admitted value or be allocated/captured privately by the selected native producer before insertion. Planned sequence allocations may leave gaps after rollback; they do not establish committed events. An unknown later default, trigger-generated report member or unbounded producer output refuses this profile rather than requiring a partial report placeholder.

Insert schema_rev once with that complete immutable report/origin, then its exact schema_doc archives, then dependent catalog/source/lineage/graph/journal/history effects in the selected FK-compatible native order. Persist each planned generated identity/metadata value exactly where required; independently compare complete actual pending effects and full original source/report correspondence afterward. A report inserted inside this transaction is pending, not proof that its planned effects occurred or that acceptance committed. No partial seed report, accepted-row rewrite or mutable pending-index status is introduced.

Only after complete actual post-state/report parity may the protected finalizer publish schema_head and return pending acceptance under CONTRACT-007. Missing/extra/different effects or generated metadata abort the whole original acceptance under its qualified containment/recovery procedure; they cannot be repaired by rewriting the immutable report to fit unexpected effects. The selected native procedure/arbitration must prevent a caller from committing between parent insertion and finalization, including host extension and direct granted paths. A library call sequence alone does not qualify this boundary. Caller-owned outer durability remains pending; sent-COMMIT uncertainty and confirmed commit follow the executor's existing vocabulary. Exact native producer, parameter/canonical transport, phase encapsulation, privilege and fault qualification remain required design/adoption outputs.

#### Protected report encoder algorithm proposal

The native report producer consumes a complete privately owned validated report tree through its registered inert node/UTF-8 scalar representation, never arbitrary host objects, getters or callbacks. Input ownership covers every actual report/event/source value and its original capture; the encoder cannot fetch a later catalog value to finish a field. Reject unsupported node kinds, numeric nodes, cycles and invalid scalar encoding before treating them as report content. Shared internal storage is permitted only under the producer's immutable ownership profile; every occurrence still contributes output/work charges. This algorithm selects byte behavior, not a native language/extension or qualified implementation.

Use an explicit bounded task stack and a private segmented byte sink. A value task emits lowercase null/boolean literals, a scalar-string task, or opens an array/object frame. Arrays schedule children in their original order with comma separators and a closing bracket; empty arrays emit `[]`. Objects first collect the complete exact member-key inventory, reject duplicate decoded keys, reserve its storage/sort work and order keys by unsigned UTF-8 bytes. Schedule each quoted key, colon and corresponding value in that order, then close the object; empty objects emit `{}`. Sorting keys cannot reorder arrays or alter field values. Advance only the original top frame, preserving bounded depth and remaining-child count; finishing one chunk does not finish a container.

String emission decodes each complete Unicode scalar from the selected exact scalar source. Emit opening/closing quote; emit quote/backslash with their required two-byte escapes; emit control U+0000–U+001F as the exact lowercase ASCII six-byte escape specified by CONTRACT-009; emit every other scalar's original UTF-8 bytes, including slash, without normalization or alternate escape. Invalid UTF-8, surrogate content or selected forbidden NUL refuses under the applicable value/source profile. The native producer must not rely on JSONB output, locale formatting or a default JSON serializer to supply this spelling. Embedded ExactArtifact bytesBase64 remains a string; no traversal into its decoded payload occurs.

The sink uses proposed 65,536-byte chunks. Before allocating a chunk or accepting the next producer block, reserve its maximum capacity and simultaneous source/frame/key/sink ownership under the original report/acceptance ledger. Charge actual emitted bytes, scalar/key inspection, comparisons and copies independently; fixed chunk size does not bound total work or native memory. A large scalar emits incrementally without repeated concatenation of the accumulated output. Container/key inventories, parser/native detoast/sort/intermediate allocations and producer blocks remain separately bounded. A complete output limit failure aborts encoding, never truncates a field or produces a partial report/hash.

After the final frame closes, check actual total bytes and all container/producer completion invariants. Reserve the full contiguous report_bytes allocation while all source chunks still exist, copy exactly once in emission order, then release chunks only after their actual ownership ends. Hash the resulting complete bytes through the selected trusted SHA-256 implementation and encode ExactArtifact base64 under its existing grammar; charge both operations/copies and verify the actual stored report bytes under P5/P6. No digest or artifact is returned before complete encoding/admission. A native storage/driver implementation that requires additional copies must reserve them explicitly; a small sink chunk does not certify its maximum allocation.

The ExactArtifact base64 producer follows the standard alphabet/padding of [RFC 4648 sections 3–4](https://www.rfc-editor.org/rfc/rfc4648.html), with no line breaks or whitespace. Consume complete source bytes in three-byte groups, producing four alphabet bytes; carry at most two trailing bytes across sink/source chunk boundaries. Apply one or two final padding characters only after actual whole-source completion, with unused final bits zero. Do not pad each 65,536-byte report chunk independently. Reserve the exact widened output length `4 * ceil(byteLength / 3)` before output allocation and charge simultaneous source/base64/storage copies. Counts use the selected exact native domain, not host-number rounding.

A native MIME/base64 formatter is not automatically this producer: qualified PostgreSQL encode output may contain line breaks under its native format. Select an implementation that emits the exact artifact grammar or an explicitly specified bounded conversion whose complete output is independently checked; do not accept arbitrary whitespace stripping or alternate alphabets on ingress. On load, reject malformed length/alphabet/padding, nonzero unused pad bits or line breaks before trusting decoded bytes, then independently verify complete decoded length/hash/custody. Base64 syntax does not provide source authority or a commit/report validity claim. Native text/base64 buffers and conversion work remain part of the same original encoder/acceptance ledger.

For the proposed PostgreSQL 17 native report artifact profile, compute the direct artifact digest with qualified `pg_catalog.sha256(report_bytes)`, then lowercase hex with `pg_catalog.encode(digest_bytes,'hex')`. [PostgreSQL 17 binary-string functions](https://www.postgresql.org/docs/17/functions-binarystring.html) define the bytea SHA-256 and encoding operations. Admit the actual server/build/function identities and original complete bytea carrier; no function search-path lookup, caller-selected algorithm, pgcrypto substitution or SQL-text/JSONB hash is implied. The intermediate digest must be exactly 32 bytes and its hex exactly 64 lowercase digits. These operations are proposed profile selections, not qualified support for another major/build.

Hash the final complete report allocation, not chunks individually, base64 output, report identity text, a schema_rev JSONB rendering or the domain-framed acceptance-input fingerprint. Original native producer/storage correspondence must show that those same bytes were inserted/read as the immutable artifact. Independently compare against a separately implemented expected hash over retained original bytes; equality of two calls to the same native helper alone cannot qualify correctness/custody. Charge full input inspection/detoast/native output/hex buffers and copies to the original ledger, including failed work. Function absence/incompatible type/build or unknown resource/termination behavior refuses the selected profile; it cannot silently switch algorithms or supply an empty digest. The full report encoder/native binding remains a separate required implementation/design realization.

The original protected statement owns this encoder invocation and failure/arbitration. It invokes no external host callback, compiler, user-selected code or asynchronous worker after effects. Producer/encoder failure at this phase remains whole-acceptance rollback or original unresolved recovery, not a pure schema rejection. The selected native binding must realize the complete node/scalar/sink/hash/allocation/accounting procedure and original byte custody before adoption. Existing generic canonical vectors check spelling only; complete report/native producer/resource evidence remains separate.

## Error Semantics

| Condition | Outcome | Retry | Recovery |
|-----------|---------|-------|----------|
| A document fails UMF validation | Set rejected; report lists the violations | After fixing the document | Correct the document |
| Unknown endpoint with `reject` | Set rejected, naming each | After adding the definition or changing policy | Add the missing document |
| A tightened rule has violating objects | Set rejected; every violator listed | After correcting data or adding a transform | Fix the data |
| A type or cardinality change has no total transform | Set rejected | After declaring a transform | Declare it |
| Two documents define the same `(module, element)` with different bytes | Set rejected as `duplicate_definition` | After fixing the documents | Remove one definition |
| The lock is not granted within `lock_timeout` | The acceptance rolls back | yes, later | Retry |
| Dependency cycle between documents | Accepted together only when the pinned upstream package/validity profile supports that exact cycle; then use qualified SCC ordering | After selecting a supported valid representation | No fabricated external resolver or cycle permission |
| A writer is running | Acceptance waits for the writers' share locks to be released | automatic | None |
| Two acceptances at once | The second waits on the head row, reads the new head when it is granted, and validates against it | automatic | None |
| The same document bytes accepted twice | The current revision is returned only for a verified complete-input repeat; derived-row equality alone is insufficient | n/a | None |
