## Purpose

Defines how a set of UMF documents becomes an accepted catalog revision: the order documents are imported in, how catalog rows are derived, how ids stay stable, what happens to an entity type that a relationship names but no document defines, and the report every acceptance produces. Any implementation that accepts a revision does so the same way, so the resulting tables are the same.

## Selected reference property retirement and reactivation

Apply the owner-selected same-qualified-identity rule and the [reactivation persistence procedure](catalog-reactivation-persistence.proposal.md). Retirement preserves committed catalog identity and original value/presence/source custody under the original registered home and definition; it is not deletion, implicit movement to unknown name-keyed storage or allocation of a replacement Field. A retirement-only catalog transition records complete lifecycle history and report effects without inventing a property-value change. Separately required transforms remain explicit full plans.

Same-identity reactivation validates all retained values, keys/reservations, endpoints, ownership, cardinality and current authority before restoring active membership under the original ID and creation basis. A different authored identity receives a fresh ID without inherited values/history/grants. Reactivation neither restores revoked grants nor resurrects deleted records. Unsupported retained meaning or incomplete original custody refuses atomically. Current active projection and original retired-state integrity collection remain separate inventories under the [reference decoder](reference-row-decoder.proposal.md#retired-property-custody-and-active-projection); filtering retired states out cannot prove complete integrity.

Restored IDs and repeated original UMF bytes do not make an old accepted binding/current-authority observation fresh again. Re-admit the selected accepted/native context and owner registration per execution; separately qualified historical reads retain their original definition/history interpretation and current disclosure requirements. The concrete R-A/R-B/R-C source fixtures in STP-004 are valid experimental UMF inputs with complete=false, not accepted revisions or native lifecycle evidence. Their required value disposition, protected producers, complete report/history and profile composition must be realized before claiming support. This selection does not adopt every proposed ADR-004 physical identity mechanism or change the independently preserved baseline installation.

| Element | Rules |
|---------|-------|
| `documents` | One or more UMF documents as received bytes. Each has an identity `doc_id` and an owner-issued `doc_revision`. |
| `binding` | Optional truss binding vocabulary (storage home, indexes, statistics). |

**Acceptance steps.** An implementation MUST perform these in order. Acceptance is all-or-nothing: if any step rejects, nothing is written and the report says why.

0. **Lock.** Begin a transaction and take the catalog lock: `SELECT rev FROM schema_head WHERE id = 1 FOR UPDATE` (CONTRACT-001). This waits for the writers holding the share lock and blocks new ones while it is held, so no write runs between the checks below and the revision's insert. Set a `lock_timeout` first; on timeout the acceptance rolls back and MAY be retried later. The row read is the head; the new revision is head + 1. Steps 1 and 2 MAY run before the lock; everything from step 3 runs under it.
1. **Verify.** Compute `content_sha256` of each document's bytes, parse it exactly, and validate it with the pinned UMF validator. A document that fails validation rejects the set. An implementation that is not UMF's reference MUST accept and reject the same documents as the validator, with the same diagnostics (severity, code and path), which the corpus's `umf` cases test (CONTRACT-004); a document using a feature the implementation does not support is rejected and reported, never accepted silently.
2. **Order.** Sort the documents so that a document comes after every document it declares as a dependency or references by element. Collapse dependency cycles into strongly connected components, then topologically order the component graph dependency-first. Among ready components, compare their member `doc_id` vectors (each sorted by exact UTF-8 byte order) lexicographically. Members of each component take consecutive positions in that same byte order. This ordering rule does not authorize references or cycles that the pinned upstream validity profile rejects. External dependency syntax, valid cycle policy and revision pins remain upstream-gated; a local reference never searches another document. The resulting `ord` of each document is recorded in `schema_doc` and is deterministic for a given set.
3. **Derive in phases.** Over the whole sorted set, derive in this fixed order: all types, then all properties, then all keys, then all relationships and their endpoints. Because every type exists before any relationship is derived, an endpoint defined in a later document of the set is not unknown. Derivation follows SPIKE-002 and ADR-002 D5: a UMF record becomes a type; a field becomes a property; a record-valued field whose record has identity becomes a composition relationship to a child object with owned lifecycle, carrying `root_id` and `root_type`; a record-valued field whose record has no identity is stored as a structured value inside the owner's `props`, typed through the catalog (ADR-002 D5, provisional on V3); a named key becomes a `key_def`; an authored relationship becomes a `rel_def` with one endpoint triple per source and target pair.
4. **Resolve unknown endpoints** by `policy.unknown_endpoint` (below).
5. **Keep identity** under the selected layout/profile (below). In the legacy baseline, two documents in one set that define the same `(module, element)` reject the set as `duplicate_definition`, unless their bytes are identical; each catalog row records its defining document (`doc_ord`). Proposed document-qualified acceptance instead requires ADR-004 source ownership and the complete matching/allocation/finalization profiles below. A profile must preserve original IDs and retained high-water evidence; current visible rows alone cannot establish safe allocation (CONTRACT-001).
6. **Plan transforms and check candidate state.** A property type/cardinality change requires a declared qualified total transform; absence rejects before persistence. Evaluate each required transform over every affected stored value under the head lock, retaining the exact candidate result or its failure. Validate all tightened/added rules against the candidate state: transformed values where declared, unchanged values elsewhere, and final derived keys/relationship invariants. Report every available violation and transform failure, not only the first. A failed or incomplete scan rejects. Evaluation MUST NOT publish graph or catalog changes. Trusted transform registration, exact carriers and resource/report bounds require a versioned profile; input document content cannot load executable code.
7. **Persist** in the same transaction, still under the lock, unless the verified exact-repeat rule below applies. The following lists required effects, not permission to construct an incomplete parent report or expose separate persistence phases: insert `schema_rev` at head + 1 with its `origin` and the `schema_doc` rows; insert catalog rows using identities assigned once by the selected complete matching/high-water/allocation protocol (CONTRACT-001 and the allocation sections below), with owner-local key numbers kept distinct from global catalog IDs; update in place only the rows this contract permits, recording the before and after in `schema_change`; persist the exact transformed candidate values already checked at step 6 and write `transform` journal rows for each actual changed value; write `rebind` journal rows (CONTRACT-002); store the complete acceptance report once in the selected `catalog_acceptance_report` home, including declared pending index work, after original event production and before head publication; and update `schema_head` to the new revision. A failure while constructing or storing the report rejects and rolls back the entire acceptance. Accepting a type adds catalog rows only: no table, partition, column or index is created. Because the acceptance holds the lock, the revision number it inserts cannot conflict with another acceptance.
8. **Return acceptance** only according to CONTRACT-007 durability: engine-owned results follow successful commit; caller-owned results remain pending until the host commits. The report stored at step 7 is an immutable statement of acceptance, not a mutable index-job status row.
9. **Build declared indexes separately** after confirmed commit. Index work does not run inside acceptance and cannot change its accepted result. The acceptance report lists the declared jobs as pending at acceptance time; separate versioned readiness receipts record completion or failure. For an adopted transaction, the host must explicitly confirm commit before dispatching jobs; savepoint release is insufficient. The job/receipt schema and administrative execution API remain design gates.

The acceptance holds the catalog lock while it builds the rows, so its duration grows with the number of objects of the type, and the report says how many rows were built. A key removed from the documents is retired (`retired_rev`): its `object_key` rows are deleted, and its `key_num` is never reused.

**Transform persistence.** Persistence MUST use the validated candidate outputs rather than invoke a potentially stateful transform a second time. If an implementation cannot retain a candidate within its qualified resource profile, it rejects explicitly; it does not truncate checks or stream partial committed migration. Any native guard, key collision, journal or report failure during persistence rolls back the entire acceptance. The declared transform profile must specify no-op/version semantics and exact definition-revision attribution before support is claimed.

## Error Semantics

| Condition | Outcome | Retry | Recovery |
|-----------|---------|-------|----------|
| A document fails UMF validation | Set rejected; report lists the violations | After fixing the document | Correct the document |
| Unknown endpoint with `reject` | Set rejected, naming each | After adding the definition or changing policy | Add the missing document |
| A tightened rule has violating objects | Set rejected; every violator listed | After correcting data or adding a transform | Fix the data |
| A type or cardinality change has no total transform | Set rejected | After declaring a transform | Declare it |
| Two documents define the same `(module, element)` with different bytes | Set rejected as `duplicate_definition` | After fixing the documents | Remove one definition |
| The lock is not granted within `lock_timeout` | The acceptance rolls back | yes, later | Retry |
| Dependency cycle between documents | Accepted together only when the pinned upstream package/validity profile supports that exact cycle; then use qualified SCC ordering | After selecting a supported valid representation | No fabricated external resolver or cycle permission |
| A writer is running | Acceptance waits for the writers' share locks to be released | automatic | None |
| Two acceptances at once | The second waits on the head row, reads the new head when it is granted, and validates against it | automatic | None |
| The same document bytes accepted twice | The current revision is returned only for a verified complete-input repeat; derived-row equality alone is insufficient | n/a | None |
