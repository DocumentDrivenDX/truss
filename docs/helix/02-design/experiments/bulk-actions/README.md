# Bounded frozen UPDATE batch model

US-048-AC7 / TD-048 / CONTRACT-013 / original UMF CONTRACT-904.

`python3 check_model.py` enumerates the finite state graph directly, comparing full immutable state values. `BulkUpdate.tla` independently specifies the same actions/invariants for TLC. `check_tlc.py --java /path/to/java --jar /path/to/tla2tools.jar` runs the full model, five independent source mutations, and verifies that its reachable-state count equals the retained Python result. Obtain the official checker from [TLA+ releases](https://github.com/tlaplus/tlaplus/releases/tag/v1.7.4). The executed tools are pinned in the receipts; binaries are external tools, not committed dependencies.

The model has two workers, two bounded claim fences, three frozen targets2/10/11, and two batches [2,1]. Eight initial change/no-op masks independently track attempted item staging, actual changes, complete original result vectors, durable contiguous prefix and published observations. External edits/rebindings are possible before native guard locking; neither can race a write within the modeled lock boundary. Removing that boundary yields a counterexample.

Physical effect connection opening precedes independent admission-marker persistence. Actual and observed native/marker dispositions are separate. Lost marker acknowledgement cannot permit effects without original committed-result recovery. A running original transaction can remain unresolved after crash/lease expiry/missing lookup. A committed transaction retains its result and effects despite lost acknowledgement. Confirmed rollback after a staged write, then crash before stop persistence, is a useful witness: reconciliation stops without retry. Missing lookup cannot invent noncommit. Cancellation records its admission fence separately from a settled result; terminal stopped/completed states are preserved. Namespace restore fences future effects unless an external complete consistency proof is supplied.

Python invariants and nine mutated transition systems test stale writes, live lease/fence at job-lock admission, whole-batch outcome/receipt atomicity, exact no-op/changed effects, complete retained result vectors, frozen identity/version, no automatic admitted retry, no future dispatch/commit after cancellation/stop/restore cutoff and no invented native disposition. TLC rejects five mutations: expired-admission, partial-commit, guard-race, unconfirmed-marker and `job_refinement_restart_stopped`. Successful traces reach both batches, reconcile lost COMMIT acknowledgement, preserve a cancelled prefix and stop after original rollback/crash.

These are bounded safety results. Claim bound2 and three targets are deliberate; unbounded liveness is not verified. Fair scheduling, eventual original native termination and current-authorized lookup are liveness premises. This does not qualify native PostgreSQL locks, issuer/driver/ACL/source installation, seal/submit/claim/cancel immutable control-result APIs, delegated human authorization, full tx/1 stage semantics, namespaces/token bytes, journal/feed/outbox or exact storage/resource accounting. Semantic control-result retention is a separate runtime requirement even though marker custody is modeled.

## Job-table refinement (UMF US-907-AC7)

`gen_job_table.py --fixture <umf>/docs/helix/03-test/fixtures/bulk-update/transitions.json` generates `BulkUpdateJobTable.tla` (18 permitted `(from, to, committed-delta)` triples; the header pins the fixture hash; `--check` fails if stale). `BulkUpdate.tla` projects every state to a job status and durable committed-batch count (a native commit with a lost acknowledgement counts once the original result is observed) and `PROPERTY JobRefinement` requires every step to stutter or match a fixture triple. `check_job_refinement.py` does the same over the Python graph. The retained Python and TLC result JSONs report 607,102 states ([Python result](../../../04-build/evidence/bulk-update/batch-model-results.json); [TLC result](../../../04-build/evidence/bulk-update/tlc-model-results.json)); the retained TLC log confirms that state count. The retained `python-model.log` instead reports the earlier 604,852-state run and pins an older `check_model.py` hash, so it does not corroborate the current Python result JSON; this evidence discrepancy is unresolved and no model was rerun for this reconciliation. The fixture is hand-authored from UMF CONTRACT-904 and still needs owner review (`status: planned`; [job-refinement receipt](../../../04-build/evidence/bulk-update/job-refinement-results.json)).

Two fixture behaviours were added to the model so the refinement exercises them: a lease that expires before any native work puts the job back in the queue (T8; a projection rule), and a cancel requested during an admitted attempt is consumed by that attempt's commit, including a lost-acknowledgement commit (T10; `Commit` now fences cancel and sets `cancel_status`). Controls: `job_refinement_restart_stopped` (TLC, violates `JobRefinement`) and `unsafe_restart_stopped` / `unsafe_retry_admitted` (Python). The only fixture triples not exercised are terminal and self steps (stutters). Receipts: `tlc-model-results.json`, `tlc-negative-results.json`, `job-refinement-results.json`. TLC 2.19 ran on OpenJDK 21 with the v1.7.4 jar.

## Candidate control layout (`bulk-control-layout.sql`)

Fixed-layout homes `truss_bulk.job` and `truss_bulk.batch_receipt` (one home per concern, never per job). The job row's CHECK constraints encode the state invariants: contiguous committed prefix within the batch count, all-or-none claim and stop records, a claim naming the next batch under the current fence, per-status shape, canonical decimal fences, bounded manifest (1 B to 16 MiB) and per-batch result (R = 2 MiB). Transition legality stays in the executor under the job lock.

`PYTHONPATH=packages/python/src python3.11 check_control_layout.py --fixture <fixture> --pg-bin <postgresql@18 bin> --out <receipt>` runs it on a scratch initdb cluster (unix socket only): all 53 states reachable from `_bulk_job_control` and the fixture's sample states are accepted, and 26 invalid rows are rejected (79 cases). Dropping `claim_is_next_batch`, `status_shape` or `stop_all_or_none` each makes a reject case fail. Running it surfaced two model facts: terminal jobs keep `cancelRequested` as history, and a cancel pending when the LAST batch commits must leave `completed` (UMF fixed its TypeScript model, oracle and fixture in UMF PR 131, and CONTRACT-904 now states it; owner to confirm; the Truss module follows `BulkUpdate.tla`).

This is a design candidate, not a migration: UMF has not exported this layout, it is not in the pinned install baseline (`_migrations`, ACL profile, deparse equivalence), and it has no grants, writer role, locks or concurrency. Installing it needs a new qualified baseline.

## Candidate control functions, role `bulk-worker`, lock level 4a

Owner decisions (2026-11-10): the worker database role is `"bulk-worker"`, and the job-control lock is level 4a of CONTRACT-009. `bulk-control-functions.sql` implements the transitions as `SECURITY DEFINER` functions: `worker_event` (claim, execute, commit, failure, lose-custody, reconcile, expire-claim) and `control_event` (cancel) over private `_apply`/`_advance`, plus the control-plane `submit`. Each function's first and only lock is `SELECT ... FOR UPDATE` on the job row, which is the 4a lock, held until the calling transaction ends. `bulk-control-grants.sql` gives `"bulk-worker"` USAGE on the schema and EXECUTE on `worker_event` only: no table privileges, no submit, no control surface, no helpers. The installer creates the role; the SQL does not.

`PYTHONPATH=packages/python/src python3.11 check_claim_fence_native.py --pg-bin <postgresql@18 bin> [--out receipt]` runs 27 checks with concurrent psql sessions on a scratch cluster: a claim race (second claimant blocks on the lock, then is refused), stale fence refusal, cancel against an admitted attempt in both lock orders, the role surface, the lock footprint (relation locks on the job home only, no advisory locks) and 400 random event sequences (about 1,100 events) that agree exactly with `_bulk_job_control`. Controls that each fail the run: removing `FOR UPDATE` (a second claimant wins with fence 2), disabling the fence check, granting the worker table access, and restoring the old final-batch rule (the layout's CHECK rejects it).

Not covered: levels 1-4 (the caller must already hold them; nothing here verifies that), the effect transaction and its atomic coupling with the committed-prefix advance (a native commit whose acknowledgement is lost can leave the job row behind the graph), authority, custody and reconciliation evidence, lease timing, and the install baseline. Native US-046-049 criteria stay planned.
