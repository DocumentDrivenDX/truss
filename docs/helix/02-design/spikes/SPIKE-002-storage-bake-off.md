# SPIKE-002: Storage bake-off on PostgreSQL: UMF-generated per-type tables (A) versus generic catalog storage (C)

**Spike ID**: SPIKE-002 | **Lead**: Claude Code agent for the project owner | **Time Budget**: about 7 hours of agent work (one sandbox session) | **Status**: Completed as evidence; owner review and the storage ADR are pending

Executed evidence for the [research plan](../../01-frame/research-plan.md). Everything here was run on
2026-09-25 in one cloud sandbox. Each finding quotes raw output from
[`SPIKE-002-storage-bake-off/out/`](SPIKE-002-storage-bake-off/out/). The scripts, the UMF model and the
generated DDL are in [`SPIKE-002-storage-bake-off/`](SPIKE-002-storage-bake-off/). Spike code is throwaway
evidence, not truss implementation code.

Time box: about 7 hours of agent work. Actual: about 1 hour 30 minutes of wall-clock time from the PostgreSQL 17
build (03:22 UTC) to the last revision rerun (04:43 UTC), plus the write-up; PostgreSQL 17.11 built from source in
1 min 31 s. Nothing in the plan was cut for time.

## Objective

**Technical Question**: On PostgreSQL, what do option A (per-type tables generated by UMF's DDD-to-PostgreSQL
projection, CONTRACT-043) and option C (generic catalog storage: one flat JSONB property map per object, keyed by
property-definition id, with edges in their own table) each cost on the five questions in the research plan?

**Goals**:
- [x] Q1: cost of the five scripted revisions R1–R5 while a background writer runs
- [x] Q2: which UMF assertions each option enforces, in which layer, and the evidence for each
- [x] Q3: whether any value changes between write and read through a TypeScript client on Bun
- [x] Q4: query code per shape, whether it is generic or per type, and whether UMF plus a binding can generate it
- [x] Q5: p50/p95 latency and on-disk size, as C/A ratios against the 2× target

**Success Criteria**: the plan's success criteria for Q1–Q5, with raw outputs committed beside this document, every
hand-written substitute for missing UMF generator output listed, and a recommendation that names a storage strategy
and the conditions that would reverse it.

**Out of Scope**: SQL Server; query language design; production code; UMF proposal-stage concepts (cross-document
references, schema evolution, temporal facets, constraint ideals) except where a revision needed a truss-local
stand-in, which is flagged; replication, high availability, Python.

## Hypothesis

**Primary**: generic catalog storage (C) absorbs schema revisions without table rewrites or table locks, enforces at
least the assertions A enforces when an engine layer is added, keeps every value exact when JSONB is read as text,
needs generic rather than per-type query code, and stays within 2× of A's p95 latency.

Per question: H1: C's revisions need no DDL and block no writers, A's rewrite tables and take `ACCESS EXCLUSIVE`
locks. H2: C can enforce everything A enforces, in the engine or through conditional `CHECK` constraints. H3: A
changes some values (types chosen for it), C changes none when JSONB is read as text. H4: A's query code is per type
and not generatable from UMF plus a binding today; C's is generic. H5: C's p95 is within 2× of A's for fetch and
one-to-three hops.

**Assumptions**: synthetic data with skewed fan-out is adequate for relative comparisons; one shared VM gives usable
ratios, not absolute figures; UMF's library at the pinned commit is representative of what truss would consume.

**Expected Outcome**: C is at least as good as A on Q1–Q4 and within 2× on Q5, at a size and planning-cost premium.

  loader deriving catalog rows, 11 indexes and 52 conditional CHECK constraints from the core model, and one generic
  deferred multiplicity trigger (`sql/c_triggers.sql`):

  ```
  catalog: 5 types, 26 props, 5 keys, 4 relationships; 52 CHECK constraints; 11 indexes
  {"records":{"Customer":20000,"Product":5000,"Order":100000,"OrderLine":401568},"objects":542508,"edges":919076,"engineViolations":0,"encodeMs":5137,"validateMs":6341,"validatePerSec":83047}

  engine validator rejected all 5,000 generated products because the generator had written prices as JSON strings;
  A's CSV load had accepted the same values silently (text coerced to `numeric`).
- **Implications**: A depends on hand-written DDL for every key, relationship, invariant and multiplicity rule, and
  on a hand-written policy for every column type. C's per-type DDL is generated from the core model by about 160
  lines of generic loader code (`loader/catalog.ts`).

### Q1. What does each option cost when the schema changes?

**FINDING 3**: Every A revision takes `ACCESS EXCLUSIVE` on the changed table, and R2 and R4 rewrite it; C's
revisions with engine-side enforcement take no table lock stronger than `ROW EXCLUSIVE` and rewrite no table.
With database-side CHECKs, C takes a brief `ACCESS EXCLUSIVE` on the shared objects table, which blocks writers of
every type, not only the changed one.

  `ACCESS EXCLUSIVE` on the table every type shares.
- **Inferred caveat**: C-engine's rule change is safe only if every engine instance reads the new catalog before
  writing; the spike did not test an engine that caches an old catalog.

### Q2. Which UMF assertions does each option enforce, in which layer?

**FINDING 4**: Option C enforces every assertion in the test model, in the engine and again in the database; option
A enforces most in the database, but three are silently unenforced (decimal scale is rounded, a string column
coerces a number, array items are unchecked JSONB) and every primary key, relationship and invariant rule in A is
hand-written DDL (only the alternate key's uniqueness comes from a generated binding index). Cross-row minimum
multiplicity needs a deferred trigger in both, and both triggers lose to the same READ COMMITTED race; the engine
closes it by locking the parent object.

- **Evidence** (observed, `out/20_enforcement_pg17.txt`; the same matrix on 18.6 in `out/20_enforcement_pg18.txt`;
  harness `harness/enforcement.ts`). Every case is one violating write and one control write per option and layer,
  each in a transaction rolled back after `SET CONSTRAINTS ALL IMMEDIATE`. All 57 control writes were accepted, so
  no cell passes vacuously. Selected raw lines:

  ```
  [P2] decimal scale 2, no implicit rounding: Order.total 10.005

## Analysis

**Hypothesis**: PARTIALLY CONFIRMED

**Rationale**: H1 is confirmed for C with engine-side enforcement (no DDL, no table lock above `ROW EXCLUSIVE`,
no rewrite) and only partly for C with database CHECKs (brief `ACCESS EXCLUSIVE` on the table every type shares);
A took `ACCESS EXCLUSIVE` in all five revisions and rewrote the table twice. H2 is confirmed: C enforced all 19
assertions, A left three silently unenforced, and both need a parent lock (not a trigger alone) for cross-row minimum
multiplicity. H3 is confirmed: A changed values in four ways traceable to its column types; C changed none once JSONB
is read as text, while both lose precision through `Bun.sql`'s default decoding. H4 is confirmed: A's six statements
are per type and its traversals cannot be generated from UMF plus `umf-binding-1`; C's four templates are generic.
H5 is only partly confirmed: C is within 2× at p95 for fetch, one hop, range and update with prepared statements, at
the boundary for two hops (1.70–2.32× across run sets and key choices), and misses by 2.8–6.6× without prepared
statements.

What the evidence says beyond the hypotheses:

- **The UMF generator is not yet a storage generator.** Its output is the table-shaped fraction of A: every key,
  relationship, invariant, multiplicity rule, migration and query is hand-written, it reads a DDD view instead of the
  core model, and it accepted a policy that contradicts the core facets without a new residual. A "runtime over
  UMF-generated tables" today means a runtime that generates most of A itself, per type.
- **C's costs are generic and bounded, but real.** C trades A's per-type code and table locks for 4.8× disk, an extra
  index probe per hop, planning overhead that grows with the model, and client-side care (text read path, prepared
  statements). None of these grow with per-type hand-written code.
- **Where database enforcement lives matters more than whether it exists.** Per-type conditional CHECKs on the shared
  table enforce everything, but cost about 14 µs per constraint per statement for every type and take
  `ACCESS EXCLUSIVE` on every revision. Generated unique partial indexes, typed endpoint FKs against catalog rows and
  partial unique edge indexes gave database enforcement for keys, endpoints and maximum multiplicity with no DDL on
  revision; a catalog-driven trigger covered the value rules at about 0.2 ms per row.

### Risks

| Risk | Prob | Impact | Mitigation |
|------|------|--------|------------|
| Planning cost grows with the number of types (partial indexes on shared tables): 5–8 ms per query at 105 types | H | H | Prepared statements are mandatory; partition objects by type (probe: 1.0–1.9 ms at 105 types); measure at realistic type counts |
| Two-hop tail at or above 2× for heavy fan-out | M | M | Covering edge indexes that include `target_type`; shaped (per-type) storage for hot relationships behind differential tests |
| 4.8× disk footprint (edge table and its indexes dominate) | H | M | Drop indexes a runtime does not need (edge `id` PK, `(id, type_id)` key once partitioned by type); measure JSONB compression |
| Engine instances enforcing a stale catalog after a revision | M | H | Catalog revision checked per transaction (for example `FOR SHARE` on the current `schema_rev` row); not tested here |
| Cross-row rules race under READ COMMITTED (observed in both options' triggers) | H | H | Engine locks the parent (`FOR NO KEY UPDATE`) or runs SERIALIZABLE; only delete-last-line was tested |
| Row-lock strength: `FOR UPDATE` on objects blocks every edge insert through the typed FKs (observed 1.7 s stall) | M | M | Use `FOR NO KEY UPDATE` everywhere in C's write path |
| Client decoding silently loses precision (int64, decimal scale, timestamps) | H | H | Text read path with an exact parser in every adapter; conformance tests on every client |
| Evidence limits: one VM, cached data, a 5-type model, Bun only, no pooler | H | M | Repeat on the project's benchmark corpus with a pooler and Node `pg` before the ADR is final |
| UMF generator scope changes (relationship stage, core-driven types) | M | M | Re-run `model/validate_and_generate.ts` against a newer UMF commit; A's hand-written list shrinks accordingly |

## Conclusions

**Primary Conclusion**: On PostgreSQL 17.11 (and 18.6 for fidelity and enforcement), generic catalog storage (C)
beats UMF-generated per-type tables (A) on schema change, enforcement coverage and transparency, value fidelity and
query-code generality, and meets the 2× latency target for fetch, one hop, range and update with prepared statements;
it is at the 2× boundary for two-hop traversals and costs 4.8× the disk space. A is not a finished alternative today:
UMF's generator emits only the table stage, so a runtime over A would generate keys, relationships, invariants,
migrations and queries per type itself.

**Confidence**: Medium. The functional results (Q1–Q4) are deterministic and reproduced on two PostgreSQL majors;
the latency ratios come from one shared VM with cached data and vary by up to about 0.45× between run sets at p95.

**Limitations**: Not tested: a connection pooler; Node's `pg` client (SPIKE-001 showed the same `JSON.parse`
hazard); multi-instance engines and catalog caching; concurrent readers; generated plain-SQL views over C; A with an
alternative policy (text timestamps, presence flags); revisions at larger table sizes (A's rewrite cost is inferred to
grow with rows); UMF's per-concept key and facet projections (read, not run). The owner has not yet reviewed this
spike.

## Recommendations

**RECOMMENDATION**: Choose option C, generic catalog storage, as truss's storage strategy on PostgreSQL. Do not
build a runtime over UMF-generated per-type tables. Keep generated per-type ("shaped") storage as a later,
measured optimization for hot types behind differential tests, not as part of the first build.

- **Rationale**: C absorbed all five revisions without DDL or table locks and listed every violating object before
  accepting a tightened rule (FINDING 3); it enforced all 19 assertions and names each rule it enforces (FINDING 4);
  it returned every corpus value exactly on the careful read path (FINDING 5); its query code is generic and derived
  from UMF (FINDING 6); and it meets the 2× target for four of six shapes and sits at the boundary for the other two
  with prepared statements (FINDING 7). A depends on 12 hand-written DDL items, a hand-written type policy and
  stand-in model fields today (FINDING 2), and it still cannot hold unknown data or keep timestamp offsets.
- **Design constraints the evidence imposes on C**:
  1. Prepared statements (or an equivalent plan cache) in every adapter; bound the number of indexes per table as the
     model grows, most likely by partitioning objects by type.
  2. Engine-side validation is the reporting layer; database-side enforcement only in DDL-free forms: generated
     unique partial expression indexes for keys (`COLLATE "C"`), typed endpoint FKs against `rel_endpoint` rows,
     partial unique edge indexes for maximum multiplicity, and optionally the catalog-driven trigger. Avoid per-type
     CHECK constraints on shared tables.
  3. Cross-row rules lock the parent object (`FOR NO KEY UPDATE`) or run SERIALIZABLE; never rely on a deferred
     trigger alone under READ COMMITTED.
  4. Read JSONB as text and parse it exactly; encode binary as base64 and timestamps as their RFC 3339 text.
- **Conditions that would reverse or modify this recommendation**:
  1. On the project's benchmark corpus at production scale, with prepared statements and a pooler, C's p95 for one to
     three hops exceeds 2× A's and partitioning or covering indexes do not bring it back: move hot types to shaped
     per-type tables (C with generated per-type tables), or reconsider A.
  2. Target deployments cannot use prepared statements or plan caching (for example a transaction-mode pooler
     without prepared-statement support): C missed 2× by up to 6.6× without them.
  3. The 4–5× disk footprint is unacceptable for the target users.
  4. UMF's generator gains the relationship, key and migration stages and core-facet-driven types, and users need
     typed per-type tables as the storage of record for plain SQL (not views): A's hand-written share shrinks and the
     remaining difference is revision cost.
  5. Engine-side enforcement cannot be made safe across engine instances (stale catalogs) and database-side value
     enforcement (trigger at about 0.2 ms per row) is too expensive: C's enforcement-transparency advantage narrows.
- **Next Steps**:
  1. Owner review of this spike, then a storage ADR in `02-design` recording the decision (completion criterion not
     yet met).
  2. Follow-up spike: C partitioned by type at realistic type counts, data larger than memory, a pooler, Node `pg`,
     and generated read views for plain SQL.
  3. Design the engine's catalog-revision protocol and the parent-lock rule for cross-row constraints.
  4. Hand the UMF gaps found here to UMF: the generator reads only `umf.ddd`, not core records, facets, keys or
     relationships; it does not cross-check policy types against facets; no offset-preserving temporal type; no map
     cardinality in DDD; no invariant concept in core; `umf-binding-1` has no generic storage strategy; and
     `encodeCoreKeyTuple` revalidates the whole document per call.
- **Concern Impact**: No concern is adopted or rejected. The evidence refines practices under `postgresql`
  (prepared statements; bounded index count per table), `sql-exactness` (text read path; `FOR NO KEY UPDATE`; no
  implicit decimal rounding) and `umf-fidelity` (retained map observed working); an ADR should ratify these and
  update the concerns document.
