# ADR-004: Document-qualified catalog ownership

**Status:** accepted by the owner on 2026-10-09; exact native/profile implementation remains unqualified. **Date:** 2026-10-05.

## Problem

Logical identity in CONTRACT-003 includes owning document, module and element, while layout 0.2 type uniqueness and module access collapse module names across documents. Weft retains owning model pins. Two independent documents containing module sales and element Customer cannot safely share one catalog row or policy grant. Definition revision, source digest and Truss catalog revision also have different meanings.

## Proposed decision

Use exact `(document_id,module_id,element_id)` as lineage identity. An accepted definition adds its owner-issued document revision and verified source bytes; Truss's numeric catalog revision remains the acceptance boundary. Generated type/property/relationship ids and key_num remain storage identifiers, never semantic identity. Document identity is case-sensitive opaque text, without namespace/name guessing or normalization.

Add owning document identity to catalog type ownership and qualify module grants by `(document_id,module_id)`. Relationship ownership is its declaring document/module independently of endpoint ownership. Properties and named keys inherit their owning type's document/module while retaining authored element/key identities. For synthesized composition relationships, publish a collision-free versioned derived identity distinct from authored element IDs; do not assume a field display name is an authored relationship identity.

The fixed physical layout remains generic: this introduces fixed ownership columns/constraints, not per-type tables. Revise type uniqueness to the full lineage tuple; optional module_access key and helpers receive document plus module. Exact column names, relationship inheritance and historical policy envelope are shared-contract changes to review before any generated DDL is authoritative. Candidate layout version must change explicitly; this proposal does not relabel existing 0.2 storage as compatible.

## Definition provenance

A catalog definition's source points to `(catalog_revision,document_ordinal)` or an equally unambiguous immutable schema_doc key. An ordinal alone is insufficient across revisions. In-place updates retain original since_rev and record both old/new definition provenance in schema_change. Provisional placeholders require exact declared owner identity; absent authoritative ownership is a blocked capability rather than global name search.

Current core 0.7 documents do not gain successor revision semantics from matching unknown fields. CONTRACT-003's host-issued doc_revision remains a verified-byte label within its current input profile. Future UMF package pins are consumed only after the corresponding upstream version/migration is implemented. Ownership qualification does not enable cross-document relationship resolution by itself.

## Owner-selected retirement direction — 2026-10-07

Same-qualified-authored-identity reactivation preserves its original Truss storage ID after full validation; distinct incarnations require a distinct authored identity and fresh storage ID. Historical definitions/reservations remain interpretable and grants are not implicitly restored. CONTRACT-003, US-004 and STP-004 carry this selected direction. Document-qualified catalog ownership is owner-selected; exact interface/native/profile implementation remains unqualified; that status does not reopen the answered lifecycle choice.

## Alternatives

### Historical retirement alternatives before owner selection

FR-4 requires unchanged UMF identity to retain its storage identifier; US-004's retired-redefinition edge case also says not to issue a retired identifier. These conflict when a removed element returns with the same qualified identity. Document revision alone cannot distinguish a successor definition from a new logical incarnation. Do not resolve this by silently allocating a different storage id for unchanged lineage or clearing retirement and calling the old id new.

Recommended model: active compatible lineage preserves its storage id; retirement retains its complete historical definition and id reservation. A genuinely new incarnation receives a new owner-declared semantic identity and a fresh storage id. If upstream permits reactivation of the same identity, preserving its old storage id is continuity rather than reuse, but it requires explicit product reconciliation of the edge-case wording plus validation of retained values, keys, endpoints and policy history. Otherwise same-identity reintroduction must refuse with an explicit lifecycle diagnostic until the owner supplies a valid distinct incarnation or approves a migration. This refusal is a gate, not completion of the desired lifecycle capability.

Independent review vectors: active rename with unchanged authored identity preserves id; retire A then add distinct B never reuses A's id; same-identity A reintroduced cannot be guessed from its display name or new document revision; distinct incarnation A2 receives a fresh id and does not inherit A's keys, grants or objects implicitly. Historical journal values continue to resolve A's original definitions in every branch. Select and reconcile one upstream-valid lifecycle before DDL/API implementation.

| Alternative | Consequence |
| --- | --- |
| Require globally unique module/element tuples across all documents | May be an explicitly restrictive temporary profile, but cannot fulfill independent document ownership; must refuse collisions before derivation |
| Flatten/rename modules on import | Changes authored identities and breaks model pins; rejected without explicit semantic migration and loss reporting |
| Store only document ordinal on types | Ordinal is revision-local and cannot establish stable lineage or policy scope |
| Allocate new storage ids for every document revision | Breaks lineage stability and stored/journal identity across compatible revisions |

## Migration and rollback

### Candidate lifecycle transition matrix

This historical matrix compares both policies; the owner-selected reactivation direction above governs current work. The terminal alternative is retained for comparison, not a pending choice. Match exact qualified authored identity before labels or allocation. Document revision changes definition provenance, not incarnation identity.

| Transition | Reactivation profile | Terminal-retirement profile | Shared invariant |
| --- | --- | --- | --- |
| Active, unchanged identity and compatible renamed label | Preserve ID | Preserve ID | Retain historical definition |
| Active definition removed | Retire, retaining ID/history | Same | No recycling or implicit canonical deletion |
| Retired, same exact identity reintroduced | Validate completely, then reactivate existing ID | Refuse lifecycle transition | Never assign new ID as unchanged lineage |
| Retired, distinct authored incarnation introduced | Allocate fresh ID | Same | No implicit data/key/grant/endpoint inheritance |
| Equal label with ambiguous identity | Refuse | Refuse | No name-based matching |

The selected reactivation behavior validates retained canonical values, ordered key domains/uniqueness/reservations, endpoint/cardinality/ownership closure, transforms and qualified current authorization before clearing retirement or advancing the head. Failed validation preserves prior retired state, history, keys and journal atomically; no implicit deletion repairs invalid data. Success records an auditable retired-to-active definition transition while old events keep original definition pins. Deleted records stay deleted and tombstones remain. Apply the rule separately to property/type/key/relationship identifier domains. Terminal retirement instead requires distinct authored identity or a separately reviewed migration; changed bytes/labels/revisions cannot evade it. Pin the selected lifecycle in the acceptance profile so repeated acceptance and cached mappings cannot change meaning silently.

### Physical migration

#### Required key-history conversion admission

For the selected reactivation/history behavior, conversion begins with an original protected cut, complete native key/ID-reservation inventory and original accepted document/binding/definition/allocation archives through that cut. Establish each owner's full lineage, immutable since_rev, exact owner-local number and actual definition edits/retirement intervals from retained evidence. Current key_def alone cannot prove prior component changes, source versions or intervals. Baseline schema_change excludes keys, so an empty matching query is not proof that no key changed. Evidence must independently cover every expected key and revision, including retired keys with no live object_key rows; ambiguous owner/allocation/source gaps refuse conversion before candidate publication.

Produce one explicit source-to-target correspondence per creation basis and actual transition, retaining original source/capture artifacts and conversion profile. Newly encoded snapshot bytes are conversion-produced representations with their own identity/provenance, never the original historical bytes. Preserve original native semantics and unknown content, record any unavailable lexical distinction or interpretation and refuse a selected exact-history claim if that loss prevents its required meaning. Do not manufacture original report/event/group/transaction metadata, rename an old retirement into reactivation, guess seq from source array order or use today's validator registry to certify old acceptance. Target sequence ordering must be derived from independently admitted original transition order under the selected conversion profile.

Stage complete candidate history privately, independently reconstruct every supported historical cut and compare original current state at the captured cut. Verify native type/dependency/constraint/privilege inventory, full report/feed/seed interpretation and protected source retention before switching selected layout/reader/writer profiles. Publish the new profile/head/history basis atomically under original migration exclusion and preserve original-attempt recovery for unknown outcomes. Unresolved or missing required archives produce unavailable conversion; installing an empty history table is not a completed migration. A separately proposed cut-only checkpoint cannot silently replace the goal's full historical support and requires an explicit reviewed scope/loss decision. Fresh installation remains separate from populated conversion, and old readers/mappings must refuse the changed layout unless explicitly qualified.

Existing databases need an explicit reviewed migration that assigns every historical definition to its verified owning document and checks ambiguity before any uniqueness/grant change. Never infer owner from equal names or assign an arbitrary first document. Ambiguous rows block migration. Rebuild mappings and policy profiles with new pins; old cursors/bindings refuse rather than reinterpret. Rollback after new competing owners are stored cannot safely collapse them into old uniqueness, so disabling the new profile is not a destructive downgrade.

## Acceptance of this design

Review exact ownership/provenance schema with UMF and Weft owners, then update CONTRACT-001/003/005, native UMF model, bootstrap inventory, report schemas and affected TD/STPs. Independently expected fixtures must prove equal module/element names across two documents remain distinct, same lineage stays stable across revisions, wrong-owner references refuse and grants do not leak across owners. Native migration/policy evidence is a later build gate; this ADR is a concrete proposal, not accepted storage behavior.


## Proposed synthesized composition identity profile

Candidate `truss-composition-field-lineage/0.1.0` represents relationship lineage as a tagged identity, not an encoded display-name string. Authored relationships use category authored with their exact qualified owner/element identity. Truss-derived composition relationships use category composition_field with exact profile, owning document/module, owning Record authored identity and owner-provided field identity. Category is a separate identity component in storage/lookup/uniqueness and history. An authored opaque element string that resembles the serialized derived tuple cannot collide with the derived category.

The field identity must come from the admitted UMF source/profile's actual identity contract and exact original source pointer/provenance. A field name, array index, display label, JSON pointer or digest is not a substitute for stable authored identity. If the selected source profile has no qualified continuity identity for that field, derivation cannot claim rename/reorder stability; retain the source and report unavailable lineage support until an owner-defined identity/migration profile exists. This does not add a field-ID requirement to UMF validity or invent upstream semantics.

The target Record/endpoint, cardinality and lifecycle belong to the revision-qualified derived definition, not this lineage tuple. Supported changes preserve the derived storage ID only after candidate transformation, endpoint/value/key/ownership validation and complete before/after history admission. They cannot silently redirect retained owned edges. Rename/reorder with unchanged qualified field identity preserves lineage; moving owner document/module/Record or changing field identity selects different lineage unless a separately reviewed migration applies. When a field no longer requires an owned object relationship, retire the derived relationship and preserve its historical provenance. Same-identity later reintroduction follows the owner-selected validated reactivation rule; this identity profile alone does not satisfy its complete lifecycle validation gate.

Use a fixed generic category/discriminator plus exact full identity component columns or an equivalently qualified injective full-tuple native representation. No per-field tables, reserved string prefix or digest-only unique key. Persist the full original derivation profile/source/owner identity and exact prior/new derived definitions atomically with acceptance. Numeric relationship IDs remain storage bookkeeping. Complete physical columns/constraints and UMF extraction/Weft mapping review remain proposed layout-adoption outputs; neither the baseline 0.2 rel_def nor an opaque synthesized element label is reclassified as supporting this profile.


### Current UMF core identity correspondence

Read-only source review at UMF commit 16c35e8d943769ccfa7bb57d16785aa7159abe65 confirms Element.id is distinct from optional Element.name (`src/model/types.ts`), CoreKindIdentity is `{module,element}` (`src/model/field-kind.ts`), and Record membership uses explicit ordered Field references (`src/model/keys.ts`). Consume that existing owner identity for qualified authored core Fields; no new UMF field-ID capability is required for this subset. The proposed full derived identity has exact components `{category:composition_field, profile:truss-composition-field-lineage/0.1.0, ownerRecord:{document,module,element}, sourceField:{document,module,element}}`. Both module identities are explicit; never assume the Field module equals the Record module.

Admission verifies original pinned Record membership names that exact Field and the owner record-type declaration resolves its target under the selected core/source version. Display names and membership order are definition/source facts; changing them with the same qualified identities does not change this proposed lineage. This is Truss continuity design using owner identity, not evidence of a native adapter preserving IDs across arbitrary schema rename. Captured/native sources whose IDs derive from changed native names still need their own continuity/migration profile; a new element ID cannot be relabeled an unchanged field merely because names resemble one another.

The owner record-type operation is explicit authoring/provenance consistency, not cryptographic authorship, cross-document resolution or Truss owned-lifecycle authority. Truss separately admits actual original ingress/custody, composition storage binding and target support. Core 0.8.0 dispatch/support is not inferred from 0.7.0 source branches; owner pins remain exact. This review narrows the outstanding dependency to extraction/source continuity, physical mapping and owner interface adoption; it does not accept the broader ADR or qualify the native realization of the separately selected reactivation rule.


### Implementation consequences of selected reactivation

The baseline storage-layout.sql schema_change kind CHECK admits only type, prop and rel, and its def_id is a single global int. Keys instead use the owner-local (type_id,key_num) identity. A reactivation implementation cannot merely add kind=key and pack that pair into def_id, reinterpret key_num as globally unique, or clear key_def.retired_rev without preserving prior retirement intervals. For selected key reactivation, author a complete owner-qualified key lifecycle history carrier/home and reconstruction/uniqueness/retention/disclosure rules, then thread it through the versioned physical inventory, report/feed/seed/history contracts and conversion. Historical reads must distinguish each original active/retired interval after a later reactivation. Baseline terminal one-way retirement cannot certify repeated intervals.

The current AcceptanceReport counts additions/retirements and carries rebind events, but has no required reactivation inventory. A same-ID reactivation must not increment typesAdded/keysAdded or be disguised as an ordinary rebind. Selected reactivation therefore requires a versioned auditable report representation for each category's exact before/after lifecycle/source identity, with independent current/historical/feed correspondence. Uninterpreted extensions cannot silently become required reactivation meaning. Preserve the separately selected immutable full-event report home and its native adoption obligations; adding a lifecycle field does not resolve its insertion-generated event dependency.

Terminal retirement avoids these reactivation writes but still needs explicit candidate refusal for a returning identical lineage and complete distinct-incarnation allocation/source/history evidence. Both alternatives preserve old graph/history/key reservations and require no implicit object/key/grant inheritance. Current helper/table/report fragments provide neither branch's complete adopted lifecycle implementation. This assessment records the implementation consequences of the owner-selected reactivation branch. Terminal retirement remains a historical alternative; it does not reopen the product decision or weaken FR-4/US-004.


The [reactivation report declaration alternative](../contracts/bindings/truss-reactivation-report-v0.2.proposal.d.ts) and [closed schema alternative](../contracts/reactivation-acceptance-report-v0.2.proposal.schema.json) make the report change reviewable without adopting it. They propose a separate 0.2.0 report, explicit lifecycleProfile and one exact same-ID transition entry with original owner/lineage, prior retirement revision and complete before/after definition/source snapshots. Key identity is (typeId,keyNumber), never global keyNumber. Existing additions/retirements/rebind meanings remain distinct; inherited property schemas reference exact 0.1.0 definitions without extending its closed root. The proposal is not a new optional field on 0.1.0, not an accepted result ABI, and not a native producer. Shape constraints preserve signed lexemes; exact int32/int16 bounds and actual transition correspondence remain semantic obligations.

For the selected reactivation branch, independently match complete actual retired-to-active transitions against report membership: exactly one per qualified category/identity, no duplicates, omissions or unrelated entries; before retirement must predate report.rev and after snapshot must identify actual reactivation at report.rev. IDs and full lineage remain unchanged, while definition-source provenance may change independently of creation revision. Counts of additions remain zero for these transitions. Complete key history and native storage/parity/disclosure remain separate prerequisites. Existing 0.1.0 report validators/encoding profiles must refuse this new report until exact 0.2.0 schema, byte-profile compatibility and consumer adoption are supplied; generic canonical spelling does not establish wire compatibility. Terminal retirement does not require this alternative report to be silently emitted.

The [key lifecycle history home alternative](../contracts/key-lifecycle-history-v0.1.proposal.sql) preserves the complete owner-local tuple, each retirement/reactivation transition and each intervening definition change. Its foreign key uses the existing UNIQUE(type_id,key_num), while key_def's primary key remains (type_id,key_id); neither identifier is repacked or renumbered. Each row carries complete original before/after definition/source bytes under a separately adopted profile, not JSONB-derived reconstructions. Nullable retirement revisions distinguish active and retired states. The tagged CHECK excludes both-null/both-present retirement or reactivation, while definition_change requires identical prior/result retirement state (including two nulls for an active edit) and an earlier nonnull retirement reference. Its explicit null branches avoid SQL-UNKNOWN acceptance; it does not impose a new unsigned domain on retained catalog identities or prior retirement references. rev is a new positive acceptance revision. seq is local history ordering, not an event sequence, report index, transaction order or wall clock.

The [saved UMF native-source capture](../contracts/key-lifecycle-history-v0.1.proposal.umf.json) retains this entire SQL alternative through the existing owner adapter, JSON reload and stable export. [Scoped receipt](../../04-build/evidence/design-audit/key-history-source.json) observes one table/nine columns, with transition_kind and both byte carriers unresolved and the index statement unhandled by partial declaration extraction. Six integer builtin-syntax observations are not native type/collation/constraint resolution. All original CHECK/FK/index content remains in the native source/AST; nothing is promoted to complete portable inventory. Reproduce with `bun docs/helix/04-build/evidence/design-audit/check-key-history-source.ts` from the Truss root. Complete authored physical IDs, dependency/exporter correspondence and native installation remain separate prerequisites.

Reconstruction for the selected lifecycle starts from the original creation definition at since_rev, reads the complete qualified tuple's transitions through the requested revision in (rev,seq) order and requires every before snapshot/state to match the preceding after snapshot/state. A retirement opens an interval at its actual revision; reactivation closes that interval at its actual revision. Every actual source/definition edit between those transitions also enters the chain as definition_change, without changing retirement state or counting as reactivation. Creation stays the separately retained initial basis. A no-change repeat creates no synthetic history row. An edit while retired requires explicit selected semantic support; the SQL shape does not authorize it. Reject missing, duplicate, reordered, contradictory or unsupported source transitions; never fill a gap from today's key_def. For an original admitted capture cut C, current retired_rev and complete current definition/source at C must match reconstruction through C. Historical target R must be an actual admitted catalog revision with R<=C; project its state from the verified original chain through R, not by comparing it with today's state at C. A later retirement/reactivation or definition edit must not invalidate a correctly reconstructed earlier state. Creation after R proves absence at R only from complete original identity/creation inventory under the selected disclosure profile; a missing basis/history is unavailable, not absence. The owner-local (type_id,key_num,rev,seq) index supports ordered collection without claiming bounded cardinality or native performance. Multiple transitions within a revision are not licensed by the table: the accepted lifecycle profile must define whether they are legal and their visibility before any producer relies on seq. This proposal therefore avoids inventing a uniqueness constraint on (rev,type_id,key_num).

The candidate native profile requires rev/seq/type_id/before_retired_rev/after_retired_rev to resolve to PostgreSQL pg_catalog.int4, key_num to pg_catalog.int2, transition_kind to pg_catalog.text and both definition carriers to pg_catalog.bytea. Reject unresolved or substituted domains/typmods/types rather than coercing a convenient equivalent. The transition tag explicitly uses pg_catalog.C collation: byte-distinct case/space/Unicode spellings cannot satisfy a closed tag via database-default nondeterministic comparison. Exact CHECK operator/function dependencies, including pg_catalog.octet_length(bytea), native PK/index opclasses and referenced schema_rev/key_def identities require original installed-catalog correspondence; qualified names alone do not prove that binding. Nullable revision state and full byte payloads retain their separate original admission rules. No text rendering, JSONB parse or UTF-8 conversion of arbitrary byte carriers is licensed by this native type selection.

The protected acceptance producer must insert actual complete history and update the current definition in the same recoverable transaction, with independent full-tuple/source/state parity before report construction and head advancement. Foreign keys and nonempty bytes alone prove neither continuity nor immutable history. Key retirement's removal of object_key rows remains a separate actual effect; reactivation must validate and reconstruct required reservations from admitted retained values before clearing retirement, never restore obsolete rows blindly. Ordinary callers receive no raw history access; qualified history/report readers require the complete original owner union and current disclosure authority. Retention cannot remove a required interval or source basis while dependent historical/report/feed/seed interpretation remains admitted. Layout/exporter conversion, lifecycle byte profiles, feed/seed inventory and native writer/reader closure remain prerequisites; this source proposal does not qualify a baseline layout conversion or native lifecycle implementation. The owner-selected reactivation behavior governs that implementation.

Hash the complete stored bytes directly and use the existing strict artifact base64 grammar. Snapshot profile pins exact source/native capture and interpretation; this encoding convention does not qualify any native encoder.

The envelope mirrors every baseline key_def field with signed canonical native integer lexemes and explicit null retirement, ordered propertyIds and exact boolean primary status. Semantic admission enforces int32/int16 domains, complete native row parity and selected key-component validity; an empty component list or overflow may be structurally valid but cannot bypass the selected key profile. Full nativeDefinition/sourceDefinition/acceptedBinding/interpretation artifacts retain original bytes, unknown extension content and complete storage/portable meanings rather than reducing them to these mirrors. Resolve each through original custody, verify hashes/bytes/profiles and match its actual owner/lineage/key identity. No absent binding is filled from today's profile: its original admitted absence, if applicable, must be explicitly represented inside the pinned binding artifact.

catalogRevision identifies the original capture cut, not creation or an inferred latest-definition revision; sinceRevision remains immutable creation provenance. A transition's before snapshot is captured at the actual preceding admitted state and its after snapshot at the accepting revision. Reconstruct definition continuity by comparing complete definition/source/binding/interpretation/state meaning under the pinned profile while keeping capture-cut provenance distinct: consecutive captures may have different catalogRevision even without a definition change. Do not require raw whole-envelope byte equality across distinct capture cuts or strip provenance to manufacture equality. Report membership retains each original snapshot artifact unchanged. This snapshot proposal is not permission to convert legacy JSONB into apparent original lexical bytes; unsupported legacy source/capture completeness requires explicit conversion admission or refusal. Snapshot/profile adoption, source extraction and native bounded producer/loader implementation remain open.


### Reviewable US-004 reconciliation wording

The following alternatives prepare the required owner decision; neither changes the governing story or accepts this ADR.

- Reactivation alternative for US-004's retired-redefinition edge case: “A retired element reintroduced with the same exact qualified authored identity retains its original storage identifier only after complete lifecycle validation. A distinct authored identity receives a fresh identifier that differs from every identifier ever issued. Reactivation never transfers identity or implicitly restores old grants, keys or data semantics.” US-004-AC2 remains the fresh-identity no-reuse rule.
- Terminal-retirement alternative: “A retired element cannot be reintroduced with the same exact qualified authored identity. The author must supply a distinct incarnation identity, which receives a fresh identifier that differs from every identifier ever issued. Retained historical definitions and identifiers remain reserved.” US-004-AC2 remains unchanged; add an explicit refusal scenario for same-identity reintroduction.

The comparison packet below predates the owner decision; retain it as historical rationale. Current work must keep FR-4, the story edge case, CONTRACT-003 lifecycle admission, TD-004 and STP-004 aligned with the selected reactivation behavior. Neither display-name changes nor document revisions supply distinct incarnation identity. The reactivation branch must independently validate retained values, keys/reservations, endpoint/ownership/cardinality and current authorization before atomic retirement/head transition; the terminal branch must refuse without catalog/data/history effects. Preserve original historical resolution in both branches. The terminal branch remains a historical alternative; the explicit owner decision below supplies the current product authority.


Owner decision, 2026-10-07: same exact qualified authored identity may reactivate its original Truss identifier after full lifecycle validation. Distinct authored identities still receive fresh identifiers. Current authorization must be independently admitted; old permissions are not automatically restored.
