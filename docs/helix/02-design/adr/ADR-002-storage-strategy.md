# ADR-002: Storage strategy on PostgreSQL — generic catalog storage, partitioned by type

| Field | Value |
|-------|-------|
| Status | **Accepted** with the drafted recommendations. D4, D5 and parts of D6 are provisional until measured (see §Owner decisions) |
| Date | Proposed 2026-10-03; accepted 2026-10-03 |
| Decider | Project owner |
| Drafted by | Claude Code agent |
| Evidence | [SPIKE-001](../spikes/SPIKE-001-apache-age.md), [SPIKE-002](../spikes/SPIKE-002-storage-bake-off.md), [storage layout review](../storage-layout-review.md) |

[ADR-001](ADR-001-language-and-portable-core.md) accepts TypeScript first, a
portable core and measured triggers for a Rust core. Its Node support remains
provisional until L1; this storage decision applies across supported runtimes.

Terminology: UMF is DocumentDrivenDX's machine-readable metamodel and schema
interchange fabric. SQL is Structured Query Language; PostgreSQL JSONB is its
binary JSON storage type. DDL means data definition language, FK means foreign
key, and p95 is the 95th percentile. PRD means product requirements document;
the project PRD has not yet been authored.
HOT means PostgreSQL heap-only tuple updates; WAL is PostgreSQL's write-ahead
log. RFC 3339 is the IETF date and time format used by D3. DDD means
domain-driven design; `umf.ddd` is UMF's semantic projection.

## Context

truss stores connected data described by UMF in the user's PostgreSQL database.
The [product vision](../../00-discover/product-vision.md) promises four
outcomes:

- schema change without per-type table migrations;
- an enforcement status (database, engine or none) for every UMF assertion;
- no silent loss of values or unknown data;
- p95 within 2× of a hand-designed schema for fetch and 1–3 hop traversal.

Three storage strategies were tested:

| Option | Evidence | Result |
|--------|----------|--------|
| B: Apache AGE | SPIKE-001, AGE 1.8.0 on PostgreSQL 18.6 | Rejected. Silent value loss (int64 wraparound, decimal literal precision, dropped explicit nulls), triggers and FKs bypassed by Cypher writes, concurrent writes to one vertex fail with an internal error, variable-length traversal p95 577 ms under 10% writes. Building on AGE would still need most of truss. |
| A: per-type tables generated by UMF | SPIKE-002, PostgreSQL 17.11 (fidelity and enforcement also on 18.6), UMF `master` `24d3bf3c`, UMF core 0.7.0 | Not viable today. UMF's generator emits only the table stage; 12 hand-written DDL items plus a hand-written type policy were needed. `ACCESS EXCLUSIVE` on every revision, two table rewrites, three assertions silently unenforced, four silent value changes, no place for unknown data. |
| C: generic catalog storage | SPIKE-002, same versions | Recommended. No DDL or table locks above `ROW EXCLUSIVE` for revisions, all violators listed before acceptance, 19 of 19 assertions enforced, zero silent value changes on the careful read path, generic query templates. p95 within 2× for fetch, one hop, range and update with prepared statements; two hops at the boundary (1.70–2.32×); 4.8× disk. |

SPIKE-002 also found costs that constrain how C must be built: planning grows
with the number of types on a shared table (7.6–8.0 ms at 105 types), per-type
CHECK constraints on a shared table cost about 14 µs per constraint per statement
for every type, deferred triggers race under READ COMMITTED, and the default
`Bun.sql` decoding loses precision. The
[storage layout review](../storage-layout-review.md) adds open concerns that
SPIKE-002 did not measure: object-level write cost, the cost of storing every
nested record as a child object, the canonical store, and property identity
across revisions.

## Decision

Adopt generic catalog storage (option C) as truss's storage of record on
PostgreSQL, with the constraints below. Per-type ("shaped") tables are a later,
measured optimization behind differential tests, not part of the first build.

Each decision point carries a confidence: **evidence** (SPIKE-002 measured it),
**inferred** (follows from PostgreSQL behaviour or the review, not measured
here) or **choice** (a judgement the owner may reasonably make differently).

### D1. Fixed table set

Truss owns a fixed set of tables. Adding a type, property or relationship adds
catalog rows and, where declared, indexes and partitions; it never adds columns
or rewrites tables. *(evidence: FINDING 3)*

| Layer | Tables | Notes |
|-------|--------|-------|
| Schema catalog | `schema_rev` | UMF documents verbatim and immutable per revision: content hash, exact UMF core version, validation result |
| Binding catalog | `type_def`, `prop_def`, `key_def`, `rel_def`, `rel_endpoint`, plus index and statistics declarations | Derived from UMF and the binding; rebuildable |
| Instance graph | `object` (LIST-partitioned by `type_id`), `edge`, value-row tables for `row` homes | See D2–D6 |
| History | `journal`, RANGE-partitioned by time | See D7 |

### D2. Objects partitioned by type

`object` is LIST-partitioned by `type_id`, one partition per type with a default
partition for long-tail types. The primary key is `(id, type_id)`. Every
reference carries both columns. *(evidence: the partition probe kept planning at
1.0–1.9 ms with 105 types at equal latency; inferred: per-partition statistics,
vacuum and index builds)*

Consequence: PostgreSQL cannot enforce `id` uniqueness across partitions, so it
rests on the single shared sequence. This is accepted; ids are never supplied by
callers.

### D3. Values: one flat JSONB map per object

- `props jsonb NOT NULL`, keyed by catalog property ids rendered as text
  (`'12'`). A missing key means absent; JSON `null` means explicit null.
  *(evidence: FINDING 5)*
- Unknown data goes in a separate `retained jsonb` map and is reported, never
  dropped. *(evidence: FINDING 4, U1)*
- Canonical encodings are fixed per scalar family:
  - integers and decimals are JSON numbers in the author's lexical form;
  - binary is base64 text;
  - timestamps are RFC 3339 text with the author's offset;
  - U+0000 is rejected with a reported rule.

  *(evidence: FINDING 5)* Interpretation always comes from the catalog, never
  from the JSON type.
- Adapters read JSONB as text and parse it with an exact parser. Default driver
  decoding is forbidden in truss's read path. *(evidence: FINDING 5, SPIKE-001 C9)*
- Writes render explicit null as `'null'::jsonb`. The `NOT NULL` constraint on
  `props` stays, so a SQL NULL from `jsonb_set` fails instead of erasing the
  map. *(inferred)*

### D4. Storage homes (provisional thresholds)

Each property has exactly one home, `json` (default) or `row`, recorded in the
binding. Moving a property between homes is a recorded catalog migration. A
property is bound to `row` when any of the following holds *(choice; thresholds
inferred, to be set by measurement V1–V2)*:

- it is written concurrently by independent writers;
- its values are large, or it is written often enough that whole-map rewrites
  dominate;
- it needs per-element indexing or uniqueness over array items;
- it is a very large multi-valued property.

Value-row tables use typed columns per scalar family, so native B-tree ordering
applies.

### D5. Composition (provisional)

*(choice, pending measurement V3)*

- Records with their own identity are objects. Composition with them is an edge
  with owned lifecycle.
- Every composed object carries `root_id`, its aggregate root, so a document
  view is one index range scan.
- **Change from the discovery draft:** records without identity (UMF
  value records such as an address) are stored as structured values inside the
  owner's map, typed and validated through the catalog. If V3 shows no material
  cost to child objects, keep the draft rule (child objects for all nested
  records) and keep `root_id`.

### D6. Edges (edge identity and the `target_type` include provisional)

- `edge` carries `rel_type_id`, `(source_id, source_type)` and
  `(target_id, target_type)`. Composite FKs reference `object (id, type_id)`,
  and a FK on `(rel_type_id, source_type, target_type)` references
  `rel_endpoint`. Endpoint types are therefore enforced by the database with no
  DDL per relationship. *(evidence: FINDING 4, R1)*
- Traversal indexes are `(source_id, rel_type_id) INCLUDE (target_id,
  target_type)` and the reverse. *(evidence for index-only traversal; the
  `target_type` include is SPIKE-002's proposed fix for the two-hop tail,
  unmeasured)*
- Edges take ids from the shared sequence so they can be journaled and carry
  provenance. *(choice; costs disk, see V7)*
- Edges carry `props jsonb` keyed by catalog ids for relationship attributes,
  rather than a separate object row per edge. *(choice, inferred: saves a join
  per hop)*
- Ordered relationships use fractional, lexicographically sortable text order
  keys, not integer ordinals. *(inferred)*

### D7. Canonical store and journal

*(choice)*

- The object row is the canonical current state. The journal is written in the
  same transaction as every engine write and records per-property old and new
  values, schema revision and origin.
- As-of reads are derived from the journal.
- Writes that bypass the engine (plain SQL) are not journaled, and the
  enforcement report says so.

A journal-canonical design (Datomic or XTDB style) is deferred. It can be
adopted later without changing the table set, by making current state a
projection of the journal.

### D8. Property identity across revisions

*(choice; SPIKE-002 R4 followed it)*

- A property keeps its catalog id for as long as its UMF identity (document,
  module, element) is unchanged.
- A revision that changes a property's type or cardinality is accepted only with
  a declared total transform applied in the same acceptance step, as SPIKE-002
  did for one → array. Otherwise it is rejected with every violating object
  listed.
- A new element gets a new id. When a revision defines a field that retained
  data matches, re-binding happens at acceptance and is reported.

### D9. Enforcement layering

*(evidence: FINDING 4)*

- **The engine is the reporting layer.** It validates every write against the
  catalog and names the UMF rule it enforces.
- **Database enforcement only in DDL-free forms:**
  - unique partial expression indexes per partition for keys, cast to the
    declared type, with text keys `COLLATE "C"`;
  - the typed endpoint FKs of D6;
  - partial unique edge indexes for maximum multiplicity;
  - optionally, the catalog-driven validation trigger, at about 0.2 ms per row.
- No per-type CHECK constraints on shared tables. Per-partition CHECKs are
  deferred until measured.
- Cross-row rules, such as minimum multiplicity and aggregate invariants, lock
  the parent object `FOR NO KEY UPDATE` or run SERIALIZABLE. A deferred trigger
  alone under READ COMMITTED is never reported as database enforcement.
- The write path uses `FOR NO KEY UPDATE`, never `FOR UPDATE`, on objects.

### D10. Catalog revisions

*(choice; SPIKE-002 risk, untested)*

- Engines cache the compiled catalog keyed by schema revision.
- Every write transaction confirms the revision it validated against, for
  example with `FOR SHARE` on the current `schema_rev` row, so a revision cannot
  be accepted while a writer is using the previous one.
- Revision acceptance runs the generated violator queries and lists every
  violating object before accepting a tightened rule.

### D11. Execution, indexes and statistics

- Every adapter uses prepared statements or an equivalent plan cache. *(evidence:
  C misses 2× by 2.8–6.6× without them)*
- Truss refuses to run in a deployment that cannot prepare statements (for
  example, a transaction-mode pooler without prepared-statement support) rather
  than silently degrading. *(choice)*
- Indexes and extended statistics exist only where the binding declares them.
  The engine never creates them in response to queries, and the per-partition
  index count is a reported budget. *(evidence for index-count planning cost;
  choice for the rule)*

### D12. UMF boundary

The storage strategy, storage homes, index and statistics declarations, and
canonical encodings are truss-owned binding vocabulary. `umf-binding-1` is
table-shaped and has no generic strategy (SPIKE-002 S8). Truss carries this
vocabulary as a truss-owned UMF extension and proposes it upstream. It does not
fork UMF semantics. Truss reads the UMF core model directly, not the `umf.ddd`
view.

## Consequences

**Positive**

- Schema revisions are catalog writes with row-level locks, and they list every
  violation before acceptance.
- Every UMF assertion in the SPIKE-002 model has an enforcement status, and the
  database enforces keys, endpoint types and maximum multiplicity with no DDL
  per revision.
- Values round-trip exactly, including explicit null, timestamp offsets,
  decimal lexical form and unknown data.
- Query code is generic; the number of templates does not grow with the schema.

**Negative**

- About 4.8× the disk of per-type tables at the tested scale, dominated by the
  edge table and its indexes.
- Two-hop traversal sits at the 2× boundary and heavy fan-out exceeds it.
  Meeting the target may require shaped storage for hot relationships.
- Every write is an object-level write: whole-map rewrite, no HOT updates once
  any expression index exists on `props`, and one row lock per object.
  *(inferred; V1–V2)*
- Plain-SQL readers see opaque catalog ids unless generated views are provided.
  View regeneration on revision is DDL, though cheap.
- Clients must use truss's exact read path; ad hoc tools that decode JSONB as
  JavaScript numbers lose precision.
- Global `id` uniqueness rests on the sequence, not a constraint.

## Concern Impact

Recorded in [concerns](../../01-frame/concerns.md) on acceptance:

- `postgresql`: prepared statements are mandatory; there is an index budget per
  partition.
- `sql-exactness`: the text read path; `FOR NO KEY UPDATE`; no implicit decimal
  rounding; parent locks for cross-row rules.
- `umf-fidelity`: the retained map and re-binding report.

## Alternatives

| Alternative | Why not chosen |
|-------------|----------------|
| A: runtime over UMF-generated per-type tables | The generator covers only the table stage; truss would generate keys, relationships, invariants, migrations and queries per type itself; table locks and rewrites on revision; silent value changes from column types (SPIKE-002) |
| B: Apache AGE | Silent value loss, bypassed triggers and FKs, write conflicts as internal errors, variable-length traversal cache cost (SPIKE-001) |
| C without partitioning (as built in SPIKE-002) | Planning cost and per-type CHECK cost grow with every type in one shared table (SPIKE-002 FINDINGS 4 and 7) |
| One row per value with Datomic-style covering indexes | Real per-property versioning and locking, but object fetch must rebuild rows; Apache Jena SDB's generic triple table lost to native storage. Not measured here |
| Typed columns plus a JSONB overflow map per type | Kept as the future `shaped` strategy, not the storage of record |
| Adjacency lists on the node row | Write contention on high-degree nodes, no foreign keys |

## Conditions that would reverse or modify this decision

From SPIKE-002, plus the review:

1. On the project's benchmark corpus at production scale, with prepared
   statements and a pooler, C's p95 for 1–3 hops exceeds 2× and partitioning or
   covering indexes do not recover it. Then move hot types to shaped tables, or
   reconsider A.
2. Target deployments cannot use prepared statements or plan caching.
3. Users will not accept a 4–5× disk footprint.
4. UMF's generator gains key, relationship and migration stages and
   facet-driven types, and users need typed tables as the storage of record.
5. Engine-side enforcement cannot be made safe across engine instances (D10).
6. V1–V2 show object-level write cost that `row` homes cannot contain for the
   target workloads.

## Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Object-level writes dominate cost | Unmeasured at target workloads | Contention and whole-map rewrites | Measure V1–V2 and set D4 storage-home thresholds |
| Traversal exceeds the 2× target | Observed for some SPIKE-002 shapes | Product performance target missed | Measure V5 with partitioning and covering indexes; apply reversal condition 1 |
| Revision acceptance races across engine instances | Unmeasured | Writes use the wrong catalog revision | Implement the D10 revision check and measure V6 before confirming safety |
| Disk footprint is unacceptable | 4.8× observed in SPIKE-002 | Deployment cost prevents adoption | Measure V7 and apply reversal condition 3 |

## Validation

The follow-up spike named in SPIKE-002 (C partitioned by type, realistic type
counts, data larger than memory, a pooler, Node `pg`, generated read views)
must also measure the following. Each provisional point is confirmed or amended
in this ADR, with evidence, before the code that depends on it is treated as
final:

| ID | Measurement | Decides |
|----|-------------|---------|
| V1 | WAL bytes and HOT ratio per single-property update, maps of 0.5, 2, 8 and 32 KB | D4 thresholds |
| V2 | Throughput with concurrent writers on different properties of one object, `json` versus `row` homes | D4 |
| V3 | Aggregate fetch with 1, 10, 50 and 500 composed children: child objects versus structured values, with and without `root_id` | D5 |
| V4 | Planner estimate error for filters on unindexed, indexed and correlated properties, with and without extended statistics | D11 |
| V5 | Two- and three-hop patterns filtered on intermediate-node and edge properties; edge indexes including `target_type` | D6, reversal 1 |
| V6 | Revision acceptance under concurrent writers with the D10 revision check, across two engine instances | D10, reversal 5 |
| V7 | Disk with and without edge ids; `lz4` versus `pglz` compression | D6, reversal 3 |

## Scope of the evidence

Every claim in this ADR is bounded by these conditions:

- PostgreSQL 17.11 (all suites) and 18.6 (fidelity and enforcement only);
- UMF core 0.7.0 at UMF `master` `24d3bf3c`;
- one five-type sales model with five revisions, synthetic data at 1× and 5×
  (up to 2,001,089 order lines);
- Bun 1.3.11 with `Bun.sql`;
- one shared 4-vCPU VM with cached data, no pooler;
- one client for reads, two writers for updates.

Latency figures are ratios, not absolute performance claims. Nothing here
supports a claim for SQL Server, PostgreSQL 19 or managed PostgreSQL services.

## Owner decisions (2026-10-03)

The owner accepted this ADR with the drafted recommendation for each open
question.

| # | Question | Decision |
|---|----------|----------|
| 1 | Accept option C as the storage of record (D1–D3)? | Yes |
| 2 | Partition objects by type in the first build, or start unpartitioned? | Partition in the first build (D2) |
| 3 | Value records as structured values, or every nested record as a child object? | Structured values for records without identity, with `root_id` on composed objects (D5). Provisional: if V3 shows child objects cost little, revert to child objects and keep `root_id` |
| 4 | Object row canonical, or journal canonical? | Object row canonical; the journal is history, written in the same transaction (D7). A journal-canonical design stays a later option |

| 6 | Refuse deployments without prepared statements, or support them with a reported downgrade? | Refuse (D11) |
| 7 | Require V1–V7 before acceptance, or accept now with points marked provisional? | Accept now. D4 thresholds, D5, D6 edge ids and the `target_type` include are provisional until V1–V3, V5 and V7 report |
