# Migration inspection contract walkthrough — same-version drift

Status: author-reviewed case design, not an independent implementer's review or
executed corpus case. Governing inputs are CONTRACT-008, LM-V01–06,
`LayoutMigrationTooling`, the inspection schema and conformance registry/grammar.
No new inspection method or native authority is introduced.

## Original setup and request

Admit an actual complete installed layout and separately registered read-only
inspection procedures/resources under the original administrative observer
identity. Retain independently expected complete installation, routine, grant,
dependency and selected data inventories, with exact original model/generated
bundle/inventory artifacts. A marker version or Truss collector result cannot
supply the expected inventory. The actual implementation/profile/driver tuple
and isolated environment must be registered before the run claims setup.

Construct `status`'s request from the existing `{procedure,resource}` declaration.
Construct `verify`'s request from `{procedure,resource,expected}`, where expected
is the original registered `{version,bundleSha256,inventorySha256}` pin. Resolve
case references before wire validation; these descriptions are not synthetic
artifact identities or a runnable fixture. No adopted transaction ID, backend
connection, SQL statement or arbitrary callback appears in either request.

Before the first call, independently establish that current complete native
state corresponds to the expected installation under the selected coherent cut.
Invoke status and verify through their exact registered method declarations.
Require observed current original layout/install/native artifacts from status
and matches with complete correspondence from verify. Validate full artifact
bytes and interpretation against the independent starting expectations; a
shape-valid claimed artifact is insufficient. Both results are direct unions,
not generic Outcome wrappers or committed upgrade results.

## Independent drift and comparison

In the owned disposable environment, a separately admitted harness procedure
changes one required routine body or grant while leaving the marker/version
unchanged. Retain its complete original change and independently observed
settlement. Do not dispatch informative SQL from the case as an implementation
method or broaden the inspection principal to perform this fixture mutation.

Invoke verify again with the unchanged original request. Require drift with
complete original native observation and exact differences covering the
independently changed surface. Observe no repair, new attempt/receipt, epoch,
horizon, marker/archive or application data/history effects from inspection.
The earlier matches result and unchanged version cannot authorize continued
readiness. This case does not prescribe status as an integrity verifier: status
returns admitted current observation or unavailable under its selected procedure;
only verify's complete correspondence adjudicates this drift expectation.

Deny one mandatory observation in a separate case while leaving the rest intact.
Require observation_unavailable with no partial native/correspondence payload,
not drift inferred from inaccessible facts. Restore the original complete state
through the separately registered harness and independently confirm settlement;
fresh verification may then match. The test does not reuse the old matches
artifact as a current permit.

## Boundaries and full expected evidence

Normative observers cover result artifacts, complete unchanged managed state,
actual inspection authority/cut and source/expected registration correspondence.
The fixture mutation's effects are separated from each inspection's before/after
inventory. Missing observers or unavailable registered service keep the case
unverified/not_run rather than replacing execution with a marker query.

Current matches and drift cannot settle historical unknown upgrade attempts or
reclassify confirmed commit as rollback. LM-V06 independently covers those
histories via original migration reconciliation. This walkthrough qualifies
neither apply nor provider/managed-service behavior; full populated migration
preservation and separate PostgreSQL/Aurora/Lakebase evidence remain required.
